## TWO SUBTLETIES A FLAT PORT WOULD SILENTLY BREAK (reimplement faithfully - verified in the real code)
1. PAGINATION (`_list_folder`, engine L62-71): loops nextPageToken at pageSize 1000. gog `ls --page <token>` loop must replicate it - a single un-paginated `ls` truncates large folders = silently dropped assets.
2. DEPTH-3 RECURSION (`_collect_files`, engine L302-311): finished VIDEO exports live in per-actor subfolders (Thomas/Mia/Sofia/Helen) NESTED inside the fuzzy-matched finished folder (`_find_finished_folder`, FINISHED_RE = finish|export|upload|final). A flat ls of the finished folder sees only subfolders (no files) -> FALSE "EMPTY" -> a worse failure than the auth gap (a real ad reported missing). The gog port must recurse depth<=3 exactly as the engine does.

## THE ONE OPEN ITEM: CREATE_PERMISSION / _share (empirically probed; recommendation = drop it)
EMPIRICAL FINDING (3 live shared-drive assets from the AdsUpload VIDEOS tab, driveId 0ACOzds-8-0G6Uk9PVA): the public thumbnail endpoint `drive.google.com/thumbnail?id=X` is NOT anonymously serving these files (302 -> lh3.googleusercontent.com -> HTML, not image). So per-file "anyone-with-link" public access is NOT in effect - consistent with shared-drive org policy commonly BLOCKING "anyone" links, which means the old `_share` (type=anyone, in a try/except that silently returns False) was likely FAILING or a no-op on the shared drive already.
INFERENCE: since intakes have been running and the workflow verifies col-A =IMAGE renders ([[reference_meta-video-preview-thumbnail-lag]]) while the files are NOT anon-public, render must work via OWNER/DOMAIN context (the sheet + the shared drive share owner adam@cleangreen.com; Sheets =IMAGE fetches in that workspace context, not anonymously). If render does NOT depend on an "anyone" permission, then `_share` is NOT load-bearing and dropping it is safe = Option A = ZERO new credential, fully no-gate internal port.
WHY I DO NOT HARD-ASSERT IT: the decisive confirmation is VISUAL (does col-A =IMAGE actually render in the live sheet for a row whose assets were never anyone-shared) and cannot be proven headlessly with certainty (the Sheets =IMAGE fetch context - anonymous vs owner - is the unknown; a quick col-A read came back empty on the rows I sampled, so I could not self-confirm a rendered row).
RECOMMENDATION (unblock now, verify on first live intake): build `_share` as a CONFIG-FLAGGED no-op, DEFAULT OFF (Option A). The port ships immediately with no token. On the FIRST real post-port intake, meta-ads VISUALLY confirms col-A renders (it already does this as standard QA). If it renders -> Option A confirmed, done, no gate ever. If it does NOT render -> flip the flag to Option B: `gog` has no share verb, so mint a Drive OAuth token (`gog --access-token <minted>` - gog supports it; or a Drive v3 permissions.create helper) - BUT note "type=anyone" may itself be blocked on the shared drive, so Option B may actually require a DOMAIN-share or accepting owner-context, i.e. a small sharing-model decision (the only thing that becomes an Adam/orch input, and ONLY if render fails). Isolating it behind a flag = the port is never blocked on this.
DOWNSTREAM CAVEAT (flag, not this lane): "downstream fetch" = mmb pulling the asset into Meta drafts. If mmb/AdManage fetches the Drive file as an authed workspace user it is fine; if it needs public access that is an mmb-lane concern (mmb is mid-migration) - out of scope for the intake port, noted so it is not lost.
