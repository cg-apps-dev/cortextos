# Switch an Agent's Claude Account (bearer/setup-token)

Move an agent's Claude runtime from one Max account to another with 100% accuracy: flip the token, flip the attribution, prove the agent is alive on the new account, and prove nothing else broke. Executing owner: the-orchestrator (account moves are orchestrator-coordinated fleet ops, never per-agent self-serve).

**Proven live 2026-07-09** (Adam commission): 5 agents migrated sequentially in ~15 min, zero failures, zero rollbacks, zero dedup races - every parameter below comes from that run's notes. Canonical technical spec: the `agent-auth` skill (`.claude/skills/agent-auth/SKILL.md` in each agent dir, org-shared via `list-skills`).

**PRIMARY PATH: the shipped one-command tool** - `cortextos switch-agent-account` (shipped 2026-07-09, merge `4576c07`; usage in "The one command" below). It enforces every gate in this SOP as a hard in-script assert. The per-agent sequence below is the normative spec the tool implements AND the manual fallback - execute it by hand only when the tool or daemon is unavailable, or when auditing a tool run.

## Scope (v1)

- **In**: agents running on bearer setup-tokens (`.env` `CLAUDE_CODE_OAUTH_TOKEN`) - the fleet rule mode.
- **Out**: login/keychain-mode agents (different procedure, keychain health checks first - see the agent-auth skill §4 "MIGRATION PROCEDURE (login/keychain -> bearer)" and §6 "TROUBLESHOOTING"). Do NOT apply this SOP to them.

## The three credentials (confusing these is the #1 procedure error)

- **Setup-token** (`sk-ant-oat01`, minted `claude setup-token` AS the account): RUNS the agent. ~1 year, self-contained.
- **Usage/PKCE credential** (`oauth/accounts.json`): reads the usage API only. Does NOT run an agent; a setup-token gets 403 on the usage API.
- **Stored/reused access_token**: dead for runtime. Only a fresh setup-token minted as the target account works.

## The token vault (canonical source)

Runtime setup-tokens live in the vault: `~/.cortextos/default/state/oauth/setup-tokens/<account>.token` (file 0600, dir 0700, out-of-repo, backup-excluded, leak-scan-allowlisted; validated by security-agent on creation, perms-hardening queued). The vault stores RUNTIME setup-tokens only - never usage/PKCE creds.

- **Ingest** (new mint, HUMAN GATE - Adam mints AS the target account in a clean browser context): deliver as a file -> fingerprint (bare method, below) -> write to vault -> SHRED the delivery file. Tokens last ~1yr; no routine re-minting.
- **Fingerprint standard**: bare-value sha256 (`printf '%s' | shasum -a 256`-class, never `echo` piped - the trailing newline yields a different hash for the same secret). State the method with every fingerprint you report.
- **Rollback source**: the vault RETAINS the prior account's token after a move - rollback never depends on scavenging an old `.env`. CAVEAT: this holds for a SWITCH (the prior account's token is still valid, so it is a real rollback source). It does NOT hold for a RE-MINT after a REVOCATION - see the re-mint rule below: a revoked prior token is not a rollback source, and leaving it under the live `<account>.token` name turns the vault into a recovery-trap.

## Re-mint (rotation / post-revocation) - bank-to-store is mandatory, and reconcile

A SWITCH moves an agent between accounts whose tokens already sit in the vault. A RE-MINT is different: the same account's token is replaced (revocation, rotation, or leak response), Adam mints a fresh one, and the fleet redeploys. The failure mode this section prevents: the redeploy flips `.env` (both halves) but never updates the vault, so the vault silently drifts from what agents actually run.

- **Bank BEFORE (or as part of) the redeploy, never after.** A fresh mint is written to the vault as `<account>.token` (0600) BEFORE it lands in any agent `.env`. The `.env` redeploy is a COPY-FROM-VAULT, never a direct paste that skips the vault. An incident redeploy under time pressure is exactly when this is skipped - so it is a hard step, not a cleanup.
- **A revoked prior token is DEAD, not a rollback source.** On a post-revocation re-mint, rename the prior vault file to `<account>.token.revoked-<YYYY-MM-DD>` (rename, never delete - audit + containment; the `.revoked-*` suffix does not match the `*.token` glob, so tooling will not pick it up). The fresh token becomes the canonical `<account>.token`. Leaving the revoked token under the live name means a restore-from-vault silently deploys a dead token = a 401 across every agent on that account, discovered only at the next restart.
- **Reconciliation assert (the missing guard).** After ANY mint/redeploy, and periodically as a standing sweep: for each account, assert `vault <account>.token` bare-method fingerprint == the live `.env` `CLAUDE_CODE_OAUTH_TOKEN` fingerprint of EVERY agent attributed to that account (attribution via `cortextos bus list-agent-accounts`). A mismatch = the vault is stale/wrong for a LIVE account - fix before it becomes a recovery-trap. DONE-WHEN: every in-use account's vault fingerprint equals its agents' live-`.env` fingerprint. (Dormant vault accounts with zero agents are exempt - no live token to match.)
- **Incident of record (2026-07-29 -> caught 2026-08-03):** the shared me.com setup-token was revoked; a fresh one was minted and redeployed to 10 agents' `.env`, but the vault kept the revoked Jul-9 token under `me-com-max.token` for 5 days. No leak (the working token had 10 live `.env` copies) but a live recovery-trap: a restore-from-vault would have deployed the revoked token to all 10. Surfaced by a live-`.env`-vs-vault fingerprint sweep, reconciled (current token banked, revoked token renamed `.revoked-2026-07-29`). Root cause = a redeploy that skipped the vault. This subsection is the prevention.

## Preconditions (all must hold before touching anything)

1. **No auth wobble in progress** anywhere in the fleet - never move an agent during an active auth incident.
2. **Target token in the vault, fingerprint-asserted.** DONE-WHEN: the vault file's bare-method fingerprint matches the recorded expected fingerprint - asserted BEFORE every apply, not once per wave.
3. **One agent at a time, verify each before the next.** A batch move is N sequential single moves; stop on the first failure.
4. **Fleet baseline snapshot**: pool sampler read (`multi-account-usage.json`: all accounts, 5h/7d, ok-flags) + per-agent attribution via `cortextos bus list-agent-accounts`. DONE-WHEN: both captured in the run log.

## Per-agent sequence

1. **Baseline read** (fresh, not cached): the agent's `list-agent-accounts` attribution + current heartbeat + daemon/PM2 state. DONE-WHEN: baseline recorded in the run log.
2. **Flip BOTH halves together** - a half-flip mislabels attribution:
   - `.env`: `CLAUDE_CODE_OAUTH_TOKEN=<vault token>` - exactly ONE active token line (strip stale/commented/placeholder lines), file mode 600.
   - `config.json`: `usage_account` = target billing-account name (the setup-token will not token-match `accounts.json`; this override is what attributes usage correctly).
   - DONE-WHEN: both files re-read and verified to name the target (`.env` token fingerprint = vault fingerprint, bare method; `usage_account` string = target account name).
3. **Restart = `stop` -> wait 60s -> `start`** - never a plain restart (daemon dedup / orphan-poller race; zero races in 5 cycles at 60s, so 60s stands as the wait). A "deduped - already running" on start can mean the first start already succeeded: check `cortextos status` for running + fresh uptime before retrying. DONE-WHEN: old process confirmed gone before `start`, agent shows running with fresh uptime after.
4. **Post-boot verification** (boot-verify at +40s post-start; all four points, each read fresh):
   - **Bearer proof (LAYERED - no single instrument may pass or fail it alone)**: the live process runs THE target token. Four layers, all required: (i) `.env` re-read: token fingerprint = vault fingerprint (bare method) - proves the RIGHT token is configured; (ii) **process start time AFTER the `.env` flip time** (`ps -o lstart -p $PID` vs the file's mtime - both reads proven reliable) - closes the file-vs-process gap, since a process spawned pre-flip runs the OLD token no matter what the file now says; (iii) attribution (below); (iv) inference probe (below). CORROBORATOR (strong when readable, never sole evidence, never a rollback trigger): the process-env read - `ps eww -p $PID | tr " " "\n" | grep "^CLAUDE_CODE_OAUTH_TOKEN=" | cut -d= -f2-` piped to bare sha256, first 12 hex === vault fingerprint (proven 5/5 at +40s on fresh processes, run from the operator session). `ps` READ RULES: pair with a planted positive (a var known present, e.g. `CTX_AGENT_NAME`) and repeat once; an EMPTY read = INDETERMINATE (try another layer, never rollback on it) - the empty-input hash `e3b0c442...` offered as a "fingerprint" is THE tell that nothing was read; reads are caller/session- and time-sensitive (a cross-session read of the same PID can return nothing minutes after an own-session read worked). The in-session self-probe (agent hashes its OWN env var from a tool shell) is STRUCTURALLY DEAD - arbitrated 2026-07-09 by security-agent: the harness scrubs the runtime token from tool shells fleet-wide (two bearer agents both read count=0 in-shell while process-env reads proved bearer), so it reads 0 for every bearer agent and proves nothing. Never use it. Tool path: the hardened `hashLiveProcessToken` util as the corroborator layer, proven against these caller/time quirks first, with empty-read = indeterminate semantics.
   - **Attribution**: `cortextos bus list-agent-accounts | grep <agent>` = target account. Read the LIVE resolver, not the snapshot file (the snapshot file lags; the live read was correct at +40s for all 5). Observed attribution lag: none.
   - **Heartbeat**: the agent self-reports within ~2 min - boot-clean, no 401/login prompt, inbox reachable, crons intact. Anchor freshness on the RESTART TIME, never wall-clock (a recent-but-pre-bounce heartbeat must not pass a hung agent).
   - **Inference probe**: the agent's own bus round-trip self-verification message IS the probe (agent-level - proves the agent runs inference, not merely that the token is valid). Tool path: a bus echo round-trip.
   - DONE-WHEN: all four observed; any miss = stop, do not proceed to the next agent.
5. **Post-migration functional sweep** of every lane the runtime change touches (standing-rules registry: "migration silently drops a side path"). Immediate half: boot/inbox/crons/inference (step 4's self-report). Lane-depth half: each of the agent's real lanes exercises on its next natural cycle - the agent flags anomalies rather than pre-declaring clean. Bearer specifics: the claude.ai connector bridge DIES under bearer - and a bridge call under bearer HANGS the session (no error, no fallback), so this audit is PRE-FLIP, not post: grep the agent's full EXECUTION SURFACE for bridge-tool calls by CONTRACT CLASS, never a hand-enumerated sample (security tightening 2026-07-09: a sample under-covers - a Composio DRIVE/SLACK action slips a grep that only lists GOOGLESHEETS_). FIVE detection classes, all required: (a) the claude.ai bridge prefix-class `mcp__claude_ai_` (catches every bridge connector generically), (b) the Composio entry points `COMPOSIO_MULTI_EXECUTE_TOOL` (uppercase - the fleet's actual entry point) and `mcp__composio`, (c) the Composio app-action shape (`[A-Z]+_`-prefixed app actions - GOOGLESHEETS_/GOOGLEDRIVE_/SLACK_/GMAIL_/...) - **EXCLUDE credential env-var names** (a trailing `_API_TOKEN`/`_API_KEY`/`_TOKEN`/`_KEY`/`_SECRET`/`_ID`, e.g. `CLICKUP_API_TOKEN`), which are the own-cred REPLACEMENT pattern, not a Composio action (a real action reads like `CLICKUP_GET_TASK`; security-agent + the-axon-agent, 2026-07-24), (d) **PROSE DIRECTIVES naming a bridge tool in natural language** (case-insensitive: `composio`, `claude.ai bridge`, `claude ai connector`, `bridge MCP`) - the token-class grep (a)-(c) reads 0 on an instruction like "use the Composio Google Sheets MCP to read candidate rows," but a prose directive telling the session to use a dead tool is EXACTLY as lethal as a literal call-site: it makes the session place the hanging call, (e) **LOWERCASE snake_case connector-ACTION names, defined by SHAPE not by vendor** (a bare `verb_noun` pattern like `\b(search|list|get|create|update|filter|read|fetch|send)_[a-z_]+\b` - e.g. `clickup_get_task`, but also vendor-less Airtable-style `search_bases`/`list_tables_for_base`) - no capital letters, no vendor keyword required, so this class matches NEITHER the uppercase token classes (a)-(c) NOR the prose-keyword class (d), yet hangs under bearer identically. **A VENDOR-ANCHORED (e) pattern (requiring `clickup_`/`slack_`/etc as a prefix) UNDER-COVERS and produces a false clean** - the-ad-strategist's own sweep missed a live, armed `search_bases`/`list_tables_for_base`/`list_records_for_table` trap on its own weekly-report cron's PRE-FLIGHT step (2026-07-24) for exactly this reason; anyone who ran (e) vendor-anchored must re-sweep. **EXCLUDE JSON/string-literal labels** that merely look like an action name (e.g. `source: 'clickup_rest_scripted'`) - these are own-cred artifacts, not calls (the-analyst, 2026-07-24). (2026-07-24 amendment, mmb+meta-ads: a token-only sweep scored `agents/meta-ads-agent/skills/{adset-batch,launch,analysis}/SKILL.md` clean, missing 3 armed prose-trap files - one was mmb's OWN live-read batching skill, on its real next-run path; the same-day follow-up surfaced class (e) as a distinct blind spot neither prior class covers). Surface = local `.claude/skills/` AND every remote skill the agent live-reads at run time (its IDENTITY/MEMORY/cron prompts name them; a local grep cannot see those - and the enumeration is only as complete as the prompt naming, so a transitively-referenced remote skill can hide: the live-verified DONE-WHEN is the backstop). **DEFAULT SCOPE = sweep BY DIRECTORY** (the whole `.claude/skills/` tree + every bootstrap file), not by tracing which files a cron or skill happens to name - name-tracing under-covers (see the cron-layer transitive-closure note below) and is only reliable for PRIORITIZING which already-swept hit is live-reachable, never for narrowing what gets swept. **Sweep the CURRENT REMOTE ref** for any repo the agent live-reads (`git fetch` + read `origin/main`), never a possibly-stale local clone - a local clone days behind origin can miss a trap armed that week (cro-agent, 2026-07-24). **A hit's meaning is triaged, not blind-matched**: (i) DESCRIPTIVE vs DIRECTIVE - a memory/audit entry recording that the bridge is dead, or a past incident, is a record, not an instruction site, and needs no remediation (security-agent, 2026-07-24); (ii) UNGUARDED vs ALREADY-REMEDIATED - count sites that INSTRUCT bridge use with no own-cred redirect, not raw mentions of the old tool name - a correctly-remediated site necessarily still NAMES the old tool to say "never use this," so a raw mention-count over-flags a clean file as maximally armed (meta-compliance-agent, 2026-07-24); (iii) an own-cred FILENAME or a DO-NOT-USE prohibition line that itself contains a banned action name (e.g. `slack_client.py`, or "do NOT use slack_read_thread") both superficially pattern-match but are not traps - re-flagging these forever trains sweepers to ignore real hits (the-team-lead, 2026-07-24). **REQUIRE A POSITIVE CONTROL before trusting any 0-hit result**: run the same grep against a corpus KNOWN to contain each class first (or seed a one-line probe file per class) and confirm every class fires - an empty result from a broken pattern (unquoted globs, a multi-path argument that silently fails to expand, a stale/wrong file path) looks IDENTICAL to a genuine clean, and at least three agents independently nearly reported a false clean this way (cro-agent, the-axon-agent, meta-ads-agent, 2026-07-24). Sweep **PER-PATH, one grep per path, never one grep over a combined multi-path argument** (shell glob/array expansion can silently fail for a subset of paths with no error - the-axon-agent, 2026-07-24). **REMEDIATION is AT the instruction site - not above it, not below it** (2026-07-24 amendment, meta-ads+the-analyst: a top-of-file DO-NOT-USE banner does not fix a step further down, AND a correction placed BELOW an armed step is equally useless - the-analyst found the trap in numbered step 1 with the correct own-cred path documented ~30 lines below it; execution jumps straight to the numbered procedure and never reads past it in either direction). DONE-WHEN: every class-(a)-(e) hit is remediated inline (own-cred tool + a DO-NOT-USE warning at that exact site), the positive control passed before the sweep is trusted, and the class-grep across all five classes reads 0 hits - a file-level "clean" declaration with an unremediated step further above or below does not satisfy this. **Any sweep completed before 2026-07-24 checked classes (a)-(c) only, and/or remediated at the file/banner level rather than per-site, and/or ran class (e) vendor-anchored - it must be RE-RUN covering all five classes (with the FP exclusions and per-site remediation above) before its clean-PASS is trusted.** (Live proof 2026-07-09: three hung mmb sessions - the Composio dependency sat in a brain-main live-read skill, invisible to any local-file audit.) DONE-WHEN: immediate half self-reported; lane-depth flagged-on-anomaly on the next cycle of each lane.

5b. **Cron-level defense-in-depth map** (2026-07-24, fleet-wide re-sweep): classify every cron into one of three shapes, alongside the class-(a)-(e) sweep. (i) **CONCRETE-COMMAND** - the prompt names the actual own-cred command/script directly (e.g. `bash scripts/x.sh`, `cortextos bus collect-metrics`); a second layer exists, because no skill is ever invoked, so an armed skill cannot route this cron into a hanging call. (ii) **DELEGATES TO FILE CONTENT** - the prompt says "read X and follow it," where X is ANY file whose content executes, not just a `SKILL.md` (`HEARTBEAT.md`, `IDENTITY.md`, any read-and-follow target); the delegated file IS the executor, so an armed instruction anywhere in it - or anywhere in its TRANSITIVE CLOSURE, i.e. every file it in turn tells the reader to read - hangs the cron directly, with nothing catching it. (iii) **NO DELEGATED EXECUTOR** - inline prose fully spelling out the task with no file/skill pointer at all; nothing to arm, the safest of the three shapes. **Do NOT ask an agent to convert a (ii)-shaped cron into (i)** - some crons are genuinely skill-shaped (a research routine, a checklist), and forcing a concrete-command prompt trades a thin real layer for a brittle contorted one; the goal is a KNOWN MAP, not a forced restructure. **PRIORITIZE traps behind a (ii)-shaped cron FIRST** - a trap reachable via a cron with no second layer is strictly more dangerous than the same trap behind a (i)-shaped cron (the-analyst's own near-miss survived only because its cron happened to name a concrete script - defense-in-depth by luck, not design). Cross this with the class-(e) vendor-anchored-false-clean risk above: an agent with BOTH a vendor-anchored prior (e) sweep AND (ii)-shaped crons is the highest-priority re-run population (the-ad-strategist). **The swept surface for a (ii)-shaped cron is the delegated file's FULL TRANSITIVE CLOSURE, not just the named file** - e.g. a cron naming only `HEARTBEAT.md` can chain onward into 7-8 further skills (comms, tasks, event-logging, memory, guardrails-reference, knowledge-base, human-tasks, approvals), each an equally live hang vector; a 1-file check understates the real exposure by an order of magnitude. Do not hand-trace the closure to scope a sweep (chains run 2-3 deep and a skill can name another skill in prose rather than a path, so hand-tracing is easy to get wrong) - sweep the whole directory by default (see step 5's default-scope rule) and use closure-tracing only to PRIORITIZE which already-swept file is actually cron-reachable. The closure is a runtime snapshot, not a standing guarantee: a later one-line edit to any file in the chain ("also read X") silently widens the blast radius with no cron change at all, so re-derive it at every sweep, never trust a prior report. **CRON PROMPTS THEMSELVES ARE A SIXTH SURFACE**, separate from any file: prompt text lives in `crons.json` (the real nested path is under `.cortextOS/state/agents/<agent>/`, not the commonly-documented `state/<agent>/` - verify live with `cortextos bus list-crons <agent>`, which loads from `config.json` for some agent instances instead if `crons.json` is empty there - check both). `list-crons`'s CLI display TRUNCATES long prompts to roughly 60 characters plus an ellipsis, which can hide an armed action sitting mid-prompt entirely - parse the raw JSON, never trust the truncated display alone (this is likely why cron-prompt traps went unswept fleet-wide until 2026-07-24). A prompt can embed a bridge action directly with no file or skill involved at all. Remediate a cron by `remove-cron` then `add-cron` with the corrected prompt and the IDENTICAL schedule expression - never hand-edit `crons.json`, the daemon can overwrite it - and verify the next-fire timestamp afterward. **COMMON-MODE WARNING**: `HEARTBEAT.md` and the bootstrap templates it is generated from (`templates/agent/`, `templates/analyst/`, `templates/agent-codex/`, `templates/hermes/`, `templates/orchestrator/`) are the fleet's single highest-leverage propagation surface for this whole class - nearly every agent runs the identical "read HEARTBEAT.md and follow it" cron shape with no cron-level second layer, so one armed edit to a shared template would hang every agent's heartbeat simultaneously. Worse, the heartbeat mechanism IS the fleet's liveness signal, so a common-mode heartbeat hang would leave the fleet looking idle rather than broken, with no alert generated anywhere. All 5 templates were swept clean 2026-07-24 (baseline, research-agent) - note 4 of the 5 (`agent`, `agent-codex`, `analyst`, `orchestrator`) delegate onward to further skills while `hermes` is self-contained, so their closures differ. Standing-coverage implication (flagged to the-orchestrator, not yet actioned as tooling): these templates warrant change-control weight out of proportion to their size, and fleet liveness needs at least one detector that does NOT itself depend on the heartbeat path.
6. **Only then the next agent.** Transient burst-429s when several agents land on one account and boot close together are a concurrency throttle, not a cap and not a bad token - stagger and wait, never re-mint for this.

## Rollback

Trigger: any step-4 point failing (or a step-2/3 failure). The vault retains the prior account's token (`<old-account>.token`) as the rollback source: re-apply it BOTH-halves (step 2), stop-wait-start (step 3), and run the same four-point verification (step 4) against the OLD account. A verify-fail must end in a KNOWN state - prior account, running - never an ambiguous half-flip. (Live run: 0 rollbacks needed. Tool path: snapshot-restore of the captured pre-state.)

## Fleet-level watch during a wave

- Re-read the pool sampler after each agent: account rebalances can churn global gating and wedge UNMOVED agents - per-agent `usage_account` overrides are the fix.
- The vacated account's 7d burn sheds at its weekly reset, not immediately - expected, not a leak.
- Multiple agents CAN share one account's setup-token (they then share that account's 5h/7d caps) - deliberate concentration is a capacity decision, take it knowingly.

## Cron-prompt sweeper (inlined, not path-referenced - 2026-07-24)

Inlined deliberately rather than pointed to by path: the-team-lead's copy lives in their own agent dir, which would not resolve for any other agent (the same portability failure the class-(e) fix exists to prevent). stdlib-only, macOS/Linux (shells out to `find`); reports the FIRST `crons.json` match per agent - iterate all matches if an agent ever runs multi-instance.

```python
#!/usr/bin/env python3
"""Bearer-killer sweep of the CRON-PROMPT surface (the 6th surface).
Cron prompts live outside the repo, so file greps never see them, and
list-crons truncates them (~60 chars) so mid-prompt traps stay invisible.
Usage: python3 cron-surface-sweep.py <agent-name>
"""
import json, os, re, subprocess, sys

agent = sys.argv[1] if len(sys.argv) > 1 else ""
root = os.path.expanduser("~/.cortextos")
# Self-locate: the documented path (CTX_ROOT/state/AGENT/crons.json) is stale.
hits = subprocess.run(["find", root, "-name", "crons.json", "-path", "*" + agent + "*"],
                      capture_output=True, text=True).stdout.split()
if not hits:
    sys.exit("no crons.json found for agent: " + agent)
path = hits[0]
print("surface:", path)

data = json.load(open(path))
raw = data if isinstance(data, list) else data.get("crons", data)
crons = raw if isinstance(raw, list) else list(raw.values())

CLASSES = {
    "a claude.ai-bridge": r"mcp__claude_ai_",
    "b composio-entry":   r"COMPOSIO_MULTI_EXECUTE_TOOL|mcp__composio",
    "c UPPER-action":     r"\b(GOOGLESHEETS|GOOGLEDRIVE|SLACK|GMAIL|CLICKUP|NOTION)_[A-Z_]+",
    "d prose-bridge":     r"(?i)composio|claude\.ai bridge|claude ai connector|bridge mcp",
    "e lower-action":     r"\b(clickup|slack|gmail|notion|googlesheets|googledrive)_[a-z_]{3,}",
}
DELEGATES = r"(?i)read .*SKILL\.md|follow its instructions|\.claude/skills/"

for c in crons:
    prompt = c.get("prompt") or ""
    layer = "SKILL-DELEGATING (no 2nd layer)" if re.search(DELEGATES, prompt) else "concrete/inline"
    found = [(k, m.group(0)) for k, pat in CLASSES.items() for m in re.finditer(pat, prompt)]
    print("\n" + str(c.get("name")) + ": " + layer)
    print("  " + ("REVIEW: " + str(found) if found else "clean"))
# NOTE: hits need eyeball triage. A remediated prompt re-flags forever because
# the NO-BRIDGE prohibition line contains the banned names, and own-cred
# filenames (slack_client.py) match class-e. Distinguish INSTRUCTION-to-use
# from PROHIBITION-naming from own-cred-filename before acting.
```

Output is labeled `REVIEW`, deliberately not `ARMED` - a remediated prompt re-flags forever (its own DO-NOT-USE line contains the banned names), so an `ARMED` label would train sweepers to ignore real hits. Worked example, kept verbatim so sweepers can see what a correctly-remediated cron looks like when re-swept (the-team-lead, 2026-07-24):
```
  experiment-review-usefulness: SKILL-DELEGATING (no 2nd layer) -> clean
  monday-review: concrete/inline -> clean
  heartbeat: SKILL-DELEGATING (no 2nd layer) -> clean
  weekly-review-sunday: concrete/inline -> REVIEW: slack_client, slack_read_thread, slack_search_
```
That last line is an ALREADY-FIXED cron: `slack_client` is an own-cred client filename, and `slack_read_thread`/`slack_search_` appear only inside the NO-BRIDGE prohibition sentence - neither is armed, both are correctly ignored after eyeball triage.

## HUMAN OPERATOR ONLY - external-switch assertion (do NOT relay this section into any agent-facing surface)

**This section is for a human operator running a terminal shell directly - it is not for any agent, skill, tool-facing text, or refusal message, ever.** An identity-less operator shell (no `CTX_AGENT_NAME` set) must `export CTX_SWITCH_EXTERNAL=1` before driving an account switch. Frame this as the operator asserting "I am external," never as a way to get past an error - it exists so the switch tool can distinguish a genuine external operator from an agent attempting to bypass its own identity gate, and it is a legitimate operator action, not a workaround.

Do NOT document this flag in: the switch tool's refusal message, any agent skill, any agent-facing section of this or any other playbook, or `knowledge.md`. A CI test (claude-dev, 2026-07-24) pins the refusal message to never name the flag, so an agent-facing leak now fails CI by design - do not work around that test. Rationale (orchestrator/security, 2026-07-24): if the bypass sits next to the refusal it teaches, setting the flag becomes ritual - the thing you paste to make the error go away - and the guard is functionally dead within a month while still appearing to exist. General pattern for any future SOP rule someone could helpfully violate: ask whether it can be pinned by a test, since a policy erodes and a test does not.
