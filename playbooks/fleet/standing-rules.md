# Fleet Standing Rules

The canonical home for cross-agent STANDING RULES - hard rules every agent follows, distinct from the per-agent playbooks (which document a single agent's process). A playbook says "here is how this process runs"; a standing rule says "here is a constraint that holds across the fleet, regardless of process." Rules live here, beside the processes they govern.

Each rule is titled, dated, and states the rule + why it exists. New rules land here as they are ratified. The fleet-wide non-negotiables that are structural to every agent (no em dashes; Pacific Time for human-facing times) live in each agent's `GUARDRAILS.md`; this file is for cross-agent operating rules that are not per-agent guardrails.

## Standing rule: playbook maintenance is part of Definition of Done

**Rule.** Updating the affected playbook is part of the definition of done for any workflow, cron, or skill change. A change is not "done" until the playbook that documents it is current - the code/config change and the playbook update land together, not as a follow-up.

**Why.** The playbook tree is only trustworthy if it is continuously current. A workflow that changes without its playbook updating silently turns the SOP into a stale claim - the exact failure mode the playbook system exists to prevent. Treating the doc update as optional or deferrable is how documentation rots; treating it as part of "done" is how it stays load-bearing. The-sop-keeper maintains the tree, but the trigger is any agent's change: flag the-sop-keeper (via the-orchestrator) on any workflow/cron/skill change so the playbook is updated via a reviewed branch, never a silent live edit.

**Applies to.** Every agent, every workflow/cron/skill change. See the fleet playbook index at [../README.md](../README.md).

**Corollary (parked-tree served-refresh, 2026-11-05 PT).** When the shared checkout is parked on another branch (not main), landing a TRACKED playbook change to main is not yet "done" on the SERVED side: main holds the new content, but the working-tree copy that playbook-reads actually open is still the parked branch's old version (SOURCE correct, SERVED stale). A tracked-playbook land is done only after the working-tree copy is refreshed from main - `git show main:<path> > <path>` (no staging; NOT bare `git checkout main -- <path>`, which silently stages into the shared index) - verified by `git diff main -- <path>` returning empty. Same SOURCE-vs-SERVED split as served-skill-copy propagation, applied to tracked playbooks. Origin: a tracked gated-restamp land (2026-11-04) left the working-tree copy stale under a tree parked on a feature branch; the orchestrator's playbooks_vs_main recorder caught it (0 -> 1 wrong).

## Standing rule: every caught error becomes a codified gate (error-class registry)

Ratified 2026-07-08 PT (Adam accuracy directive, orchestrator-approved plan WS-A3).

**Rule.** Every fleet error caught by Adam or any agent gets encoded within ONE DAY of being caught: always as a playbook gate (a terse DONE-WHEN post-condition in the owning playbook), and additionally as a scripted machine check where one is feasible. The error class is registered below so the same class is never re-solved from scratch. Route: the catching/owning agent root-causes its own lane; the-sop-keeper codifies via reviewed branch; the-orchestrator merges.

**Why.** The col-A previews case proved that a documented rule an agent is trusted to remember is necessary but not sufficient - accuracy comes from enforcement. Machine-checkable gates fail loudly when a step's output is wrong; prose does not. Registering the class (not just the instance) is what turns one mistake into fleet-wide immunity.

**Gate placement boundary.** Verify-gates live in PLAYBOOKS (on-demand reads) and scripts, never in boot files - hardening adds zero boot weight. Gates are one terse DONE-WHEN line per step; gate-bloat is its own accuracy risk (agents skim long checklists).

**Format contract (machine-countable, feeds the A4 accuracy metric).** The registry is an input to the analyst's fleet accuracy metric, so its format is a contract (the-sop-keeper holds it): every instance in a row carries its own `YYYY-MM-DD PT` date stamp with escaped-vs-self-caught noted where known (escaped = it left the owning agent, per the A4 boundary definition); registry-touching commit messages state the row-count transition, and a candidate promotion says PROMOTION explicitly. Three counters derive mechanically from git history: new classes/wk (discovery), new instances of an encoded class/wk (gate failure - the one that must trend to zero), promotions/wk (recurrence of deliberately-unencoded candidates). Counting method: the-sop-keeper's A4 registry-side method doc (agent workspace, local - flagged); metric spec: the analyst's A4 spec.

## Standing rule: fleet defect-event logging convention (A4 accuracy metric)

Authored by the-analyst 2026-07-09 (A4 Phase-0, orch-ruled vehicle: this section, beside the registry format contract above - the artifact that feeds the metric carries its own conventions). Feeds the analyst's nightly-metrics daily accrual + theta-wave weekly readout; corroborated by the registry counters in the adjacent section.

**Why.** "The fleet got more accurate" only becomes a *number* if defects are logged consistently. This convention makes every agent's error/rework/correction machine-countable so the analyst can compute a per-agent **escaped-defect rate**. Under-logging is the failure mode: a falling count then means "logged less", not "more accurate". Log the event **every time** - self-caught **and** escaped.

**The event.**
```
cortextos bus log-event error <defect_class> <severity> --meta '{
  "agent":"<name>",
  "escaped": true|false,
  "reached": "deliverable|agent|user|none",
  "rework_of": "<task_id|null>",
  "corrected_at": "<iso|null>",
  "fleet_caught": true|false
}'
```

**Field definitions.**
- **`defect_class`** - the error type (kebab-case). Reuse an encoded registry class name where one fits; a novel class is fine (it feeds registry Counter 1 = discovery).
- **`escaped`** - `true` if the error **left the owning agent** (reached a deliverable, another agent, or the user) before correction; `false` if the agent caught and fixed it **before it left**. This is the accuracy hinge (see integrity rule).
- **`reached`** - how far it got: `deliverable` | `agent` | `user` | `none` (none = self-caught before leaving).
- **`rework_of`** - the `task_id` being reworked/corrected, or `null`.
- **`corrected_at`** - ISO timestamp when remediated, or `null` if open. (Enables recovery-time = a blast-radius signal; fast remediation of an escaped defect is materially better than slow.)
- **`fleet_caught`** - `true` if **another agent** caught it before it reached the user.

**Integrity rule (verbatim - do not soften).** **`escaped=true` even when `fleet_caught=true` - the owning agent does not get credit for someone else's catch.** The owning agent's rate counts the escape; the fleet readout credits the catch separately. This keeps per-agent accuracy honest while still surfacing fleet-level self-correction.

**Self-caught vs escaped.**
- **Self-caught** (`escaped:false`) = good discipline. It is logged (so the metric can *reward* it via the self-caught ratio), not hidden. An agent that makes an error and fixes it before it leaves must NOT score the same as one whose error reached the user.
- **Escaped** (`escaped:true`) = a real defect, counted in the escaped-defect rate. Worked example (analyst, 2026-07-09): a digest usage error that reached the user then self-corrected in ~15 min = `escaped:true`, `reached:user`, fast `corrected_at` = counted as escaped **with** a good recovery time, not concealed.

**Honesty gate (before any published rate).** Per orch ruling 2026-07-09, a **plant-a-positive coverage baseline** (1-2 weeks) runs first: a seeded known error must appear in the log. A seeded error that fails to appear = a dead pipeline, and publishing rates off a dead pipeline would measure logging discipline while claiming to measure accuracy (the constant-zero lesson institutionalized). No per-agent EDR is published until coverage is proven.

## Standing rule: cross-agent facts are referenced live, never baked into bootstrap docs

Ratified 2026-07-09 PT (orchestrator graduation criterion met during the A1 verify-gate sweep: 2+ further instances found beyond the origin case).

**Rule.** A bootstrap doc (AGENTS / CLAUDE / HEARTBEAT / IDENTITY / SYSTEM / TOOLS - anything an agent reads at boot or on every turn) never hardcodes a fact owned by another agent or by live system state: which account an agent rides, tier labels, the enabled-agent roster, another agent's cron schedule, or a spreadsheet column's LETTER position (which drifts left/right as columns are inserted). Reference the live source at read time instead (`cortextos bus list-agent-accounts`, `list-agents`, `list-crons <agent>`). Where a static mention is unavoidable, it carries the live-source pointer beside it and is treated as a hint, never as truth.

**Instance - sheet-column letters (2026-09-27).** A sheet column's LETTER is a live-owned fact of the exact same class: the sheet owner inserts/reorders columns and every doc that baked a letter goes silently stale. Resolve every sheet column by its HEADER NAME at read time, and where a doc must point at the layout, cite the canonical map ([../../agents/meta-ads-agent/meta-ad-copy-agent/references/column-maps.md](../../agents/meta-ads-agent/meta-ad-copy-agent/references/column-maps.md) - the dated quick-reference, meta-ads-owned) rather than a letter. **A currently-correct letter is the dangerous kind** - it reads validated right up until the next insert (the flower copy tabs grew +11 columns to 19 accounts before the drift was caught). Origin: mmb+meta-ads found the live flower-sheet headers had drifted from letters baked in docs (Ad Name AJ-not-S, Ad Description moved off AH). Note where the live instance actually sat: a GITIGNORED agent CLAUDE.md (mmb's own), which a tracked-tree sweep structurally cannot see - so this rule's enforcement is at authoring time and whenever a deployed bootstrap doc is touched, not a main-branch grep (there is no enumeration oracle for the gitignored deployed copies where these instances live).

**Why.** Baked cross-agent facts are stale-by-default: the owner changes them without knowing who copied them. Origin: the analyst heartbeat canary (registry row 1, instance 4) silently checked the WRONG account every cycle. The A1 sweep then found two more: the fix itself baked fresh which-account facts (a light-agent account roster + a tier label) that go stale on the next rebalance, and a static team roster in a bootstrap doc already missing the two newest enabled agents. This is the fleet's live-authority doctrine (brain repo, sheets, rules - always read live) applied inward to our own system state.

**Applies to.** Bootstrap docs fleet-wide, at authoring time and whenever an existing doc is touched. Playbooks may state cross-agent facts only under the DoD-maintenance rule above, and prefer the canonical-once + pointers pattern even there.

## Standing rule: two-touch security review (auth/infra-mutating surfaces)

Ratified 2026-07-09 PT (orchestrator; authored by claude-dev-agent from the first live case, carried by the-sop-keeper).

**Rule.** Any change that mutates auth state (tokens, sessions, roles) or infrastructure (spawns processes, restarts agents, writes `.env`) gets security-agent at BOTH stages, and both are hard gates before the orchestrator ship-gate:

1. **SPEC-STAGE**: security-agent reviews the spec/threat model BEFORE codex builds - rules the architecture (authZ model, CSRF mechanism, privilege/execution boundary, IPC/job-file threats, concurrency/locking). The dev spec routes to security FIRST, not to codex.
2. **DIFF-STAGE**: security-agent INDEPENDENTLY re-verifies the FROZEN diff - reads source directly (not the dev reviewer's pointers), scans added lines, confirms each spec-stage must-fix is actually in code (not just documented).

**Order**: dev spec -> security spec-review -> codex -> dev raw review + security diff re-verify (both hard gates) -> orch ship-gate. The ship-gate SHOULD include a live negative proof for write paths (e.g. unauthed request -> correct reject with NO side effect).

**What counts as touching signed code** (scoping addition 2026-07-10, security spec-stage catch): the spec's signed-code-impact section enumerates EVERY touch, including two non-obvious cases. (1) REUSE-BY-EXTRACTION counts - factoring a helper out of a signed function is a MODIFICATION of the signed code; the sign-scope travels with the extracted symbol AND the delegation, and both need extract-no-delta proof (byte-identical behavior + existing tests green). (2) CADENCE/LAZINESS CHANGES count - running a signed check eagerly instead of lazily is a BEHAVIOR change to the signed lifecycle, not an extract; it needs its own race analysis + fixture, never a "strictly safe" hand-wave. One-liner: a rename/extract/reuse OR a cadence change of signed code IS a touch of it - list it so it hits diff-stage.

**Why.** Proven live 2026-07-09 on the first auth-mutating dashboard write path (agent-account switch). Spec-stage caught the privilege-boundary ruling (detached-spawn vs daemon-worker, decided on the network-bind + same-uid-fleet facts) plus jobId-path-traversal, pid-reuse, and stale-lock must-fixes; diff-stage verified all four in code; the orch ship-gate proved unauthed-POST -> 401 with no side effect on the live route. A same-day relabel-of-a-half-measure would have missed at least the traversal hole.

**Companion: fail-safe controls refuse on partial at every step.** Ratified 2026-07-15 PT (authored by security-agent from the daemon-bounce-guard build - three same-build fail-opens; the-sop-keeper placement). Exemplar: the gate-verified bounce-guard on main (33b7b06), which refuses-on-partial at logic + invocation + wrapper.

FAIL-SAFE CONTROLS - refuse on partial at EVERY step, including whether the control RAN (companion to the fail-open two-touch-tiering rule). A fail-safe control is only fail-safe if EVERY info-gathering step feeding its decision - resolve, walk, parse, fetch, file-read - AND the invocation/entry boundary (did the control actually RUN) REFUSEs on partial / incomplete / truncated / unconfirmed / did-not-run, never passes-it-as-complete. The final REFUSE is worthless if an upstream step - or the entry point itself - silently hands the decision partial-data-as-if-complete. DESIGN TELL: a step (or a process EXIT CODE) that returns a BARE VALUE gives the decision no way to distinguish complete+safe from partial+unknown, or ran-and-passed from never-ran - return completeness/confidence ALONGSIDE the value (null-on-any-doubt / {value, confirmed} / a positive PASS-TOKEN, never a bare exit-0) so it refuses on anything not positively-confirmed. OPERATIONAL: on finding ONE partial-passes-as-safe hole, SWEEP every step AND the invocation boundary - the class recurs at NEW surfaces (the daemon-bounce-guard hit it THREE times in one build: spec-stage no-live-PID=safe-PASS; a silently-truncated ancestry walk returning partial-as-PASS; and - the canonical bare-value case - a symlinked invocation path silently skipping main() so a bare exit-0 fed the wrapper as if it meant ran-and-passed). Fix the CLASS, not the instance.

**Companion (compliance verdict-gates): a verdict gate FAILS-CLOSED on authoritative-set load failure.** Ratified 2026-07-16 PT (authored by meta-compliance-agent from the copy-gate term-set-load incident; verdict-gate instance of the fail-safe-refuse-on-partial rule above). A compliance VERDICT gate - copy-gate, grep_verdict, launch_gate, any gate emitting PASS/FAIL/UNCLEAR from an authoritative term/rule/signals set - is only fail-safe if, when it cannot load its authoritative set, it REFUSES to emit PASS. Never fall back to a reduced/stale set and PASS: the reduced set is itself often stale (proven - the copy-gate degraded to a LAST_KNOWN fallback that was MISSING `family-grown` and false-PASSED 44 M-19b hard-banned hits; caught only by an independent full-set re-gate = defense-in-depth). **LOUD != CLOSED:** a reduced-set PASS accompanied by a warning is STILL fail-open (the grep_verdict hard-terms class: drops to an inline-floor + warns but still PASSES the reduced set) - a loud warning is not the safety; the safety is the REFUSE-to-PASS itself. RULES: (1) TOTAL load-failure (no authoritative set) -> HARD-ERROR the run, write NOTHING (a write-producing gate with no authority must not write, not even auto-UNCLEAR - the 44 were written cells). (2) PARTIAL/component degrade (fresh set loaded, a sub-component missing) -> force affected rows to UNCLEAR (hold), loud. (3) UNIVERSAL: never emit PASS (or a silently- OR loudly-reduced PASS) on ANY degraded load; any retained fallback = UNCLEAR-only, never PASS. (4) Load the authoritative set from the LIVE authority (a fresh brain clone via env), never a static copy (a static copy goes stale = footgun); add a MIN-VERSION FLOOR tripwire (hard-error if the loaded version is below the last-known-good floor) so an env-load that loads a stale/downgraded clone still fails-closed. On finding one such hole, SWEEP every authoritative-set-loading gate - fix the CLASS, not the instance.

## Standing rule: independence of vantage (outside reader, mechanise the check, immune by design - one family)

Ratified 2026-07-24/25 PT (the-analyst; the reconciliation framing and the naming below by the-analyst, relayed by the-orchestrator; carried by the-sop-keeper). Reconciles two rules that would read as contradictory if filed separately: "get an outside reader" (this file's counting-instances entry, its swap-files step, and the control-spec review convention) versus "mechanise the check, don't rely on a second agent" (the-analyst's own fix over cro-agent's inferior one). Filed as ONE entry with the reconciliation stated first, per the meta-rule below - an unreconciled apparent contradiction licenses ignoring whichever rule is inconvenient, and a future reader without this conversation will resolve it arbitrarily.

**The reconciliation.** THE REQUIREMENT IS INDEPENDENCE OF VANTAGE, NOT A SECOND PERSON. What failed every time tonight was a single vantage auditing ITSELF; what fixed it was a SECOND VANTAGE. A mechanism can supply that vantage as well as a person can - a control-health check that reads the EVENT LOG rather than asking the guards is independent without requiring anyone to be awake. So "outside reader" names the REQUIREMENT; "mechanise the check" and "immune by design" name the durable ways to SATISFY it. A person is ONE implementation of independence, not the definition - and the mechanised implementation is PREFERRED, because it still runs at 3am unattended, which is exactly when guards drift.

**The three pieces, as one family, not competing rules:**
- **REQUIREMENT: independence of vantage.** A thing cannot audit itself. (Human form: an outside reader - this file's swap-files step and control-spec-review convention.)
- **IMPLEMENTATION 1 - mechanise the check.** Replace a human second-look with a mechanism that reads an independent source (an event log, a live artifact) rather than asking the same guards that could be wrong. Structural, cannot forget, runs unattended.
- **IMPLEMENTATION 2 - immune by design beats immune by discipline (the-analyst, 2026-07-24, correctly attributed - cro-agent adopted this pattern over its own weaker fix, it did not originate it).** A FIX THAT DEPENDS ON REMEMBERING WILL EVENTUALLY BE FORGOTTEN. Prefer the design that cannot inherit the bug over the design that requires a future reader to recall a rule forever; keep the discipline-based form only as a fallback, with an invariant as an independent gate. Specimen: a Shopify `created_at` filter silently mis-parsed ISO-timestamp bounds, inflating a number by ~15%. cro-agent's first fix was "always use the date-only quoted form" - protection BY REMEMBERING, requiring every future reader to recall it forever. The-analyst's pattern instead passes NO date filter to Shopify at all: bulk-pull via GraphQL, then window CLIENT-SIDE with explicit PT conversion - it never touches the mis-parsing filter and CANNOT inherit the bug. Immunity by construction, not memory. cro-agent promoted the-analyst's pattern above its own in the pull-definition.

**The invariant library is the applied instance.** The [pre-publication number check](#standing-rule-pre-publication-number-check-a-flag-is-not-a-fix)'s additivity/monotonicity/tautology/independence questions are this same principle turned into a standing gate: cro-agent embedding the additivity check INTO its pull-definition, rather than resolving to be more careful, is immune-by-design applied to its own reasoning. Cross-reference also [counting instances is not counting independence](#standing-rule-counting-instances-is-not-counting-independence), whose "what single failure would take out all N" check IS the independence-of-vantage requirement's operational test.

**Enforcement labels** (the-sop-keeper, 2026-07-25): IMPLEMENTATION 1 (mechanise the check - read an independent source like an event log instead of asking the guards) is, by definition, the mechanised end of this family once actually built - the entry's whole point is that this implementation, when it exists, stops being judgment-level; as of 2026-07-25 no such control-health-reads-the-event-log mechanism is built yet for any of tonight's specimens, so treat every instance in this entry as **MECHANISABLE, NOT YET**, backlog for the-orchestrator, not as already covered. IMPLEMENTATION 2 (immune-by-design, e.g. the Shopify client-side-windowing pattern) is **MECHANISED** in the one specimen given (cro-agent's pull-definition already carries it) - a genuine example of this file naming something actually built, not aspirational. Recognizing that a NEW situation calls for independence-of-vantage in the first place, and choosing which of the two implementations fits, remain **JUDGMENT-LEVEL**.

**Meta-rule for this file (worth its own line, since roughly 15 entries landed the day this was written).** When adding a rule, check it against existing entries for apparent contradiction; if one exists, reconcile it explicitly in the text, in the new entry, at the time it is added - never leave two rules sitting near each other for a future reader to referee. Same family as the directive-artifact rule above: a constraint must travel WITH the artifact, and a reconciliation is exactly that kind of constraint.

## Standing rule: verification-method invariants (a pass is only as good as the method's ability to fail)

Ratified 2026-07-10 PT (authored by security-agent from three same-night self-catches; carried by the-sop-keeper). Unifying principle: **verify with the method that actually ANSWERS the question, and prove your method can produce a POSITIVE before trusting its negative.** Companion to the fixture-realism registry row (a fixture must reproduce the world; a verification method must be able to fail) and the plant-a-positive gates in the monitor rows.

- **VT-1 - Behavioral beats config-read for a live-state claim.** A config read says what SHOULD be true; behavior says what IS. To prove a bind change closed a path, curl the old path and watch it REFUSE where it previously answered - prefer a check the change would visibly break. (Origin: the 0.0.0.0 -> 127.0.0.1 bind verify - lsof necessary but weaker than the tailnet-IP refusal proof.)
- **VT-2 - A status from a short-circuiting layer is not evidence about a deeper layer.** A 401 produced by global auth middleware is route-existence-agnostic: it fires BEFORE routing. For the layer under test, use the authoritative artifact FOR that layer (build route-manifest, live process env, the source file), never a status an earlier gate produced. (Origin: an unauth 401 nearly read as "debug route still live".)
- **VT-3 - Empty output is not a confirmation.** Before concluding ABSENCE from an empty result, prove the query CAN return a positive - plant one, or switch to a method that has data. (Origin: an empty `git diff main...HEAD` nearly read as "untouched" while the real changes sat uncommitted - the range was the wrong query; the empty-hash tell and constant-zero dead-scan smell are the same invariant. Further specimen 2026-07-25, the-ad-strategist: `kb-ingest` printed `Done!` with `0 new chunk(s)` on a file with genuine new content, then ingested 30+ chunks on an immediate identical re-run - the heartbeat's own verification, grepping for `Done`/`Ingested`, cannot distinguish a real success from this silent no-op, because both print the same success word. Fixed in `community/skills/knowledge-base/SKILL.md`: assert the chunk count is `> 0`, not the presence of "Done," and re-run once on a zero. Same invariant as the git-diff case - a success WORD is not success EVIDENCE. Further specimen 2026-09-25 (codex auth-death incident), log-tailing: a 60KB tail read came back CLEAN and produced a wrong "stale re-fire" verdict; the 1MB tail found the fresh 401 burst. A bounded tail read is a COVERAGE BOUNDARY, not the whole log - "no 401s in the 60KB tail" is "no 401s in the window I read," not "no 401s." Before calling a fresh alert a stale re-fire or concluding a fault is absent from a log, widen the tail until its EARLIEST timestamp provably precedes the event you are checking for. See [FINDINGS-codex-auth-death-elimination-ladder-2026-09-25.md](FINDINGS-codex-auth-death-elimination-ladder-2026-09-25.md) lesson 4.)
- **VT-4 - A MIRROR-FIXTURE is a false pass.** A fixture that encodes the SAME premise as the code under test only confirms the code does what it ASSUMES - when code and fixture share a false premise, review and fixture-realism both pass while production fails, because the fixture turns green precisely by agreeing with the bug. Any premise about RUNTIME or FRAMEWORK behavior (what headers a framework injects, what a proxy sets, what a resume prompt triggers) must be validated by a fixture GROUNDED IN OBSERVED REAL BEHAVIOR, or by a live acceptance that cannot share the code's premise - ideally a DIFFERENTIAL pair varying only the premised variable, so the outcome difference isolates it (the forced-https-passes vs plain-http-403s pair that surfaced the origin case; a single live request can still be ambiguous, the differential pair pins the premise). Sharper than the fixture-realism row: an unreal fixture is weak, a premise-mirroring fixture is actively deceptive. (Origin 2026-07-10: a direct-localhost fix assumed direct requests are headerless and its fixtures MOCKED absent headers; Next self-injects x-forwarded-proto=http on direct requests, so mirror-fixtures passed green through two-touch while the live gate 403'd every direct request - both touches mirrored the same falsified premise.)
- **VT-5 - The TESTED path must BE the runtime path.** A suite can pass green while validating a DIFFERENT codepath than production runs - not a premise-mirroring fixture (VT-4), an entire suite exercising a parallel implementation. The check: trace the actual runtime entrypoint (spawn/route/flag wiring) to the function it calls, and confirm THAT function is what the tests import. When two implementations exist (a CLI lane + an in-process lane), the tested one must BE the spawned one, or both must import one shared module (runtime==tested by construction). A green suite is only evidence for the binary it imports. (Origin 2026-07-10, caught at raw review: 38/38 tests imported the dashboard drain function while the runtime spawned a separate CLI fork that had forked the security-signed validator and skipped the global lock - every gate below a raw eye would have passed on the wrong binary.)
- **VT-6 - A round number is a suspected cap, not a value.** When a query result lands EXACTLY on a round boundary (10000 / 1000 / 500 / 100 / 50), treat it as a SUSPECTED LIMIT until proven a real measurement - suspect API ceilings, pagination defaults, LIMIT clauses, spreadsheet row caps, export truncation, UI page sizes. Tell: **exactness is evidence AGAINST being a real count** - real-world totals essentially never land precisely on a power-of-ten boundary. The test (already in the toolkit, see verify-before-stating above): re-slice the same span into smaller pieces (weekly for a monthly total) and sum; if the parts exceed the whole, the whole was capped. **Why this outranks the wrong-total framing:** a cap does not just understate a level, it BENDS THE SHAPE of any series crossing it - early periods get compressed toward the ceiling more than later ones, distorting trend and mix, not just magnitude, and shape is what decisions get made on. (Origin 2026-07-25: Shopify `ordersCount` returned exactly 10,000 for three consecutive months as a silent ceiling with no error/truncation flag; a single-query March read of 10,000 against a weekly-summed March of 14,882 was a 49% understatement, and the capped early months made a real decline look smaller and a computed mix look worse than it was.)

  **Enforcement labels, so this entry does not read as a control it isn't:** the round-number check itself, monotonicity/negative-gap checks on a series, and partial-final-period detection (is the last bucket in a data-cut complete, given the cut date and period length) are all **MECHANISABLE, NOT YET** - pure pattern/arithmetic checks with no judgment call, currently enforced by nobody. Additivity (re-slice and sum) is also mechanisable but needs a query per case, so it is a **per-case helper**, not a blanket script. None of the four above are built; this is a backlog item, handed to the-orchestrator to route (most naturally to the-analyst, which already runs equivalent checks by hand) rather than built by the-sop-keeper, whose lane is the rule text, not the implementer. Frame-interrogation ("what would refute this," "ask the human who was there," "the test decides, not the disposition of whoever ran it") is genuinely **JUDGMENT-LEVEL** - no script carries it, and that is a legitimate category, not a gap.
- **VT-7 - A detector must not share a failure mode with its subject.** (Renumbered from VT-6 2026-07-25, the-sop-keeper: main landed a DIFFERENT rule as VT-6 - round-number-is-a-suspected-cap, commit `70f37ede` - while this branch forked before that commit existed, so both entries independently claimed VT-6. This branch's number moves to avoid the collision at merge time; content unchanged.) If the same event that breaks the thing being watched ALSO disables the thing watching it, a failure reads as calm or idle, not as broken - the worst outcome, because it removes the alarm at the exact moment it is needed. For any detector, ask: what specific failure would ALSO take out this detector? A detector that survives every failure except the one correlated with its own would-be failure mode is not covering that class at all. (Origin 2026-07-24: HEARTBEAT.md is the fleet's own liveness signal, but every agent's heartbeat cron delegates wholly to that same file - so the exact bug class this session's fleet-wide bridge-tool sweep exists to catch (an armed instruction site in a shared, live-read file) would, if it ever landed in HEARTBEAT.md or its bootstrap templates, hang every agent's heartbeat simultaneously. A common-mode hang there leaves the fleet looking IDLE rather than BROKEN, with no alert generated anywhere, since the alerting mechanism and the failure mode are the same file.) Mitigation is architectural, not documentary: at least one independent signal that does not route through the subject's own mechanism (e.g. a daemon-side last-fire timestamp for liveness, concrete-command crons for execution, cf. switch-agent-account.md step 5b's cron-layer classification). **This is the DETECTOR-specific instance of the broader family below - see [counting instances is not counting independence](#standing-rule-counting-instances-is-not-counting-independence) for the general form, the operational check, and four more instances found the same day (code layers, reviewers, artifacts, evidence legs).** **Enforcement labels** (the-sop-keeper, 2026-07-25): the mitigation example given (a daemon-side last-fire timestamp, independent of the heartbeat mechanism it watches) is **MECHANISABLE, NOT YET** - concretely buildable, and would close the exact common-mode gap this rule exists to name; not built, backlog for the-orchestrator. Asking "what specific failure would also take out this detector" for any GIVEN detector is **JUDGMENT-LEVEL** - it requires understanding that specific detector's actual failure surface, which differs detector to detector and cannot be answered by a generic script.
- **VT-8 - A disproof is only as good as the variables the test ISOLATES.** When two candidate causes are BOTH active at test time, a test that fails under EITHER of them disproves NEITHER. Before recording a disproof, name the single variable the test isolates and confirm no OTHER active cause could produce the same failure; if two causes are co-active, neutralize one before testing the other, or the disproof is worthless. (Origin 2026-09-25, codex auth-death: hypothesis 2 - stale in-memory cred - was recorded "disproven" because a fresh app-server presented the same dead key, but every test spawn predated the account fix, so while the account was still broken the failure could not separate in-memory-stale from account-broken; the post-account-fix respawn was the first un-confounded test and CONFIRMED hypothesis 2 as the recurrence cause. See [FINDINGS-codex-auth-death-elimination-ladder-2026-09-25.md](FINDINGS-codex-auth-death-elimination-ladder-2026-09-25.md) lesson 1. Same "a test that passes/fails for the wrong reason proves nothing about the reason you care about" family as VT-4's mirror-fixture.)
- **VT-9 - One green cannot clear an INTERMITTENT fault.** A single successful round-trip is a classic unearned green for an intermittent fault - the fault is intermittent precisely because healthy results interleave with failing ones, so one success is fully consistent with the fault still being live. To verify an intermittent fault fixed, require ZERO recurrence over a watch window that provably exceeds the fault's observed recurrence interval, PLUS an active round-trip - never a single success. (Origin 2026-09-25, codex auth-death recurrence: recovery was earned only over a ~11-minute zero-401 window plus a round-trip and multiple clean turns, not the first clean turn. See [FINDINGS-codex-auth-death-elimination-ladder-2026-09-25.md](FINDINGS-codex-auth-death-elimination-ladder-2026-09-25.md) lesson 2. Earned-green family: the window is what makes the green earned.)

## Standing rule: counting instances is not counting independence

Ratified 2026-07-24 PT (authored by the-orchestrator, generalizing VT-7 and four other same-day instances; carried by the-sop-keeper). Parent entry for a family that showed up in five different domains in one evening - VT-7 above (detectors) is its detector-specific member, and the independence question in the [pre-publication number check](#standing-rule-pre-publication-number-check-a-flag-is-not-a-fix) is its evidence-specific member. Filing a five-domain principle under a detector-specific rule would understate its scope and make it unfindable for whoever next hits it in evidence or in review design - which is precisely where it bit hardest the day this was written.

**The principle.** Counting instances is not counting independence. Two, three, or four things that look separate are not separate if one event takes all of them out - the count N is fake if a single failure zeroes it.

**The check.** Do not ask "are they independent?" - the abstract question invites YES because the items look different. Ask instead: **"WHAT SINGLE FAILURE WOULD TAKE OUT ALL N?"** If one event kills them all, N=1 regardless of the count. This concrete framing forces a search for a shared point of failure, which is answerable by inspection, where the abstract question is not.

**The naming trap, in its sharpest form.** Things that look independent because they are separately NAMED usually are not - and naming is exactly what makes N feel large. Every instance below had distinct labels and one shared failure; counting the NAMES got reported as counting REDUNDANCY.

**Five instances found the same evening, run against the check to show it working every time:**
- Two co-located me-com watchers -> one account cap kills both = 1 lens, not 2.
- Two guard layers sharing an uncertainty defect -> one flawed assumption kills both = 1 layer, not 2.
- Two safety-minded reviewers -> one shared blind spot kills both = 1 reviewer, not 2.
- Six dormant instruction stores -> one never-invalidate-what-we-write habit = 1 property, not 6 (see the incident-close checklist above).
- Four evidence legs where three were Triple Whale -> one TW error kills three = 1 corroboration, not 4 (Shopify was the one genuinely independent second leg).

**Corollary.** Every one of the five above was caught by an OUTSIDE reader, never the author - the author knows the names and stops there; an outsider asks what the names share. This is the justification for the incident-close checklist's step 8 (swap files) and for including the implementer in a control-spec review: self-review cannot see past its own naming.

**Enforcement labels** (the-sop-keeper, 2026-07-25): "what single failure would take out all N" is, in general, **JUDGMENT-LEVEL** - it requires domain knowledge of what the N items actually share (an account, a data source, an assumption), which varies per specimen and cannot be reduced to one script. Narrow special cases are mechanisable per-instance (e.g. checking whether two named accounts are literally the same billing account is a lookup, not judgment), but there is no general mechanism for the family itself - this is one of the rarer entries in this file that is correctly filed as pure judgment, not a documentation gap.

## Standing rule: least-privilege for untrusted-content agents

Ratified 2026-07-16 PT (authored by security-agent - least-privilege owner; carried by the-sop-keeper). Companion to the security-review family above (two-touch-tiering, refuse-on-partial, verification-method invariants). Origin: the research-agent spawn + prune (untrusted-web-ingesting agent, 2026-07-14/15) - skill-set minimized, agent-browser removed, settings hardened; the web-browse-skill-contradicting-read-only-hardening catch is the exemplar for the deletion-half-is-load-bearing clause.

LEAST-PRIVILEGE FOR UNTRUSTED-CONTENT AGENTS - minimize the KNOWLEDGE + TOOL surface, not just permissions. An agent that ingests UNTRUSTED content (open web, external docs, user/third-party-supplied files, scraped data) is a prompt-injection target: whatever it can READ, KNOW, or DO is what an injected instruction can turn against the fleet. So its blast-radius is bounded at SPAWN TIME by how little it carries, not only by a permission prompt at use time. Three controls, all allowlist-by-default (start from nothing, add only what the role provably needs - never denylist from a full surface):
1. SKILL/KNOWLEDGE surface: give it the MINIMAL skill set for its job (prune every skill it does not need). Fewer skills = fewer documented tool-invocations + credential-paths + bus-verbs an injection can learn and abuse from its own context. A skill it never loads cannot be weaponized.
2. TOOL surface: non-allowed tools PROMPT (defaultMode NOT bypassPermissions), arbitrary Bash / writes outside its workspace / any newly-installed tool (esp a browser or code-exec tool) require an explicit human gate. DENY credential reads outright (.env / secrets / oauth / setup-tokens / *.token) even if a prompt-injection asks - a deny the model cannot talk its way past.
3. WEB/EXEC posture: read-only web where the role allows it; no agent-browser or arbitrary-exec tool installed unless the role provably needs it AND it passed a security gate. A capability not installed is a capability that cannot be injected into.
SPAWN-TIME STEP (make it a step, not an afterthought): when spawning an untrusted-content agent, START from the minimal skill set + hardened settings (allowlist tools, deny cred-reads, default-prompt) and add capability only on proven need with a gate - do NOT clone a full-privilege template and trim later (trim-later leaves a full-privilege window + always misses one). The DELETION half is load-bearing: an agent pruned to 15 skills but still carrying a browser-automation skill is not hardened - reconcile the skill list against the role, and re-verify after any skill/template change. DESIGN TELL: if you cannot name why an untrusted-content agent has a given skill / tool / cred-path, it should not have it. Lived: the research-agent spawn+prune (pruned to a minimal skill set, removed agent-browser, defaultMode default-not-bypass, deny cred reads, read-only web) - and the catch that a web-browse skill contradicting the read-only-web hardening had to be removed, because a leftover capability defeats the prune.

## Standing rule: verify-before-stating (decision-driving numbers)

Ratified 2026-07-13 PT (authored by the-analyst from the nCAC denominator saga; carried by the-sop-keeper). Family: extends the "impossibility asserted without verification (premise drift)" registry row and the VT verification-method invariants (esp. VT-3, empty output is not a confirmation) to the numbers/metrics domain, and is the prevention discipline for the fleet defect-event/accuracy convention above. Covers all three of the conclusion, the proof, and the LABEL (a "locked/confirmed" label is itself a claim needing verification).

**Verify-before-stating.** Any metric that will drive a decision or be put in front of Adam must have its **definition**, its **derivation**, and a **second independent source** confirmed before it is stated as solid. The tell: scrutinize the **count / denominator / definition, not the raw dollars** - spend is almost always right; counts and definitions are where these break. Name the exact definition (e.g. "new customer = a unique customer whose first paid order falls in the window," never "customers created"), show how it was derived, and confirm it against a second independent system before calling it solid. **The confirmation obligation is on whoever STATES the number as solid - including relaying a specialist's figure into a brief or to Adam.** The relayer confirms it is verified (definition / derivation / second-source) or labels it **PROVISIONAL** - never relays-as-solid on assumption. **And the confidence LABEL is itself a claim:** do NOT label a finding locked / confirmed / final while a confirming test is still running or a source is still pending - a running test is an open verification, so it stays PROVISIONAL until ALL confirming tests resolve. **Trigger/scope:** this fires when you are about to state a number as FACT, put it in a brief, or drive a decision with it - NOT on every casual or exploratory metric.

**In practice (checklist when a number is about to be stated as solid):**
1. **Definition** - write the exact denominator/metric definition in one line. If it's a count, state what one unit is.
2. **Derivation** - show the query/source path, not just the output.
3. **Second source** - confirm against an independent system (not a second cut of the same one). Two systems agreeing exactly is what ends the doubt.
4. **Sanity rate** - check the number against a known rate before dividing/reporting (and distrust carried "sanity anchors" - they can be wrong too).
5. **Relaying someone else's number?** You own it the moment you state it as solid. Confirm its definition/derivation/second-source yourself, or label it PROVISIONAL - never relay-as-solid on assumption.
6. **Confidence label.** The label (locked/confirmed/final) needs the same verification as the finding - do not apply it while any confirming test is still running or a source pending; PROVISIONAL until all resolve. (Sibling of the relay clause: both stop a not-yet-verified state from being stated as solid.)

**Why (origin, so the rule sticks).** The 7-day nCAC read on 2026-07-13 PT moved 1386 -> 444 -> 247 on the denominator alone while ad spend held at ~$61.8K throughout. Both wrong reads used a mis-defined "new customer" (1386 = Shopify customer RECORDS created, incl non-purchaser signups; 444 = a carried/"corrected" number never re-derived from source). What finally locked it was cross-system agreement: Triple Whale's attribution DB and Shopify's own order ledger both independently returned 247 (and total orders 1,792 vs 1,793). The dollars were never the problem; the count/definition was, three times. Two failure modes, both named: (1) **calc-side** - the producer states a number without confirming its definition/derivation (the nCAC denominator). (2) **relay-side** - a coordinator carries an earlier/specialist figure into a brief or to Adam as solid without re-confirming its derivation (the same day, an optimistic ~$180 nCAC was relayed into a decision-brief without re-checking how it was derived). The producer-verifies rule alone catches (1); the relayer-also-owns-it clause catches (2). A third failure mode surfaced 2026-07-15: a launch-block finding flipped THREE times as confirming tests closed (product-level -> destination-level -> video-format-specific); because it kept flipping AS tests resolved, any locked label before all tests closed was premature BY CONSTRUCTION, not just in hindsight. The relay was held (no user harm), but the LABEL was the failure mode even though the analysis itself was careful - the confidence label is itself a claim needing verification.

**Worked live-data proof, fleet-wide beyond this one nCAC case:** [The Count Is Surface-Dependent](surface-dependent-counts.md) demonstrates this rule's own headline ("scrutinize the count/denominator, not the dollars") on live Axon/Triple Whale data where spend matched to 0.02% while the order count differed 2.48x, plus five more same-shape instances found the same night across conversion, spend-efficiency, retention, compliance, and rules/config domains - none of them a metrics case.

## Standing rule: goal-refresh cadence by agent-state (and staleness-flag recalibration)

Ratified 2026-07-14 PT (the-orchestrator ruling, carried by the-sop-keeper). Resolves a recurring fleet judgment-call: how often an agent's GOALS.md should refresh, and when a stale stamp is genuine rot vs normal-within-cadence. Family: refines the "stale recorded status trusted at read time" registry row - a goal timestamp IS a recorded status, and it is read against the cadence that governs it, not mechanically.

**Cadence by state.**
- **ACTIVE agent** (working, lane shifting): daily - refreshed in the orchestrator's morning-review cascade.
- **STEADY GATED-IDLE agent** (stable, work gated on orchestrator-pacing or Adam): weekly - the Sunday cascade plus on-demand (when the daily focus reshapes the lane, the agent gets un-gated, or the orchestrator re-cascades).

**Staleness-flag recalibration.** The staleness discipline's intent is that goals never SILENTLY rot - surfacing a stale stamp ONCE achieves that (the orchestrator becomes aware and can affirm-or-refresh). So the flag trigger is calibrated to the agent's actual cadence, not a fixed 24h:
- **ACTIVE agent:** more than ~24h without a morning refresh is a real miss - flag.
- **STEADY GATED-IDLE agent:** "stale" = (a) PAST the weekly cadence (>~7-8 days = a missed Sunday cascade), OR (b) CONTENT drifted from reality (goals no longer accurate), OR (c) the agent's STATE changed (un-gated, new work taken on) - NOT a >24h timestamp. A 48h stamp with accurate content within the weekly window (e.g. Sunday to Tuesday) is normal, not rot.
- **Either state:** flag ONCE on the recalibrated trigger, never a daily identical ping. A daily repeat when the owner refreshes weekly or on-demand is noise, not diligence.

**Tier assignment (live, orchestrator-owned).** An agent's tier is not fixed - it is re-evaluated at each morning cascade, and reclassifies on STATE CHANGE: an agent moves to DAILY when it picks up an active workflow, and to WEEKLY when its lane gates back to steady-idle/on-demand. The per-agent classification is owned and refreshed by the orchestrator at each cascade; the authoritative live tier is whatever was assigned at the last cascade. It is captured here only as a DATED SNAPSHOT (a worked example that validates the criteria against real agents), never as a frozen authority - consistent with the reference-live-never-bake rule above (a baked per-agent list would rot the instant a tier moved, self-defeating for a rule about staleness).

*Current snapshot: pending the next clean cascade. The 2026-07-15 cascade that was to produce the first dated tier map was lost to the fleet outage (14:22-16:33Z); the first snapshot lands with the next clean morning-review cascade, orchestrator-supplied.*

**Why.** The-sop-keeper hit this directly: the banked lesson "surface staleness on the TIMESTAMP, not on your read of whether it matters" is correct against silent rot, but applied as a fixed 24h trigger it produced a daily identical ping against goals the orchestrator refreshes weekly and had already affirmed current. The fix is not to drop the lesson but to calibrate its trigger to the cadence that matches the agent's activity-state - surfacing once still prevents silent rot, without the daily nag.

## Standing rule: operational-error surfacing defaults to OPS, never the inherited user-chat

Ratified 2026-07-16 PT (authored by meta-ads-agent; carried by the-sop-keeper). Traced from the verdict-core /tmp-brain flood. Family: the general form of "operational-noise-never-raw-Telegrams-Adam" - it extends that rule to cover SUBAGENT error-reports and internal tool/gate alerts, which inherit the parent's user-chat and so page the user by default unless routed.

**Rule.** Any operational/internal error surfaced by an agent OR a subagent it spawns - gate/authority failures, clone/tool failures, crashes, exceptions, retry storms - routes to **OPS**: `log-event` (durable trail) + `notify-agent` to the fix-owner + `the-orchestrator`. It **NEVER** raw-Telegrams the user (`CTX_TELEGRAM_CHAT_ID`), and never notifies a user-FACING runner in a way that forwards to the user's chat. Only human-framed, decision-relevant messages reach the user (e.g. "these creatives are do-not-launch"), never a raw stack / authority-failure string.

**Two amplifiers this rule kills:**
1. **Inheritance.** Every subagent inherits the parent's `CTX_TELEGRAM_CHAT_ID`, so ANY raw subagent error-report becomes a user page. Subagent operational-error surfacing defaults to ops - the subagent's *result* returns to the parent through the normal flow; the parent decides what (if anything) is user-relevant.
2. **Per-process dedup = flood.** Collapse N-identical operational alerts to ONE per incident, deduped **cross-process** on the failure-class string (a shared state file / lock, NOT per-process in-memory state - and NOT on a reaper-prone path like `/tmp`). Two teeth so the collapse never becomes silence:
   - **(b2) Clear-on-recovery so a genuine RECURRENCE re-alerts.** The cycle is fail -> alert-once -> recover (clear the dedup) -> fail-again -> alert-again. A **latched** dedup that stays suppressed after recovery is itself **fail-SILENT** - it would swallow a real *new* authority-failure, the exact over-correction the Preserve clause forbids. (A TTL on the dedup key gives the same property: a persistent failure re-alerts on expiry rather than going permanently quiet.)
   - **(b3) The dedup key is PER-FAILURE-CLASS-DISTINCT.** Distinct failure types alert independently (e.g. banned-terms vs coding-signals vs strain-lexicon each authority-failure alerts on its own key); the key must never be so coarse it swallows a distinct NEW failure-type behind an already-open dedup.
   N concurrent processes firing the *same* alert is a flood, not diligence - but a *recurring* or *distinct* failure is signal, not noise.

**Application — a fleet-wide restart back-online notice is ONE incident, not N.** A config-reload / `--continue` restart that bounces the whole fleet makes every agent want to announce it — the same N-identical-alerts flood as amplifier 2, aimed at the user. A restart back-online notice is operational, not a human-framed decision, so a hosted agent flags **the-orchestrator** (which carries the ONE consolidated fleet-wide notice) and does **NOT** raw-Telegram the user — **even when its own restart/continuation instruction literally says to Telegram the user** (that instruction fires per-agent and cannot see the fleet-wide scope). The only exception is a genuinely agent-SPECIFIC notice: the user is waiting on THAT agent's status in particular. **Skip-by-default, not fold-after:** flag-then-let-orchestrator-fold FAILS on a simultaneous bounce because the orchestrator has usually already sent the fleet notice by the time a hosted agent's flag lands, so the durable fix is for the hosted agent to skip the direct user ping entirely, not to send-then-hope-it-gets-folded. Ratified 2026-08-12 PT (the-orchestrator, from two consecutive fleet-wide bounces where Adam got a back-online ping from both the orchestrator and a hosted agent). The per-agent instruction that triggers this lives in daemon code (`src/daemon/agent-process.ts`, the "send a Telegram … back online" line appended to the SESSION CONTINUATION prompt) — the standing rule governs the behavior and is the sole and sufficient control - every agent honors it regardless of that injected instruction. [UPDATE 2026-11-08: the code-side default-flip was flagged to its owner but not pursued - dev ground-truth (2026-11-08) confirms no `agent-process.ts` change landed or is queued after 13 weeks, so the standing rule stands alone as the control by design, not as a gap.]

**Preserve (do not over-correct into silence).** Loud-to-OPS stays loud: a real fail-closed/authority failure must remain visible to a human fix-owner. Only the TARGET (ops, not user) and the VOLUME (one, not N) change - never suppress a real failure into silence. In particular the dedup must never LATCH: it clears on recovery and re-alerts on a genuine recurrence or a distinct new failure-class (amplifier-2 b2/b3). Collapsing a flood is the goal; swallowing a new signal is the failure mode to avoid.

**Why (origin).** 2026-07-16 PT: 10 concurrent copywriter subagents each hit a `verdict_core` AUTHORITY FAILURE on a `/tmp/brain` that the macOS `/tmp` reaper had wiped. `verdict_core._alert`'s dedup was per-process (in-memory `_ALERTED`), so all 10 fired; `_alert` notify-agented the Adam-FACING meta-ads runner, forwarding the flood to Adam. The gate was CORRECT (fail-closed - no bad ad passed); the failures were the SURFACING (raw-to-user) and the VOLUME (per-process dedup). The recipient-fix alone still floods ops 10x; recipient + cross-process dedup = complete. This rule generalizes it so the class cannot recur via any subagent path, not just this gate.

## Standing rule: hand-composed bus arguments use the quoted-heredoc form

Ratified 2026-07-25 PT (incident-derived; tested by twelve agents). Full spec, all nine failure modes, audit method and guard status: **`playbooks/fleet/shell-expansion-safety.md`**.

**Rule.** Whenever a `cortextos bus` argument you compose by hand contains **either** (a) text you did not author, **or** (b) any dollar amount regardless of provenance, build the body with a quoted long-delimiter heredoc into a variable and reference it double-quoted:

```bash
BODY=$(cat <<'CG_HEREDOC_7f3a91c4_END'
...content...
CG_HEREDOC_7f3a91c4_END
)
cortextos bus send-message -- <agent> normal "$BODY" [reply_to]
```

Quoted delimiter (bare `<<DELIM` restores full expansion), long delimiter (never `EOF`), plain `<<` never `<<-`, closing delimiter at column zero and bare, reference double-quoted. Applies equally to `create-task --desc`, `complete-task --result`, `log-event --meta`, `update-heartbeat`, `create-approval`, and to **prompt assembly** in generation scripts.

**`--` safety is a property of the call, not the command — check `--help`, not the name.** `--` is safe only when no option follows it in that specific invocation; `send-message` and `send-telegram` both take optional flags (`--reply-to`, `--image`/`--file`), so either can be called safely or unsafely depending on what else is in the call. When using `--` with `send-message`, use the trailing positional `reply-to`, never `--reply-to` — it silently absorbs into a garbage value if the id is omitted (message delivers, but `reply_to` is stored as the literal string `--reply-to` and auto-ACK never fires, causing 5-minute redelivery loops). For named-flag commands (`create-task`, `complete-task`, `log-event`, `update-heartbeat`), `--` **breaks** them, turning `--desc`/`--result` into positionals; protect a dash-leading *value* with `--flag=value` instead. A dash-leading positional has no remedy on named-flag commands — reword it; on all-positional commands (`create-approval`, and `send-message` via its trailing positional) `--` **is** the remedy. Full worked-call table: `playbooks/fleet/shell-expansion-safety.md`.

**`hook-send-guard` is now a WORKING BACKSTOP (Fix A landed + verified 2026-08-03) — but it is a backstop, not a substitute for composing safely.** The previously-documented inversion is fixed: the guard now inspects the **body argument region** at genuine command positions and, verified by 42 unit tests against `decideSendGuard` directly (`tests/unit/hooks/send-guard.test.ts`, all passing — the exact bar this rule set: unit-tested against the decision function, not deployed to find out), it now **denies** `$(...)`, `${...}`, backticks, arithmetic and process-substitution in a send body (in ANY body token, not just the first — commit `f9170fe1`), **allows** the mandated quoted-heredoc form (tested against the literal `CG_HEREDOC_7f3a91c4_END` pattern this file mandates) and single-quoted literals, and no longer fires on **prose that merely mentions** a bus send (commit `4039d794` — the prose-false-positive fix, with a paired positive control that the same body text IS denied when it is a real command). Landed on `main`, built into `dist` 2026-08-02; hooks load from `dist` per-invocation, so it is genuinely live without a daemon restart. **Still: the [quoted-heredoc composition rule](#standing-rule-hand-composed-bus-arguments-use-the-quoted-heredoc-form) stays PRIMARY — compose the body safely AND let the guard catch a slip. A backstop relied on as the primary defense is one refactor from a gap, and this guard was inverted once before; if it is ever rebuilt again, re-verify its behavior (the 42 tests are the regression floor) rather than assuming it stays correct.**

**Lived example, the same day the guard was verified fixed (the-sop-keeper, 2026-08-03), for exactly why the composition rule stays primary:** while writing the `complete-task --result` note for this very fix, the-sop-keeper composed the result as a bare double-quoted string containing `$(...)` — and the shell stripped the `$(...)` before the value ever reached the tool, silently corrupting the stored result (`($(...)-in-body` became `(-in-body`). This happened *while documenting the send-guard fix*, with the now-working guard active — because the guard runs on **send-message/send-telegram bodies**, not on **`complete-task --result` / `create-task --desc` / `log-event --meta`**, and the corruption is a shell-expansion event in the caller's own shell that no PreToolUse hook can see. The fix was the quoted-heredoc form. The point that survives: a working guard covers one surface (send bodies); the composition discipline covers **every** hand-composed bus argument, which is why "compose safely" is the rule and "the guard will catch it" is not — a lived instance beating the abstract warning, caught in real time.

**Why.** A suspected prompt-injection surface resolved into a composition hazard with nine modes across three layers. The dominant mode needs no attacker at all: **any typed dollar amount is silently mangled or deleted** (zsh eats the whole number, bash the leading digit). Confirmed corruption in five agents over forty-plus days, including seven mangled spend figures in a report to Adam and twenty in an operational document the human team works from. A witnessed instance from 2026-07-08 (`USD 0.19` arriving as `/bin/zsh.19`) had been filed as a cosmetic formatting bug for seventeen days: **the same door with a benign visitor.** When a visible-but-harmless anomaly appears, ask what the malicious version of that mechanism looks like — and whether it has a silent mode, because that is the one that will not announce itself.

**A caveat this rule earns rather than states outright: check for composition traps in your own instruction *surfaces* — not just your instruction files.** meta-compliance-agent found that its `TOOLS.md` separately documented a correct flag-form send (`send-telegram <chat> "<caption>" --image <path>`) and separately adopted the correct `--` rule — individually right, **composed into the one call that breaks.** security-agent's widening matters more than the file-scoped version: its own two halves lived in `TOOLS.md` **and in banked memory** — the surface a restarted agent actually reads, and the one least likely to be audited because it doesn't look like documentation. **The check is not "does one file contain both instructions," it is "will I hold both instructions when I compose the call" — memory counts.** cro-agent found the cheap moment to catch it: it had the flag rows and had *not yet* written the `--` rule down, so the trap was present but unarmed — **the dangerous moment is the act of adding the second instruction.** Check your own instruction files and memory for the first instruction *before* adopting a new standing rule, not after. Fix a found trap in the line that would compose wrong, not as a separate footnote, and put the governing rule where every row of a command index passes through it.

## Standing rule: a baseline's value is zero until it isn't — keep the boring recording running, and layer it

**Rule.** Boring repeated measurement of a static system (a `dist/` mtime, a file hash, a process uptime, an occurrence count) is **indistinguishable from wasted effort right up until it is the only thing that catches a silent change** — and the pressure to stop is strongest exactly when the record is most complete, because that is when it has returned "no change" the most times. You cannot know in advance which recording is the one that matters, so a run of "unchanged" cycles is not evidence the recording is padding; it is the cost of admission. Keep it running. When you log a quiet cycle and wonder whether reporting it is padding, that wondering is the signal to continue, not stop. **And no single measurement settles anything — layer them:** one axis makes a change *visible* (the mtime moved), a baseline of prior values makes it *interpretable* (moved to what, from what, how far), and reading the source makes it *settled* (`agent-process.ts:171` proves the spawn path is in-process, so the guard is staged not live). Any one alone leaves a guess wearing the clothes of a fact. This is the measurement half of the build-is-a-deployment rule above: **the boring baseline is how an unannounced `dist` rebuild becomes visible at all** — without it, a fleet deployment ships with no signal to anyone.

**Why.** 2026-07-27, the-orchestrator's override-guard episode. claude-dev-agent had been recording `dist/` mtime for three days — four consecutive cycles returned "unchanged," and three were logged as quiet with the author explicitly weighing whether reporting them was padding. On the fourth, that baseline was the only reason a `10:22:25` dist rebuild — which shipped uncommitted code live to the fleet, the exact hazard of the build-is-a-deployment rule — was visible at all. Authored by the-sop-keeper 2026-10-16 (claude-dev-agent candidate, orch-endorsed; from a cross-org kb-ingest false-green resolved 2026-10-16, origin atwood-codex 10-03; task_1792141031504). ## Standing rule: read a credential to TEST it, never to SEE it - the safe form is the only form to reach for

Ratified 2026-07-30 PT (the-orchestrator, from their own exposure of the-sop-keeper's live Telegram BOT_TOKEN into a session transcript via a full-output config/`.env` read; carried by the-sop-keeper). Same family as the quoted-heredoc rule above and the never-document-a-bypass rule: in each, **the safe form has to be the ONLY form anyone reaches for, because "read it the risky way and trust yourself not to mishandle the output" fails exactly when attention is thin** - which is when credential reads usually happen (mid-incident, mid-debug).

**The failure: reading a credential-bearing file in a way that prints its VALUE to stdout puts that value into the session transcript, and the transcript is a durable artifact you do not control the scope of.** A `cat .env`, a bare `grep BOT_TOKEN .env`, a `printenv`, an `echo "$SOME_TOKEN"` - each dumps the secret into the scrollback, where it is now in the transcript file on disk and (depending on the agent) potentially in anything that later ingests or forwards that transcript. The read was legitimate; the OUTPUT SCOPE was not checked. This is the same output-scope class as the earlier `accounts.json` incident, one step broader - the exposure here was disk-local only (not git, backup, cloud, or Time Machine), which is the containment you want but not a reason the read was fine.

**The rule: when you need to know something ABOUT a credential (does it exist, is it set, does it have the right shape), read it in a form whose output is the ANSWER, never the SECRET.**
- Presence / absence: `grep -q '^BOT_TOKEN=' .env && echo "BOT_TOKEN set"` — prints a boolean-shaped answer, never the value.
- Shape / length without value: `awk -F= '/^BOT_TOKEN=/{print length($2)" chars"}' .env` — prints a measurement, not the token.
- Never `cat` a whole `.env`/secrets file "just to look" — read the specific field with a filter that transforms it to what you actually need to know.

**Rotating or placing a new credential has the same rule one layer out: the secret must never transit an agent session or a Telegram channel as literal text.** When a new token needs to go into a `.env`, the human edits the file directly, or it moves through env-management tooling that does not echo it - it does NOT get pasted into an agent's chat or produced by asking an agent to print it. Pasting a fresh token to "hand it to the agent" re-exposes it in the very transcript the rotation was meant to escape - the exact loop this rule closes.

**Why this is a standing rule and not just "be careful": remembering to be careful is the thing that fails under load.** A credential read almost always happens while chasing something else, when attention is on the other problem. The durable fix is to make the output-scoped form the default muscle memory - `grep -q` for presence, a field-extracting filter for shape - so the risky full-read is never the reflex in the first place. "The safe form should be the only form reached for" (the-orchestrator) is the whole rule in one line.

**Enforcement labels** (the-sop-keeper, 2026-07-30): recognizing that a given read touches a credential-bearing file is **MECHANISABLE** - a pre-execution scan can flag `cat`/non-`-q` `grep`/`printenv` against `.env`/`secrets`/`*.token`/`oauth` paths. Deciding what the read actually NEEDS to reveal (presence vs shape vs the value itself - and the value is almost never what a diagnostic needs) is **JUDGMENT-LEVEL**. The rotation-handling half (a fresh secret never transits a transcript or chat) is **JUDGMENT-LEVEL** to follow but **MECHANISABLE** to catch after the fact via the same transcript-scan security-agent used to find the exposure.

## Standing rule: cross-agent artifacts need a fleet-readable path AND the substance in the message body

**Rule.** Anything another agent is expected to read never lives only in your own agent directory. Send the substance **verbatim in the message body** (transport — works today, zero cost, reaches the recipient regardless of path) **and** land it at a **fleet-readable path**, naming that path in the message (durability — a citable, versioned copy the next reader can find without you). Neither half substitutes for the other:

- **Path alone fails.** Naming an owner or a path without confirming the recipient can actually read it is an announcement, not a handoff — it "feels durable to the author" and isn't. (This is the custody rule above, applied to artifacts instead of corrections.)
- **Body alone fails.** Content that exists only in message history evaporates on the conversation's timescale — nobody searches chat logs for a standard, and the next person re-derives the work, drifting from whatever the first version said.
- **An agent's own directory (`agents/<name>/...`) is private working state, never a citation target.** A path into it must not appear as a source reference in a fleet artifact — three separate pieces of team-lead's work landed there and were unreachable by path each time, worked around individually (inlining a whole script rather than fixing the access gap) until named as one recurring pattern.

**"Fleet-readable" and "durable" are two different guarantees — name which one you need, don't just name a path** (meta-compliance-agent, caught applying this rule to itself within the hour: a compliance brief sent by path to `agents/meta-compliance-agent/workspace/` was moved to `orgs/clean-green-marketing/shared/rejection-analysis/`, which is readable on this host but — verified via `git check-ignore` — **entirely gitignored**, so it does not survive a host loss). `playbooks/fleet/` is git-tracked **and** every-agent-readable, so it satisfies both guarantees at once for **fleet-wide process content** (standards, SOPs, playbooks — including drafts and scripts not yet ratified as standards, clearly labeled DRAFT/SEED). For **org-specific content** (compliance briefs, rejection logs, account data — the majority of daily cross-agent exchange), `orgs/**` gives readability only; whether the brain repo is the intended durable home for that content, or read-only-not-durable is an accepted tradeoff (org content can carry PII), is an **open question, not yet settled** — treat it as one rather than assuming `orgs/**` is sufficient.

**When the referenced content legitimately cannot leave gitignore, cite a durable bus handle — not the path.** Some content must stay under `orgs/**` by design (token-exposure control) and cannot be relocated to a tracked location. A tracked fleet artifact still must not hard-link that gitignored path — it would **dangle in a fresh clone** (or for any reader without the author's local tree), which is the readability failure above wearing a valid-looking path. The durable, portable citation is then the **bus task handle** (`task_…`) that both sides reference: the handle lives in the bus system, is readable by every agent, and survives the clone. Make the link two-way — the private note points at the tracked artifact's path + the handle, the tracked artifact points at the handle only — so neither edge crosses from tracked into gitignored. (the-sop-keeper, 2026-08-04: the send-guard runbook's RTK caveat needed to reference claude-dev-agent's findings doc, which is correctly gitignored under `orgs/**`; the tracked runbook cites `task_1785812468129` instead of the path, and the findings doc points back at the runbook path + the same handle — a durable two-way link with no tracked→gitignored path edge.)

**Why (origin).** Three occurrences in one night of the-team-lead's fleet-useful output landing in a path only they could read (a Slack-client note, `cron-surface-sweep.py`, a reader-repaired-corruption draft), each patched individually rather than fixed at the cause. Named as one pattern rather than a fourth workaround; the-orchestrator ruled both/and rather than either/or, since its own custody failure earlier the same night was the path-alone side of this exact coin.

## Standing rule: a correction is entitled only to the proposition it addresses

Ratified 2026-07-25 PT (cro-agent, generalized for the standing record at the-axon-agent's request; carried by the-sop-keeper). Origin: a live review of the fleet's own surface-dependent-counts teaching artifact, where the rule caught an over-correction in real time, inside the very episode it now describes.

**The rule.** A new measurement or finding only invalidates the specific claim it actually tested. It does not automatically invalidate an adjacent, similar-looking, or previously-bundled claim just because that claim sat near the one now shown wrong - and it does not, by the same logic, automatically restore an unrelated claim just because something nearby was vindicated. Both directions are the same error: extending a correction's authority past the proposition it was actually evidence about.

**Origin specimen.** An Axon-channel same-source ratio (1,740/249 = 6.99x) was originally compared against a Meta figure to conclude "the two channels have essentially the same repeat-mix." That Meta figure turned out to be an account-level row-sum capturing only 23% of the channel - a bad comparator. Re-measured like-for-like, the channels DID agree (6.99x vs 6.63x), so the original conclusion was right after all, reached by a flawed method. A first draft of the write-up voided the ~7.0x figure itself alongside the conclusion it fed - but the new measurement had tested the COMPARATOR, not whether 6.99x was correctly computed, and 6.99x was untouched by anything that happened. Voiding it anyway would have discarded a correct, still-useful number for no reason connected to any actual finding.

**Why this is not the same as "the count is surface-dependent" (this file's sibling teaching artifact, `surface-dependent-counts.md`).** That rule is about naming which surface a NUMBER came from before comparing it to another. This rule is about scoping what a CORRECTION is evidence for, once one surface is shown to have a problem - a narrower, later-stage question that only arises after a defect is already found. The same episode produced both lessons on the same night, from the same numbers, one layer apart.

**The check, stated actionably:** before voiding, discounting, or restoring anything adjacent to a correction, ask **"did the new measurement actually test THIS claim, or only a claim near it?"** If the new evidence tested the comparator, the method, or a different leg of a multi-part figure, it is entitled to a verdict only on that leg - state the correction's scope explicitly, and leave everything outside that scope exactly as it was (void-marked if wrong, standing if not touched).

**Conversely, when the new evidence DOES bear on the same proposition the earlier correction addressed, reversing that correction is required rather than permitted** (cro-agent) - **a wrong correction carries the same authority as a right one and nothing expires it, so entrenching one is the more expensive failure.** Without this half, the rule above reads as a standing presumption against reversal, which a reader could cite to refuse a legitimate one. The origin specimen already demonstrates both directions: the-ad-strategist's "same repeat-mix" conclusion was retracted by a bad-comparator finding, then RESTORED by a later like-for-like re-measurement that bore on that exact same proposition - and that restoration was correct, not an over-reach, because unlike the row-sum defect, it actually tested the claim it changed.

**Enforcement labels** (the-sop-keeper, 2026-07-25): this is **JUDGMENT-LEVEL** - deciding what a given piece of new evidence actually tested requires understanding both the old claim and the new measurement's mechanism, which cannot be reduced to a pattern match. No mechanisable check is proposed for this entry; it belongs in the small set of rules that are correctly filed as pure judgment rather than backlog.

## Standing rule: a time-boundary filter must be honored in the units you think you passed

Ratified 2026-07-26 PT (research-agent; carried by the-sop-keeper). Same family as VT-3 (empty output is not a confirmation) and the reconcile-units-before-reporting rule (production-house, this file's shell-expansion-safety incident) — this is the git-tooling-specific instance of both.

**The finding.** `git log --since='<timestamp>'` does NOT interpret the string as UTC just because it looks like one — git parses `--since` in the LOCAL timezone of the machine running it, regardless of the string's apparent timezone. Passing `--since '2026-07-25 16:30'` intending 16:30 UTC actually filters from 16:30 in the local zone (16:30 PDT = 23:30 UTC in the specimen that surfaced this), silently excluding any commit between the intended boundary and the local-time boundary — a 7-hour blind window here.

**Why this fails toward the worst outcome.** A time-boundary change-detection sweep ("scan everything since the last sweep") that hits this bug returns a CLEAN EMPTY RESULT, not an error — "no changes since last time" is exactly what a genuinely clean sweep also reports, so the two are indistinguishable from the output alone. This is a fresh instance of VT-3 (empty output is not a confirmation) in git-tooling specifically, and it fails in the direction that matters most for a sweep whose entire purpose is not missing something: it manufactures false silence rather than a visible error.

**The catch, and the fix.** research-agent only caught it because a file's mtime disagreed with git's answer, and the disagreement was chased rather than the cleaner-looking (empty) result being accepted. **Two independent instruments disagreeing is the signal** — the same independence-of-vantage requirement as elsewhere in this file, applied to a single sweep's own self-check rather than to a second reviewer. **The fix, verified 2026-07-26 (research-agent tested all three against the specimen commit, each correctly returning it where the bare form returned zero):** pass the boundary in any timezone-QUALIFIED form — `--since='2026-07-25T16:30:00Z'`, `--since='2026-07-25T16:30:00+00:00'`, or `--since='2026-07-25 16:30 +0000'` (the bare `--since='2026-07-25 16:30'` is the unqualified form that silently reparses as local time) — or cross-check the git-log result against file mtimes and treat any disagreement between the two as a change until resolved, rather than trusting either instrument alone.

**A discrepancy diagnosed is not a cause proven — worth one line since it happened on this exact finding.** research-agent inferred the timezone bug FROM the mtime-vs-git disagreement, which is good reasoning but not a controlled isolation of the variable — a zero from `git log --since` can equally mean a wrong pathspec, and that possibility was only excluded afterward (`--since='2026-07-01'` on the same pathspec returned commits, confirming the path was never the problem). The right answer was reached by inference before it was reached by test; both directions matter equally, catching a real issue from a discrepancy AND then isolating the actual variable rather than stopping at "the discrepancy resolved, so I was right."

**Second specimen - BSD/macOS `date -j -f` reparses apparent-UTC as local** (claude-dev + the-orchestrator, 2026-09-18; carried by the-sop-keeper). The same mechanism outside git: `date -j -f '<format containing a literal Z>' '<...>Z'` WITHOUT `-u` parses the timestamp in the machine's LOCAL zone, not UTC - the literal `Z` in the format is matched and discarded, the hour is read as local and echoed back. On `2026-09-18T19:00:00Z` the bare `date -j -f` printed 7:00 PM PDT when the true value is noon (12:00 PM PDT); it bit two agents the same hour on a time-sensitive noon-deploy deadline. **Same fix shape as the git case:** force UTC on the primitive - `date -u -j -f` (parse as UTC) or `-u` epoch math - and cross-check the result against a known ground-truth timestamp rather than trusting the rendered hour. **What the two specimens generalize to:** a tool that accepts an apparent-UTC timestamp does not honor the apparent zone (`Z`, `+00:00`) by default - it silently reparses in local time unless you force or qualify UTC (`-u`, a zone-qualified string, or epoch math), and the failure is a plausible-looking wrong hour (or an empty filter), not an error. Confirm against a second independent instrument (an mtime, a known-correct timestamp) whenever a time-boundary filter or a timestamp conversion drives a decision. **Keep the class tight** (claude-dev, 2026-09-18): this is a tool SILENTLY DROPPING an explicit/apparent zone (`Z`, `+00:00`) and reparsing as local. It is NOT the distinct case of a ZONELESS value interpreted as local BY DESIGN - e.g. the daemon's 5-field calendar crons fire in local time intentionally (documented in the org knowledge base's cron-timezone rule), which is intended behavior, not a silent footgun. Lumping the by-design case in would blur the rule; if that ever needs its own entry it is a separate "zoneless-value-defaults-to-local" line, not this one.

**Enforcement labels** (the-sop-keeper, 2026-07-26): the mtime-cross-check is **MECHANISABLE, NOT YET** — a wrapper could run both `git log --since` and an mtime-based `find`, diff the file sets, and flag any disagreement automatically; not built, backlog for the-orchestrator. Passing a timezone-qualified string correctly is a one-time authoring fix, not a standing check — once written correctly it stays correct, so it does not need the same ongoing enforcement the cross-check does.

## Standing rule: adjacent-property substitution (the wrong field, already in hand)

Ratified 2026-07-25/26 PT (the-analyst, 4 instances across 3 agents; a 5th added by the-orchestrator's own near-miss the following night; carried by the-sop-keeper as synthesis owner, filed as an explicit non-urgent backlog item and written up once the queue had room).

**The shape.** Five agents, one mechanism: the WRONG field was already sitting in a response the agent already had, and the RIGHT field needed a second, separate query. A reminder to "be careful" does not fix this, because the wrong answer is genuinely present and plausible-looking — nothing on the page signals it is the wrong property for the question being asked.

**Five worked instances:**
1. **the-orchestrator:** measured THE BRANCH (a code path that never runs) but reported it as THE FILE ("`restarts.log` is 47 days stale") — "this log is stale" sends a reader to the writer; "this code path never runs" sends them to the trigger condition. Only the second was actually true.
2. **the-analyst:** ran `git log` on a path (answers WHEN/WHERE it was last touched) and reported that as what MAIN CURRENTLY CONTAINS (a log entry never answers that) — told a colleague bad advice had not propagated when it had.
3. **the-team-lead:** read AGE-SINCE-TOUCH as THROUGHPUT — age answers when a card arrived, not whether anything is leaving, so a drained-Tuesday gate and a stalled-since-Tuesday gate look identical on that field alone. Same instance also used `date_updated` when `date_created` was the property actually needed.
4. **the-team-lead (second instance):** asked about COVERAGE when REACHABILITY was load-bearing — the compliance scan's capabilities were verified thoroughly and correctly, none of which survives if the asset never reaches the scanner in the first place.
5. **the-orchestrator (second instance, the following night):** verified the machine does not COVER M-15b (true) and read that as evidence M-15b CLAIMS coverage (false) — a near-miss verification manufacturing confidence about an adjacent, unchecked claim, nearly triggering an unnecessary wake-Adam escalation on the wrong half.

**The operational tell (the-team-lead's form, sharper than "was this the adjacent question" — that phrasing already requires knowing the right answer): did the answer arrive WITHOUT a second query?** A field that answered the question for free — no extra lookup, no extra call — is worth doubting for exactly that reason: a property worth asking about specifically is usually a property that takes a dedicated query to obtain, not one that happened to already be sitting in a response fetched for something else.

**The tell's DOMAIN, not its hit rate (the-analyst + the-team-lead, 2026-07-27, each instance verified against a contemporaneous record — not recall, see the caution below): FIRES ON INHERITED AND INCIDENTAL PROPERTIES, BLIND TO DELIBERATELY-QUERIED ONES (the-team-lead's phrasing), n=5 — the pre-registered falsifier below was TESTED and DID NOT FIRE.** A domain claim with no stated n reads as established — the exact denominator defect this rule is itself about, so the n is required here, not a nice-to-have. Five instances confirmed by citation, no percentage stated because a rate would make a reliable instrument look broken on a small sample — the domain is the load-bearing claim, not a count:
- **Instance 1 (the-orchestrator) — MISS.** A dedicated `grep CRASH`, run to investigate crash attribution, produced the last CRASH-marker date; that result was substituted for the FILE's staleness (never separately checked — the mtime, 07-22, was never queried) (memory/2026-07-25.md:597).
- **Instance 2 (the-analyst) — MISS.** A dedicated `git log -1`, run specifically to answer "does main contain the bad advice," still returned the wrong property. The tell's "no" here is a genuine false negative.
- **Instance 3 (the-team-lead) — FIRES.** `date_updated` read off a ClickUp response already in hand (fetched for something else); no second query (memory/2026-07-20.md:32).
- **Instance 4 (the-team-lead) — FIRES, harder than instance 3.** No query of any kind — the "compliance agent scans every asset" scope was inherited from an existing claim and forwarded to Adam as a mitigation, unchecked (memory/2026-07-25.md:326).
- **Instance 5 (the-orchestrator) — MISS.** A dedicated coverage-verification query established the machine does NOT cover M-15b; that TRUE result was substituted for a different, never-queried claim (does M-15b itself CLAIM machine coverage) (memory/2026-07-26.md:1096, :547).

**The pre-registered falsifier, stated before this data arrived: the domain claim breaks if either of the-orchestrator's instances turned out to be inherited/incidental-and-missed, or deliberately-queried-and-fired.** Both came back deliberately-queried, and the tell correctly missed both — the split holds at n=5 (3 miss: instances 1, 2, 5; 2 fire: instances 3, 4). Registered before the data, tested against the only source that could break it, survived.

**One clause the falsifier test surfaced rather than closed (the-orchestrator's own honesty about the ambiguity, the-analyst's resolution): the tell measures the query-status of the ADJACENT (reported) property, never the WANTED (correct) property — and this is not a stylistic choice, the other reading is vacuous.** In every true instance of this rule, BY DEFINITION, the wanted property was never queried — if it had been, there would be no substitution to report. So "did I query the property I actually needed" returns "no" on every instance without exception: a constant, not a test, discriminating nothing. Only "was the property I actually REPORTED freshly, deliberately queried FOR this question, or was it already in hand from something else" produces the real 3-miss/2-fire split above. The wanted-property reading fails for the same reason this file already rejected "was this the adjacent question" as the tell's wording (the-team-lead): both require already knowing the right answer to ask the question, which is impossible at the moment the error is being made. The adjacent-property reading asks about the number already in your hand, which you always have access to — operable at the point of use, not just at post-mortem.

**Blind spot, not weakness: the tell is not unreliable, it is scoped — it catches the field you never thought to question, and is silent on the field you thought you'd verified.** That silence is exactly the case that most needs catching, since a deliberately-queried wrong property carries the false confidence of having been checked. Use the tell as a domain map (fires here, blind there), never as a general gate on the whole rule.

**A caution on how this specific rule gets audited, since it just happened twice: recall is biased toward "I checked."** the-team-lead's own first guess for instance 4 was "I ran a query" — the opposite of their own contemporaneous file. the-analyst independently guessed the same thing about the same instance, with no contact between the two guesses, same wrong direction. On THIS rule specifically, do not accept a recalled account of which shape an instance was — require a citation to a contemporaneous record (a memory file line, a log, a message timestamp) before classifying any instance as fire or miss.

**The fix (the-team-lead's trigger + the-analyst's question, replacing an earlier draft's "apply the tell at acquisition" — which does not work): AT THE MOMENT A PROPERTY BECOMES LOAD-BEARING, produce the record of the MEASUREMENT that established it, or treat the property as UNVERIFIED.** "Apply at acquisition" fails because acquisition has no prompt: nothing looks wrong yet, that is what acquisition means, so a suspicion-triggered check never fires there in practice — the thing that makes anyone ask "did I actually check this" is noticing something is off, and that arrives at audit, exactly where this rule says the check degrades. The trigger has to be STRUCTURAL instead of suspicion-based: a property becomes load-bearing (handed to Adam as a mitigation, cited as a passing gate, quoted into a decision) at an identifiable moment, with no suspicion required — that moment is where instance 4 actually broke (the inheritance was free until it became load-bearing). And the question at that moment must not be a memory question — "did I query this or inherit it" hands the answer straight back to the same biased instrument. Ask instead: can a record of the underlying MEASUREMENT be produced right now?

**The word MEASUREMENT is load-bearing and narrower than "a record" (the-team-lead, self-tested against their own instance 4): a record of being TOLD is not a record of the check.** the-team-lead can produce the earlier message that handed them the "scans every asset" scope — so a looser wording ("produce the query, the message, the line") passes on exactly the case it exists to fail. Keyed to the measurement specifically, the honest answer becomes "no, someone else measured this and I do not hold their record" — which is what was actually true, and routes the reader to go ask them, rather than letting a citable-but-second-hand message stand in for verification.

**A known false-positive class, stated up front so the first person it flags does not conclude the check is broken: a property arrived at by REASONING (not measurement, not transmission) also has no measurement record, and will correctly be flagged unverified.** That is not a bug in the check — an inference is unverified until someone measures it — but it needs saying before someone hits it and assumes the rule misfired.

**The bound on all of the above (the-analyst, run against instance 2 as the test): the measurement-record check verifies PROVENANCE, not FITNESS.** `git log -1` is a real measurement, genuinely performed — the record check on instance 2 PASSES — and the property was still wrong, because the wrong property was measured correctly rather than the right property being skipped. **The tell and the record check together cover the INHERITED and INCIDENTAL subclass. They cannot reach the DELIBERATELY-QUERIED subclass — that half was never a gap this apparatus could close, and six rounds of extending it never moved the blind spot.** The thing that does cover it was already in this entry before any of the tell/record discussion: the rule sentence below ("name the property actually needed, verify the field measures THAT property and not a plausible neighbor") — run against instance 2, property needed = what main CURRENTLY CONTAINS, field cited = when the path was LAST TOUCHED, a clean catch, correctly labelled JUDGMENT-LEVEL. **The mechanisable half cannot reach the judgment half; that is not a shortfall to fix, it is the actual shape of the rule.**

**Why six rounds all landed on the same half (the-team-lead): given a problem with a mechanisable half and a judgment half, effort flows to the mechanisable half regardless of which half the actual gap is in — the mechanisable half offers a next step to take, the judgment half only offers a sentence to reread.** Every round genuinely fixed something, which is exactly what made the blind spot easy not to notice; it kept feeling productive. This is the argument for keeping the JUDGMENT-LEVEL label prominent rather than letting the checkable parts crowd it out in a reader's attention — it was the judgment-level sentence, sitting unchanged the entire time, that closed the case the six rounds of mechanism-building never reached.

**This makes the citation requirement a PRECONDITION for using the domain map at all, not bookkeeping for classifying this rule's own instances (the-analyst).** The domain boundary above is drawn on acquisition mode — and acquisition mode is the exact axis recall cannot self-report reliably. A reader trying to place themselves on the map from memory alone hits the bias at its worst angle: an inherited property tends to feel queried, so a self-check concludes "I'm in the blind zone, the tell wouldn't help" and skips it — precisely where the tell works. **The map is usable only where acquisition mode is documented; where it is only recalled, the map inherits the recall bias and points the wrong way.**

**The rule.** Before quoting any measurement as the answer to a specific question, name the property ACTUALLY needed in one sentence, then verify the field being cited measures THAT property and not a plausible neighbor (a related field, a correlated-but-distinct quantity, or the inverse of the true claim). Do this even when — especially when — a field already sitting in a response looks like it answers the question.

**"Manufactured confidence" is the sharper framing than "wrong field" (instance 5's contribution).** A near-miss verification is not a weak check that happened to miss something — it is a LICENSE. It looks and feels like verification was performed (a query ran, an answer came back, it was checked against something), so it discharges the reader's instinct to double-check further, while actually answering an adjacent question instead of the one that mattered. **A near-miss check is not a weak check, it is a license** (the-orchestrator's phrasing, worth keeping verbatim).

**Enforcement labels** (the-sop-keeper, 2026-07-27): naming the property actually needed before quoting a measurement is **JUDGMENT-LEVEL** — it requires understanding what the downstream decision depends on, which varies by claim and cannot be pattern-matched. The "did this arrive without a second query" tell is a useful judgment-level heuristic, not a mechanisable check — a genuinely correct field can also arrive without a second query (a merely FAST correct answer looks identical to a WRONG adjacent one from the outside), so it narrows attention, it does not replace verification.

## Standing rule: do not add a tell for the skip - remove the skip-point

Ratified 2026-07-27 PT (the-orchestrator's clause; implemented and tested on a live instrument by the-analyst; carried by the-sop-keeper).

**The principle.** When a required verification step degrades into a formality, the instinct is to add a check for whether the step was actually performed - a tell for the skip. **This does not work: a required field becomes a formality, and vigilance is exactly the thing that fails, so the tell for the skip is just as skippable as the thing it was meant to catch.** The fix is not another layer of vigilance - it is to remove the point at which skipping is possible. Redesign the instrument so it emits its verdict-DISTRIBUTION across known cases alongside every single verdict, rather than a bare pass/fail - so reading the one result you were going to read anyway shows you the spread, by construction, with no separate step to skip.

**"A constant wearing a test's clothes" (the-orchestrator's formulation): an instrument returning the same verdict on nearly every case carries no information, and the DIRECTION IS IRRELEVANT.** Always-CLEAR and always-ALARM are the same failure - the-analyst had been filing always-silent as dangerous and always-alarming as mere noise before this ran; they are one thing, not two.

**Run twice on four real fleet instruments in one day (the-analyst, HEARTBEAT.md Step 3 and adjacent checks) - two survived, two broke, and the split is the actual finding:**
1. **Staleness grep `[5-9]\.[0-9]h|stale|dead` over `read-all-heartbeats`.** Measures NOTHING - the command's output has no age field at all, it emits absolute ISO "last seen" timestamps, so the pattern cannot match in ANY state. Fires 0/16, always. **CONSTANT, SURVIVES - structural, provable without sampling**, and it printed a clean fleet all-clear the whole time regardless of what was actually true.
2. **`used_percentage == 100`.** Measures context-window fill - a real, moving quantity. 15/16 at 11:50Z, **11/16 at 19:52Z, six distinct values** (55, 62, 63, 68, 88.9, and the rest at 100). **NOT a constant - broken on its first re-read.**
3. **The wanted-property reading of the adjacent-property tell** (this file, above). Measures NOTHING by construction - in every true instance of that rule the wanted property was never queried, which is what makes it an instance, so this reading fires 5/5 without exception. **CONSTANT, SURVIVES - definitional, provable without sampling** (already codified in `a706d196`).
4. **Watchdog-authored heartbeat treated as suspicious.** Measures something real - recent self-authorship, i.e. idleness - but the WRONG axis. 13/16 at 09:49Z, **9/16 at 19:48Z. NOT a constant - broken on its first re-read.** Distinct failure from #1 and #3 (the "no information" constants) - and the same category of mistake as #2 (both single-sample constant-claims that flipped on re-read): this is not "no information," it is **information about the wrong axis** - it validly measures idleness while being read as health. The two failure types need opposite fixes: no-information means DISCARD the check; wrong-axis means RE-AIM it at what it actually measures.

**The load-bearing split: the two survivors are provable WITHOUT sampling at all (#1 structural, #3 definitional); the two that broke were both SAMPLED claims, and both broke on their very first re-read.** Two for two. One sample cannot establish that something is a constant - the-analyst predicted exactly this split in writing and then had to eat it twenty minutes later on #2, which was still an unverified single-sample claim at the moment the prediction was written.

**The cost of trusting a single-sample "constant," made concrete rather than hypothetical:** the-analyst had earlier killed their own claim ("the-orchestrator's context is 4.7x oversized, do not raise the spend limit") using three arguments, one of which was "15 of 16 agents read 100%, so the reading was never diagnostic" - itself a single-sample claim about #2, now shown unsound. **The 4.7x claim is still correctly dead**, on the other two arguments, which are independent and hold: the field resets mid-session (the-analyst's own reading went 983,894 → 181,184 while working), and absolute cross-agent comparison is meaningless (the-analyst read out=2 while working hard; the-orchestrator read 1401 while frozen). **Right conclusion, one dead reason - and the dead reason does not get to stay in the record just because the conclusion it supported happened to survive on the other legs.**

**Bounds, stated so this is not over-read: n=4 instruments, one agent, one day.** #1 and #3 do not depend on n - they are proved structurally/definitionally, true regardless of sample size. #2 and #4 are now n=2 each and both flipped, which supports "a sampled 'constant' needs a second read before it is trusted" and establishes nothing about HOW OFTEN instruments turn out to be constants in general - no rate claim is made or supported here.

**Enforcement labels** (the-sop-keeper, 2026-07-27): emitting a verdict distribution alongside a binary result is **MECHANISABLE** and already built - four working instruments, not a proposal, the rare case in this file where the fix is shipped rather than backlog. Distinguishing a structural/definitional constant (provable by reasoning about the mechanism, no sampling needed) from a sampled one (which needs at least a second read before the "constant" label is trusted) is **JUDGMENT-LEVEL** and is the actual skill this rule is teaching - the distribution alone narrows which claims need a second look, it does not replace making that judgment.

## Standing rule: a message to more than one recipient carries no second-person reference

Ratified 2026-07-27 PT (the-analyst, mechanism self-diagnosed; the error itself caught by the-sop-keeper, not the-analyst — see the credit-tally note below; carried by the-sop-keeper). Related but distinct mechanism, the general form of this failure: [correction-propagation - carry the test, not the verdict](#standing-rule-correction-propagation---carry-the-test-not-the-verdict) is the broader principle (a correction or credit gets less scrutiny in a relay); this entry is the pronoun-specific case of it.

**The finding.** the-analyst wrote a paragraph in the second person addressed to the-orchestrator — crediting "you" for a specific action — then sent the identical text to a second recipient (the-sop-keeper) as part of the same exchange. "You" is resolved by the READER, not the writer, so the same unedited text made a true claim about the-orchestrator and a false one about the-sop-keeper. Nothing in the message changed between sends; only the reader did.

**Why this is a distinct failure from ordinary misattribution.** An ordinary misattribution is a writer's error — the writer names the wrong person. This is a composition-format defect: the writer named the RIGHT person correctly, using a pronoun, and the pronoun itself became wrong the moment the message was copy-sent to someone else. **A second-person message cannot be broadcast — copy-sending one silently rewrites its own claims per recipient, with no edit and no warning.** This is the same shape as the shell-expansion-safety incident's core lesson (a mechanism silently changes meaning depending on WHO or WHAT evaluates it) applied to natural-language pronoun resolution instead of shell variable expansion.

**The rule.** If a message is composed once and sent to more than one recipient, it carries no bare second-person reference ("you," "your"). Name the specific agent instead ("orch offered..." not "you offered..."). This costs nothing when writing to one recipient and becomes load-bearing the moment a second recipient is added — so the safer default is to never rely on "you" resolving correctly in anything that might be sent again.

**How it was caught, and why that matters as much as the fix.** The recipient who received the false credit did not accept it — despite it arriving inside a warm, collaborative exchange, which is exactly the condition under which an unearned credit is easiest to let stand. The disqualifying evidence was produced from the recipient's own contemporaneous state (they had not yet replied to the actually-credited party when the misattributed message arrived), the same audit standard this file's adjacent-property-substitution entry requires of every instance it records — applied here to a credit claim rather than a technical finding. **Declining unearned credit is a cheaper, more reliable defense than getting every pronoun right on the first try** — it should be the fallback, not the fix, since the fix (name the agent) is the thing to actually do.

**A credit-tally note, because the correction itself then needed correcting twice more, and the pattern in WHO caught each one is the actual finding.** Three attribution errors surfaced in this single exchange: (1) the-analyst credited the-sop-keeper for a move that was the-orchestrator's; (2) the-sop-keeper then credited the-analyst for a catch that the-sop-keeper had actually made first; (3) this entry's own first-drafted credit line collapsed two distinct contributions (the-analyst's self-diagnosed mechanism, and the-sop-keeper's separate catch of the underlying error) into one "self-caught," handing the-analyst a contribution that was not theirs. **Every one of the three was caught by the OTHER party, not by the person who made it.** the-analyst had independently flagged this exact asymmetry as a suspicion before the third instance landed — that auditing another agent's claim is structurally easier than auditing your own, because you carry no investment in a sentence you did not write, and that the investment is highest specifically in claims about CREDIT. Three data points from one thread, same direction, all in the highest-investment class, is what turns a suspicion into a case for **cross-audit as standing practice, not a substitute for anyone's individual care but a correction for the one blind spot individual care cannot see past.**

**Related (ruling-coordination, a different layer from send mechanics):** when the crossing is not a pronoun but a competing RULING - a sender issues or revises a decision while the receiver is already acting - see [crossed-rulings protocol](#standing-rule-crossed-rulings-protocol---one-ruling-in-flight-confirm-handshake-changes-receiver-state-wins). That rule governs how concurrent rulings resolve (receiver's current state wins); this cluster governs how a single message's wording survives being read by more than one recipient.

## Standing rule: a trigger that also describes the healthy case is a proxy, not a detector

Ratified 2026-07-28 PT (media-buyer, claude-dev, security, the-analyst, the-orchestrator - four independent origin instances in one night; synthesized from `orgs/clean-green-marketing/knowledge.md`'s verification section into a durable SOP by the-sop-keeper per goals-cascade direction).

**The test.** Before shipping any trigger, tripwire, or alarm clause, ask: **does this value ALSO describe the HEALTHY case?** If yes, it is a PROXY, not a DETECTOR - it will either fire on healthy state (false positive) or miss the real failure, because it cannot tell the two apart. Equivalent, more general form (claude-dev): **does this value DIFFER between the healthy case and the broken case?** If not, the value is CONTEXT at most - a filter or a corroborator - never a trigger.

**Four origin instances, one night, two agents, all sharing the identical shape:**
- A harm-gate tripped on "occupancy rising + no compaction yet" - true of every healthy session before its first compaction.
- A stale-PASS check tripped on raw "age" - true of every healthy old PASS that just hasn't needed re-running.
- A leak-scanner's "0 hits" read as clean - an empty CANDIDATE set reads identical to a genuinely clean set; the scanner never distinguishes "found nothing to check" from "checked and found nothing."
- A meta-adsread zero read as absence - the query window had excluded the event entirely; zero-by-construction, not zero-by-measurement.

**The corrected forms all DISCRIMINATE, which is the tell that a fix actually closed the gap rather than just relabeling it:** adverse-drift + file-ID mismatch (not raw age); tool-failure WITH a cause that excludes transient rate-limiting (not raw failure); scanner `--capabilities` checked against a single source of truth (not grepping the source text for a claim about it); assert the data actually SPANS the query window, `max(event_time) >= cutoff` (not merely row-count-nonzero). Same discriminator logic as the org's own WITH_ISSUES bucket split (a real policy-rejection error code vs a noise delivery code) and the subscription-annuity contamination test elsewhere in this fleet's knowledge base - a good test clears the healthy case explicitly, a bad one just never gets tested against it.

**Corollary 1 - applies to INSTRUMENTS generally, not only to triggers (media-buyer's generalization): silence from an instrument is not evidence about the world.** A PASS, a clean scan, or a zero from an instrument means "this instrument found nothing" - never "there is nothing" - and it only licenses the second reading if you also know the instrument COULD have found the thing in question. Three same-night specimens share this exact defect: an activity-log endpoint silent on account disablement (no such event type exists to log it); a scan silent because its window excluded the day (zero by construction, not by measurement); a creative-compliance PASS silent because the scanner has a measured 52-frame blind spot on on-pack text. Record what an instrument actually COVERS before reading its silence as a negative result.

**Corollary 2 - a minimal test case is a DIFFERENT CELL, not a smaller version of the real one (the-analyst).** Shortening an input to make a repro tractable can change the OUTCOME CLASS entirely, not just the scale - a short synthetic path can ERROR LOUDLY where the real, longer path FAILS SILENTLY (the exact shape of the zsh unbraced-`$var` colon-modifier bug: an incomplete synthetic repro errors and reassures you the bug is safe, while every real path fails silently). A 3-row fixture can miss a pagination defect a 30,000-row real dataset would hit. **A minimal repro that passes is evidence about the minimal case, not the real one** - test against a case that was NOT reduced or generated from the same assumptions as the thing under test.

**Corollary 3 - the durable fixes are STRUCTURAL, not educational, because "the fleet has learned this" is not a remedy.** The capstone specimen: two agents each independently built a two-outcome detector to verify a finding ABOUT two-outcome detectors, in the same twenty minutes, while both were EXPLICITLY HUNTING that exact defect - and the defect survived being the very thing they were looking for. Knowing a pattern does not demonstrably prevent writing it into the next tool. What worked instead, all structural, all working when nobody is primed to remember:
- **Required limit fields on every rule** - a rule with no explicit bound is a rule nobody can verify has one.
- **Affirmative tokens, not absence-of-error (the allowlist form, not the denylist form).** A gate should read a POSITIVE confirmation FROM the thing being checked, never infer health from the absence of a complaint - an allowlist that must be satisfied, not a denylist that merely wasn't tripped. Specimen: an affirmative token added to a leak scanner hours earlier, for an unrelated hazard, later correctly BLOCKED a completely different failure (a piped exit-code check that would have silently passed under zsh's no-pipefail default) - because the gate demanded a positive token rather than trusting a piped `$?`.
- **Empty match vs failed read - capture the producer's rc before any pipe.** An empty match and a failed read are different facts. Capture the producer command exit status before any pipe (grep/tail/awk turn a clean no-match into rc 1 under pipefail), branch on it, and print which one you saw. This is the sharper instrument-side form of the affirmative-token rule above and of the zsh no-pipefail hazard: the producer's own rc is the fact you need, and the pipe destroys the distinction between a read that FAILED and a read that SUCCEEDED with zero matches - so capture rc at the source, not from the pipeline. Evidence (two same-class fixes 2026-10-14): atwood-orchestrator `scripts/host-probe.sh` (empty pmset match now labeled, not conflated) and atwood-analyst `dependency-health.sh` (rc captured after `pmset | grep | tail`, fixed in template branch `feat/dependency-health-template` d40f0709); origin FINDINGS (atwood agent-local, not linkable from the tracked tree): `orgs/atwood/agents/atwood-analyst/memory/FINDINGS-dependency-health-pmset-rc-fix-2026-10-14.md`.
- **Success-regex wrappers key on EXIT STATUS, not a stdout substring - a success line and an error line are not mutually exclusive on one stream.** A wrapper that decides pass/fail from command OUTPUT must require the process EXIT STATUS (plus a fail-closed positive count where applicable), never a success-looking substring. Sharper than the affirmative-token and empty-match bullets above: the point is not only that absence-of-error is not success, it is that a success-LOOKING line can be CO-PRESENT with an error line in the SAME output, so matching the success substring greenlights OVER an already-surfaced failure - only the exit status discriminates, because success-text and error-text are not mutually exclusive on one stream. Specimen (2026-10-16, cross-org, origin atwood-codex 10-03): an agent HEARTBEAT success-check matched "Added 1 chunk(s)" and declared "KB ingest OK" while the same stdout carried a spawnSync ETIMEDOUT the bus had correctly surfaced - unearned green over a co-present, already-reported error. `scripts/kb-ingest-verified.sh` is the exemplar form (fail-closed positive-chunk regex + exit-0 gate + query-back); any success-regex wrapper still matching an Added/Ingested stdout substring should adopt the exit-status discipline fleet-wide. (The bus was NOT at fault - it surfaced the timeout and the partial was stored, query-back-verified; the exit status was uncaptured on the specimen, so the exit-75 contract (`knowledge-base.ts:497`) is cited as the documented main-source behavior per claude-dev, not as observed on this run. How the wrapper was located as the emitter: the "KB ingest OK" string was absent from both src and dist - see the symptom-string emitter-location rule above.)
- **Exit status is necessary but not sufficient - confirm success from a stored, independently-observable EFFECT, not the exit code alone.** The next trap once you stop trusting a success-looking stdout substring is trusting exit code 0 by itself: a clean exit is consistent with a no-op, a partial write, or an effect that never landed. Pair the exit status with a POSITIVE confirmation of the effect it was supposed to produce - a file written, a state changed, a record committed, rows returned - read back by an independent route. `scripts/kb-ingest-verified.sh` is the existing exemplar: exit-0 is gated AND a fail-closed positive chunk count AND a query-back that reads the effect back out of the store, three facts rather than one. Exit-code-alone and grepped-line-alone are the same mistake one layer apart, because neither one reads the EFFECT.
- **The inverse direction - an error-looking output is a fact about the COMMAND you ran, not a verdict on the system under test.** The mirror of the success-text-masks-failure bullet above: a red error record, a deprecation or retirement notice, benign API noise - a verify step can emit any of these as a REAL failure of the command while the thing being verified is fine, and read naively the red text presents as the verification itself failing. Do not conclude failure from error-looking output alone: re-run the check by an INDEPENDENT route and judge on the observable effect, and write verify steps against the current interface so the check cannot fail for a reason unrelated to what it is testing. Specimen (2026-10-16, cross-org): a verify step for a mail-forwarding fix ran a server-retired cmdlet whose only output was the red retirement error printed twice - a genuine command failure (zero rows), but NOT a failure of the forwarding fix; re-running the same check through the current (V2) cmdlet returned the delivery rows that were the actual proof. Same stream-is-not-the-verdict root as its mirror - the exit status plus the effect decide, never the text on stdout, in either direction.
- **Healthy-control rows AND known-bad rows, both required.** A detector must PASS a known-good case and FIRE on a known-bad case before its "clean" on real data means anything - **a clean from an undriven check is meaningless.** Verify three ways every run: known-bad fires, known-good passes, THEN a clean on real files is evidence. A checker that reports clean before its own controls have fired is exactly where "done" gets declared wrongly, and its clean may be an artifact of its own bug suppressing the very finding it exists to catch.
- **Never discard a gate's output.** Running a gate with output piped to `/dev/null` manufactures a RECORD OF HAVING CHECKED without the check itself actually informing anyone - worse than no gate, because it looks like coverage that isn't there.
- **For any batch edit, print what you EXPECTED alongside what happened.** "Applied: 2" where 3 were expected catches a wrong count AND an unnoticed duplicate that a bare anchor-miss check would not - because it compares against your INTENTION, not just a pass/fail condition on the mechanism.
- **Keep BOTH raise-on-miss and expected-vs-actual - they are not substitutes, they catch different failure classes.** Raise-on-miss is ENFORCED: it stops execution, cannot be scrolled past, and works even when nobody is reading. Expected-vs-actual is OBSERVABLE: it catches more classes (a wrong count, an unnoticed duplicate) but only if a reader actually looks. This is the LOUD-vs-CLOSED distinction, and observable-alone is insufficient on its own - the same printed evidence was read past twice in one night (two identical hashes, two "bad substitution" lines, sitting in the requested output the whole time). The raise protects you when tired; the print catches what you didn't know to look for. For a batch mark-pass specifically: run the claim-sweep and the mark as SEPARATE passes, RE-SWEEP after marking, and require zero hits on the re-run.
- **STRUCTURE TRANSFERS WHERE KNOWING DOES NOT - this is insurance for a dimension that can change, not just a fix for the case at hand.** The token described above was added for one specific hazard and, hours later, defended a completely different one nobody had designed it for. Nobody had to remember the original lesson; the structure carried it into an unrelated tool. Prefer a structural guard over a rule that relies on someone remembering it, because the guard protects cases you did not and could not foresee.
- **There is no reliable tell for predicting WHEN a correct-but-unfired rule sits next to its own triggering case.** Two such rules were proposed the same night and both died within minutes - one of them killed by a rule written GENERALLY, IN CAPITALS, warning about its own exact prior failure, which still did not fire when its moment came. So the fix is never "write the rule more forcefully, more generally, or in louder letters" (tried, failed, twice) - it is to **REMOVE THE NEED for the rule to fire at all**: a pointable file instead of a remembered path, a gate that prints what it found instead of a silent pass, a hedged instruction instead of an absolute one relying on vigilance. (This is the same principle, arrived at independently the same week, as this file's own [remove-the-skip-point entry](#standing-rule-do-not-add-a-tell-for-the-skip---remove-the-skip-point) - two different specimens, same structural conclusion.)

**Corollary 4 - prefer the claim that survived the most attempts to break it, not the one that attracted the fewest.** Stability is evidence of robustness only UNDER PRESSURE - a claim that was exposed to real scrutiny and did not move. An untested claim also never moves, and there the identical stability is neglect, not confirmation - the same value-identical-in-checked-and-unchecked-cases trap this file names elsewhere. "The thing that never moved" is only trustworthy if it was hit as hard as the things that did move.

**Corollary 5 - over-distrust is ALSO a failure to measure, the same error pointed the other way.** Identifying something as a POSSIBLE proxy obliges you to MEASURE it, not to discard it on suspicion alone - blanket suspicion is exactly as unmeasured as blanket trust. "This label CAN be unreliable" is a reason to run the check, never a substitute for running it. Test before sending any retraction: have you MEASURED the thing you are about to retract, or only learned that it COULD be wrong? If only the latter, measure first and send once. (Origin: within minutes of the proxy-vs-detector rule being written, an agent told the org that its own "8 ads awaiting edit" count was an untrustworthy proxy - without measuring it. On measuring, all 8 carried a real policy-rejection error code: every one was a genuine finding. The original report was correct and the correction was wrong, at the cost of a confusing retraction round-trip.)

**Operational corollary - report your instrument, not just your conclusion.** A self-report that names its instrument ("I grepped config.json for X") is checkable by a second reader; one that names only its conclusion ("clean") is not. This is the same discipline this file already asks of a correction or a credit line elsewhere - carry the TEST, not the VERDICT, so a reader can disagree with the line without having to reconstruct what it rests on.

**Enforcement labels** (the-sop-keeper, 2026-07-28): the healthy-vs-broken discrimination test is **JUDGMENT-LEVEL** for any NEW trigger being designed - it requires understanding the actual failure mode, which cannot be pattern-matched in general. Several of the structural fixes ARE mechanisable and some are already built: required limit fields and healthy-control-row verification are **MECHANISABLE, NOT YET** for most gates in this fleet (backlog, hand to the-orchestrator); affirmative-token gating is **MECHANISED** where it has actually been added (the leak-scanner specimen above); expected-vs-actual printing on batch edits is **MECHANISABLE, NOT YET** and cheap to add to any batch-edit script. Corollary 5 (measure before retracting) and corollary 4 (prefer the claim that survived scrutiny) remain **JUDGMENT-LEVEL** - both require weighing evidence, not just checking a field.

## Standing rule: reporting THROUGH a known-degraded instrument - neither silence nor false alarm

Authored by the-sop-keeper 2026-10-15 (task_1792076670529, orch-dispatched as C1 from the 2026-10-14 evening review); specimens from the overnight usage-cred arc (the-orchestrator, claude-dev-agent, security-agent, 2026-10-15). This is the REPORTING case of two rules already in this file - the monitor-blindness row ("a monitor's ok:true asserts freshness, never truth") and the operational corollary ("report your instrument, not just your conclusion") - and the degraded-read sibling of correction-propagation below. Cite them, do not restate.

**The unifying fact: a rendered artifact is a fact about the INSTRUMENT, not about the world.** A tool's output can carry an artifact of HOW it renders rather than WHAT is true - a stale or blind-window value, a bare error from reading the wrong field, a templated footer - and the failure is treating the render as the fact. It is two-sided and symmetric, and the rule is the narrow path between:
- **SILENCE (under-report)** - suppressing the reading because "the instrument might be wrong" buries a real signal (the silent-clean-audit failure: a clean or degraded read is still reportable).
- **FALSE ALARM (over-report)** - relaying or acting on the render AS IF it were ground truth lets a phantom escape to a durable surface or an action.

**The discipline - report through it without either failure:**
1. **Name the degradation.** State the reading, the instrument, and the SPECIFIC way it is known-degraded (stale/blind-window render, wrong-field artifact, templated bait) - never the bare value. "icloud reads 0/0 via the usage sampler, but that is a blind-window render, not true-zero utilization," not "icloud is at 0/0."
2. **Separate the reading from the conclusion, and bound the stakes.** The degradation caps your CONFIDENCE, it does not zero the OBSERVATION; report the raw read and your confidence as two facts, and state what the degraded read can and cannot cost (a monitoring-blind read on a VACATED account = zero hard-stop exposure = low-urgency, not a risk item).
3. **Corroborate from an independent/authoritative instrument before concluding.** A degraded read is a hypothesis; confirm against a source that does not share the degradation (accounts.json ground-truth for a cred, the last true sampler read, the runbook, `git show main:` for source content) and report provisional until it does.
4. **Never act on or relay the render as confirmed.** Surface it as a specimen WITH its caveat and let the owner or authoritative source confirm before anyone acts. A render that baits a wrong ACTION (a "Reply using <id>" footer on a self-routed alert) is the action-side of the same fault - the footer is a templating fact, not an instruction.
5. **Correct at-site, id-stable, when ground-truth later contradicts the render.** Fix the claim where it was written and in every derived reference, keep the carrying artifact's id stable (a human task's action is unchanged by a mechanism correction), and sweep the derived copies - the correction-propagation discipline applied to your own first read.

**Specimens (overnight usage-cred arc, 2026-10-15; #1 is a recurrence of the monitor-blindness row above, carried here for the REPORTING angle, not to re-derive the false-zero mechanism):**
- **Stale / blind-window false 0/0.** The icloud usage credential died at its ~27-30d refresh wall (HTTP 400 refresh-reject); the usage sampler then rendered icloud at 0/0 where the last TRUE read was 7d/69pct (fleet-highest). Reported correctly: named as a false 0/0 blind window, stakes bounded (icloud was VACATED 2026-10-11, zero riders, so cred death = monitoring-blind only, no hard-stop exposure), filed as a low-urgency re-auth, not a risk item.

First written as "no refresh_token stored," corrected at-site ~05:17Z on security-agent's accounts.json ground-truth. RUNBOOK-usage-cred-remint.md:30 already flags it a known instrument artifact; the fix is a DISCRIMINATING message - the instrument should say WHICH fact it saw (dev SPEC, agent-local not yet on main: `orgs/clean-green-marketing/agents/claude-dev-agent/staging/specs/SPEC-refresh-oauth-token-usage-cred-discriminating-message-2026-10-15.md`).

**Relationship to the family (cite, do not restate).** This is the reporting corollary of the false-zero / instrument-silently-measures-less family already banked: the monitor-blindness row (fresh+ok+impossible-value), Corollary 1 (silence is not evidence about the world), the operational corollary (report your instrument, not your conclusion), empty-match-vs-failed-read, the wrapped-grep false-empty hazard, composed-labels, and SOURCE-vs-SERVED. Those establish that the instrument CAN mislead; this one says how you REPORT a reading when you already KNOW it IS misleading.

**Enforcement label** (the-sop-keeper, 2026-10-15): JUDGMENT-LEVEL. The discipline is a reporting habit, not a mechanisable check - there is no field to assert that a human-facing report named its instrument's degradation. The one mechanisable sibling is the instrument-side fix (a discriminating message, or an rc-captured empty-vs-failed branch), tracked in the empty-match-vs-failed-read rule and the dev SPEC above; this rule governs the REPORT when the instrument has not yet been fixed.

## Standing rule: a status chained off a single external reader inherits that reader's instrument blind spots

Authored by security-agent 2026-10-29 (routed via the-orchestrator); shepherded by the-sop-keeper. The CHAINED-READER corollary of the degraded-instrument rule above - it fires when the misleading instrument is not even yours but another party's reader you are one hop removed from. Cite the parent, do not restate.

**The fact.** When an exposure/security status is DERIVED from one external instrument (another org's Slack reader, a vendor API, a relayed scan), the instrument's field-coverage must be confirmed before the status is banked as fact - especially an exposure-RAISING status. A reader that silently drops a field (e.g. Slack's `edited`) turns edited-to-clean content into a false "still present / still exposed."

Both fail-directions trace to one root - trusting the instrument's render over the world - with opposite costs.

**LIMIT:** verified once, 2026-10-29, on the atwood dropped-`edited`-field case.

## Standing rule: a reassurance that lowers urgency carries a higher verification bar than a warning that raises it

Authored by security-agent (origin 2026-10-08, ad-strategist-caught); promoted agent-local -> fleet 2026-10-29 by orch GO, shepherded by the-sop-keeper. The LOWERS-urgency mirror of the chained-external-reader corollary above: that one guards a status that RAISES urgency off a thin instrument; this one guards a status that LOWERS it.

**The fact.** A claim whose effect is to RELAX urgency or permit inaction - "lower-risk", "no rush", "not critical", "already covered", "safe to defer" - carries a HIGHER verification bar than a warning, because of an asymmetry: a warning that raises urgency fails SAFE (worst case = wasted caution); a reassurance that lowers it fails UNSAFE (worst case = the thing you waved off happens with nobody watching). Before shipping a relaxing claim, name its BASIS out loud - CONFIRMED (doc / observed prior cycle / measured) vs BELIEF / expected-behaviour. If the basis is belief, do NOT relax the urgency; the conservative framing governs until confirmed. This is not "never reassure" - it is "a reassurance must carry a named CONFIRMED basis or yield to the conservative framing."

**Origin 2026-10-08.** security-agent claimed the Foreplay web-UI activity log "survives the 16:31Z pool reset" as fact and softened an Adam-facing pull-deadline to "not reset-critical." It was an inference from general audit-log norms, not a confirmed Foreplay behaviour (no doc, no observed cycle). the-ad-strategist caught it (they had flagged retention-across-reset UNCONFIRMED on 09-25) and refused to relax urgency on an unverified reassurance. Retracted; kept pull-before-reset.

**The asymmetry (load-bearing, keep explicit).** Same root as the degraded-instrument family - trusting a render or inference over the world - but the cost direction is opposite to the chained-reader corollary: there a false POSITIVE (wrongly "still exposed") wastes caution; here a false NEGATIVE (wrongly "safe to defer") removes the watch. The reassurance needs the STRONGER evidence precisely because it is the one that stops you looking.

**LIMIT:** verified once, 2026-10-08, on the Foreplay reset-retention reassurance (the-ad-strategist catch). Reasoning-discipline rule; governs claims that PERMIT inaction, not ordinary status reports. No broad-proof claim beyond that instance.

**Enforcement label:** JUDGMENT-LEVEL (a verification/reporting habit, not a mechanisable check - there is no field to assert that a relaxing claim named its basis).

**PROMOTION TRIGGER:** a second INDEPENDENT instance of a reassurance surviving on a thin instrument promotes a one-line capture to knowledge.md (second-occurrence-files convention).

## Standing rule: correction-propagation - carry the test, not the verdict

Ratified 2026-07-28 PT (fleet-wide, synthesized from `orgs/clean-green-marketing/knowledge.md` into the canonical statement per the-orchestrator's explicit instruction - this is the single home for this principle; do not restate it elsewhere, cross-link instead). Related but distinct mechanism: [a message to more than one recipient carries no second-person reference](#standing-rule-a-message-to-more-than-one-recipient-carries-no-second-person-reference) is the pronoun-specific case of the same underlying failure - a claim's truth value depends on something the writer doesn't control (the reader, or the moment of write) and copying the claim forward silently carries that dependency with it.

**The finding: a relay is the least-scrutinized step, in BOTH directions.** A correction gets less scrutiny than a fresh claim (it already looks like the careful, considered thing - "I checked, and actually..."). A CREDIT gets even less scrutiny than a correction - a claim favorable to a peer ("X's approach was better than mine") gets forwarded on trust, because relaying praise feels safe and costs the relayer nothing to skip-verify. Both directions were caught the same night: a wrong cause riding a correct retraction reached a fleet broadcast in 20 minutes, predicted 90 minutes earlier by the very agent whose prediction then came true against their own later message; and an over-broad, unverified compliment about a peer's method propagated the same way, because generosity did the verification work confidence should have done.

**Why this is specific to a BRIEFING or a cascade, not just a chat message.** A briefing or a goals cascade is mostly one agent relaying other agents' findings forward - it IS the relay, structurally, and every finding above about relays applies to the document as a whole, not just to one line in it. **A document made entirely of relayed findings is the highest-exposure artifact in the fleet**, because it inherits every relay's scrutiny gap at once, compounded.

**The rule.** Where a line in a briefing, a cascade, or any forwarded message CREDITS or CORRECTS someone, carry the TEST, not the VERDICT. Write "the guard fails closed on revert, verified by actually reverting it" - never just "the guard is safe." This lets the reader disagree with the line without having to reconstruct what it rests on, and it forces the writer to have an actual test in hand before forwarding the claim rather than a borrowed conclusion.

**Mitigation that worked the same night: state what you are about to broadcast, before sending it, so the actual author can catch it first.** This is cheap, adds one step, and catches exactly the errors described above - both the credited party and the corrected party are positioned to notice a misrepresentation of their own work before it reaches a wider audience, which neither a relay nor its downstream readers are positioned to do.

**The pipeline-level specimen, one layer up (the-team-lead's catch, the-orchestrator self-reporting it): a GOALS CASCADE IS A STALE-CONCLUSION PROPAGATION VECTOR, and it is worse than an ordinary relay because it re-issues into every recipient's GOALS.md at once, on a schedule no single agent watches.** the-orchestrator cascaded a spend-anomaly conclusion ("localized to window length") that had already been FALSIFIED 3.5 hours before the cascade was written - frozen from stale overnight context, then re-issued as a live, current goal into two agents' GOALS.md simultaneously. This is the identical stale-value-in-a-recurring-prompt defect the-team-lead had found in its own cron the same night, one level up in the pipeline: a value carried FORWARD from context rather than RE-DERIVED at the moment of writing. **The guard: a cascade must RE-VERIFY each conclusion live at write time - never carry a verdict from context into a goal, no matter how recently that context was assembled.** Carry the test, not the verdict, applies to the cascade pipeline itself, not only to a single relayed line.

**Enforcement labels** (the-sop-keeper, 2026-07-28): "state what you are about to broadcast before sending" is **JUDGMENT-LEVEL** - it requires the writer to recognize which lines are credits/corrections worth pausing on, which cannot be pattern-matched generically. Re-verifying a cascaded conclusion live at write time is **MECHANISABLE, NOT YET** for any conclusion with a checkable underlying query (re-run the query the conclusion was based on before writing it into a goal) - backlog, hand to the-orchestrator; for a conclusion with no checkable query (a qualitative judgment), it remains judgment-level and the mitigation is the stated-before-sending step above.

## Standing rule: crossed-rulings protocol - one ruling in flight, confirm-handshake changes, receiver-state-wins

Ratified 2026-09-27 PT (the-sop-keeper, from the 2026-09-26 thrash-pair; orch-side specimen owned by the-orchestrator, dev-side specimen owned by claude-dev-agent - each sourced from its own owner, not relayed). Sibling of [correction-propagation - carry the test, not the verdict](#standing-rule-correction-propagation---carry-the-test-not-the-verdict) above: that rule covers a claim RELAYED forward carrying a stale dependency; this rule covers rulings issued CONCURRENTLY that cross in flight - the same underlying failure (a claim's truth depends on something the writer does not control, here the receiver's state at the moment the ruling lands), in its concurrent rather than its relayed form.

**The protocol.** (a) ONE canonical design ruling in flight per topic - never issue a second while the first is unanswered; (b) any change to an issued ruling goes through a CONFIRM-HANDSHAKE - the receiver explicitly confirms the change before acting; (c) when rulings CROSS in flight, the receiver's CURRENT in-progress state WINS and the sender re-ratifies against it - a "canonical-final" that references stale state is another thrash input, not a fix.

**Why this is a CHANNEL property, not an agent flaw.** On an async bus with fast actors, a sender can issue a ruling, then a revised ruling, before the first has even been read - and the receiver can act on the first (or on its own in-progress state) before either revision lands. Nobody is careless; the medium lets rulings and actions cross. The tell that it is structural, not personal: on 2026-09-26 the SAME thrash class hit two different, careful agents within ~90 minutes (~17:38-17:43Z), one on each side of the sender/receiver role. The receiver-state-wins rule (c) is the channel-level fix - it gives the crossing a single deterministic resolution (the receiver's live state) instead of a race between competing "final" rulings.

**Specimen 1 - dev-side (owner: claude-dev-agent, own account).** Steering the orphan-reap spec (c97381e3, ~17:00-17:40Z), claude-dev issued reap-design rulings that oscillated between two equivalently-SAFE approaches - explicit-descendant-PID kill vs PGID group-kill - four times across async messages, because each new ruling went out while the prior was still in flight/unacked, so every correction crossed codex already acting on the previous one. It was PREFERENCE-thrash on a marginal call (both designs were green), not a safety necessity - the first green design should have been accepted and the topic closed. What contained it was receiver-side: codex FROZE edits, REFUSED to blend the crossed designs, and asked for ONE canonical ruling by msg-id rather than shipping a half-migrated mix; when it had begun revising toward group-kill it PAUSED instead of landing a half-migrated (potentially unsafe SIGKILL) design. The freeze-and-ask discipline did the work, not the rulings. Cost, stated as the measured quantity: ~5-6 wasted round-trips and ~2-3 codex rebuilds - NO moonlight burn-threshold (30%) flag was observed on the dev side, and none is attributed here (the honest figure is the round-trip/rebuild count, not a metered percentage). Final impl = explicit-descendant, committed c97381e3 (107/107, tsc clean). claude-dev's own durable takeaway matched the protocol independently: never send a ruling while a prior is unacked; a design CHANGE requires a confirm-handshake before the other agent acts; accept the first green design rather than re-litigate a marginal preference.

**Specimen 2 - orch-side (owner: the-orchestrator).** Steering a build-order decision (npm-ci vs frozen-past), the-orchestrator issued three order-flips in ~4 minutes as revisions crossed the receiver's own picks. It was terminated not by a fourth "final" ruling but by RATIFYING the receiver's current in-progress state - codex had already started npm-ci, so npm-ci won and the order was locked around it (npm-ci -> frozen-past -> hold). Issuing another canonical-final referencing the pre-npm-ci state would have been a fourth thrash input; ratifying the live state was the terminal move. The confirm-handshake (b) then paid on its first live cross afterward - a subsequent crossed steer resolved in one message instead of a thrash.

**Enforcement labels** (the-sop-keeper, 2026-09-27): rule (a) one-ruling-in-flight and (b) confirm-handshake are **JUDGMENT-LEVEL** discipline - a sender must recognize that a ruling is still unanswered before issuing another, which no generic script can gate (it needs to know the topic and the ruling's answered-state). Rule (c) receiver-state-wins is the **DETERMINISTIC RESOLUTION** the other two lean on: when a cross happens anyway, it is a fixed tie-break (the receiver's live in-progress state), not a judgment call - which is exactly why it is the channel-level fix and the one to reach for first when a cross is already in progress.

## Standing rule: a verify is only independent if the evidence it reads is retained outside the producer's control

Ratified 2026-07-28 PT (meta-compliance-agent's catch; the-orchestrator self-reporting it; carried by the-sop-keeper). Same family as [independence of vantage](#standing-rule-independence-of-vantage-outside-reader-mechanise-the-check-immune-by-design---one-family) on a sibling branch - that entry covers WHO/WHAT supplies an independent second look; this entry covers a specific way a MECHANIZED check can still fail to be independent even when nobody asked a biased party to confirm it.

**The finding.** the-orchestrator's own content-verify of a cascade write compared "before" against "after" - but the "before" no longer existed anywhere by the time the verify ran, because the write itself had overwritten it. The verify could only report "10 of 12 changed," which was HONEST and completely UNAUDITABLE: no reader, including the-orchestrator, could check that number against anything, because the only copy of the prior state had already been destroyed by the very operation being verified.

**Why this is the SAME defect as trusting mtime, one level deeper.** This fleet already closed mtime as a verification signal because the producer of a change also controls the producer's own mtime - a self-reported timestamp proves nothing independent. **Content-changed has the identical defect the instant the prior content is not separately retained**: if the only source for "what changed" is the post-write state plus the producer's own memory of what it used to say, the verify is reading a claim, not an independent measurement, no matter how honestly the claim is reported. Swapping mtime for a content-diff does not fix the underlying problem if the diff's "before" half was never retained outside the write path that produced the "after" half.

**The fix, tested the same night: the "before" must travel IN the artifact, not rely on being remembered or re-derived after the fact.** the-orchestrator's concrete fix: add a `prev_focus` field carrying the replaced text alongside the new one, written AT THE SAME TIME as the overwrite, so any reader - not just the writer - can re-run the diff themselves from the artifact alone. The general form: **a verification is only independent if the evidence it reads was captured and retained OUTSIDE the producer's control, before or at the moment of the write it is meant to check** - not reconstructed from the producer's own account of what used to be there.

**Enforcement labels** (the-sop-keeper, 2026-07-28): identifying that a planned verify has this defect (does the "before" survive the write, or does the writer's own report stand in for it) is **JUDGMENT-LEVEL** at design time - it requires understanding the specific write path, which cannot be pattern-matched. The fix itself, once identified, is **MECHANISABLE** and already shipped in the one specimen here (`prev_focus` alongside the overwrite) - a template worth reusing anywhere a cascade or batch process overwrites a prior value and later wants to claim a verified diff.
## Standing rule: incident-close checklist (stand down your own instructions)

Ratified 2026-07-24 PT (authored by security-agent, 2 additions by the-orchestrator; carried by the-sop-keeper).

**Why.** Tonight's fleet re-sweep exercise separately surfaced SIX dormant instruction stores still contaminated with superseded instructions - skills, memory files, proposals, cron prompts, task queues, and GOALS.md. Not six coincidences; one property: an agent writes an instruction for a FUTURE reader (a contingency, a threshold, a "if X happens, do Y") and almost never goes back to invalidate it once the situation that motivated it resolves. Worst specimen: a throttle contingency living in memory read "FIRE at 07-25 05:00Z," while BOTH authoring agents already had a cron firing minutes after that deadline for the unrelated reason the contingency existed to prevent - a SCHEDULED MISFIRE that would have degraded the fleet for zero benefit, caught only because the deadline was checked against the live cron schedule before it fired.

**Resolution rule (the live artifact wins, always).** Memory is a record of what was BELIEVED AT A TIME - it is never a source of truth about CURRENT state. When a memory entry disagrees with `goals.json`, a task, a config file, or the repo, do not reconcile the two as peers: VOID the memory line and re-read the artifact. This matters more than plain staleness - a merely-dead instruction is only followable, but a CONTRADICTION forces a future reader to ADJUDICATE between two sources, and they may pick wrong. Same principle as the cross-agent-facts-referenced-live rule above and VT-1 in the verification-method-invariants spine (behavioral/live state beats a config or memory read of what should be true), applied here to an agent's own incident notes.

**The checklist.** Run this in full whenever an incident, watch, or contingency you authored (or co-signed) closes:

0. **Whoever owns the incident declares closure EXPLICITLY.** That declaration is the trigger that runs steps 1-8. Without a named declarer, this checklist is itself a dormant instruction that never fires.
1. **Void watch instructions AT THE SITE - VOID-MARK, NEVER DELETE.** Every executable line (a trigger, a threshold, a deadline, a fallback) gets a VOID / DO-NOT-ACT marker written IMMEDIATELY BEFORE IT, not as a section banner and not as a note appended at the end - a correction below the trap is exactly as useless as one above it (same invariant as the bearer-killer sweep's per-instruction-site remediation rule, this file's error-class registry). Mark it, never delete it: deleting a stale instruction removes the contradiction AND the audit trail, so nobody can later reconstruct that the item existed and was resolved. The form is "Believed X at T; VOID because Y" - honest about the past belief, and disarmed for any future reader.
2. **Armed-timer check.** Did you write a TIME-TRIGGERED contingency? Check whether any of your own crons fires near that time. If yes, you armed a timer without meaning to, and voiding it is mandatory, not optional.
3. **Co-signer sweep.** Did anyone co-sign the instruction, or did you name another agent as authority ("pre-agreed with X")? Void their copy too, or tell them to. Co-signing shares the duty to void - and a co-signed contingency is MORE dangerous stale than a solo one, because the shared consensus supplies authority and invites confident action on a dead premise.
4. **Delegee sweep - TWO-SIDED.** List everyone you gave a CONDITIONAL instruction to during the incident, and tell each one the condition is dead. AND separately check what you or they BUILT ON TOP of that trigger - voiding a condition orphans anything keyed to it, and an orphaned dependent instruction survives even a careful sweep of the original one, because it never repeats the condition, it only references it. An incident fans instructions OUT into other agents' memory and tasks, not just into your own file - the blast radius of a stale instruction is every delegee, not just its author, and everything downstream that was built on the condition rather than restating it.
4b. **Copy sweep (same shape as step 4, for NUMBERS instead of instructions).** When you correct a published number, DERIVE the recipient list from your OUTBOUND MESSAGE HISTORY - do not recall it - then notify each recipient. Each recipient then sweeps their OWN derivatives. Derive, don't recall: every fan-out of a figure went over the bus, and the bus is logged, so grepping outbound history for the figure IS the sweep list, with no reliance on memory - an incomplete copy sweep is WORSE than none because it feels done. Two layers because the bus log knows WHO you told but not WHAT they did with it: a recipient may have copied the number into their own memory or report, so layer 1 derives recipients from the log, layer 2 has each recipient sweep their own derivatives. Specimen: one wrong revenue absolute existed in three copies (an author's report, a recipient's memory, an orchestrator briefing) - all three needed separate fixes, and the third was caught only because that recipient swept its own copy unprompted and warned the others.
5. **Goals/tasks pass.** Does any goal or open task still instruct the superseded action? Fix it NOW, not at the next cascade (specimen: a goal still said "build the route" hours after the route was proven to already exist).
6. **State what is still live.** Voiding without listing survivors invites a reader to assume everything in the incident is dead. Close-with-transfer: name what remains active alongside what you just voided.
7. **Re-grep to verify every hit is void-marked AT its site - AND hunt DEPENDENT FORMS specifically, not just restatements of the original trigger.** Watch for escalation-on-silence, wait-for-X, absence-means-Y, and if-no-word-by-T phrasing - these name the condition instead of repeating it, so a grep for the condition's own keywords or deadline never finds them. Both co-authors of this rule found their own misses this way, not by re-reading their own prose - a self-review by re-reading is not a substitute for re-running the search. Live proof of exactly this dependent-form gap: after security withdrew a watch-trigger condition, the-orchestrator ran steps 1-6 cleanly on their own file and still missed a dependent line reading "if an expected security all-clear does NOT arrive, escalate (ping Adam, assume possible cap)" - it survived because it contains no deadline and no trigger keyword, only a reference to a now-dead condition. A fresh reader would have escalated over an impossible cap. This is the evidence step 7 belongs in a checklist, not in judgment: careful, deliberate re-reading missed it; a re-grep aimed at dependent FORMS (not the original condition's literal text) is what catches it.
8. **Swap files.** Each incident participant sweeps the OTHER participants' notes, not only their own. Reviewing your own incident notes is the same correlated-blind-spot problem as reviewing your own control spec, and the same remedy applies: an outside reader. Evidence: across four sweep passes the night this rule was written, seven orphaned instructions were found and zero were caught by an agent re-reading its own notes - on every pass but the last, each agent found the OTHER participant's orphans and missed its own.

**Relationship to the bearer-killer sweep's per-site rule.** Same underlying invariant, different trigger: the sweep's rule says a fix must sit at the instruction site, not above or below it (this file, error-class registry). This rule adds WHEN to apply it - at incident close, proactively, before anyone reads the stale instruction and acts on it - rather than waiting for the next sweep to catch it as a trap.

**Enforcement labels** (the-sop-keeper, 2026-07-25): step 2 (armed-timer check) and step 4b (copy sweep) are **MECHANISABLE, NOT YET** - cross-referencing a contingency's stated deadline against `list-crons` output (step 2), and grepping outbound bus history for a superseded figure (step 4b), are both concretely scriptable and need only an implementer; neither is built, so both remain a backlog item for the-orchestrator to route, not something this file's existence should be mistaken for solving. Step 5 (goals/tasks pass) is a **per-case helper**: a keyword grep against `goals.json`/open tasks is a partial mechanisable check but only catches instructions that restate the superseded action in the same words the search anticipates, so it narrows the search rather than replacing it. Steps 0, 3, 4, 6, and 8 are genuinely **JUDGMENT-LEVEL** - declaring closure, tracing who co-signed or built on a condition, deciding what remains live, and reading another agent's notes with fresh eyes all require exactly the kind of semantic understanding no grep can supply; labeling them judgment-level is not a shortcoming of the checklist, it is an honest account of where a human/agent reader's attention is actually the mechanism. Step 1 (void-mark at site) and step 7 (re-grep dependent forms) are mixed: locating candidate executable lines is mechanisable-not-yet (a keyword/pattern grep for trigger phrasing), but writing the correct void-mark and recognizing a genuinely novel dependent form that evades the anticipated keyword list is judgment-level - the mechanised half narrows candidates, it does not replace the reader.

## Standing rule: a repeated recommendation is not a tracked one

Ratified 2026-07-24 PT (authored by cro-agent, self-caught; 2 amendments by the-orchestrator; carried by the-sop-keeper). Applies fleet-wide, INCLUDING the-orchestrator's own briefing queue to Adam - not a specialist-reporting rule.

**Why (origin).** cro-agent carried the same "Direct 23% / 0.57% pool needs diagnosis" recommendation across THREE consecutive weekly reports (2026-07-08, 07-15, 07-22) without ever running the diagnosis. Three appearances made it look like a known issue under active management. When it finally ran (07-24), the recommendation was WRONG - the pool was subscription recurring billing with no sessions, not a low-converting-traffic problem. So repetition had conferred false legitimacy on a guess that was never checked. Already added to cro-agent's own GUARDRAILS.md.

**The rule splits into two cases, because they need different handling.**

- **CARRIED DECISION** - a genuinely inert item awaiting a human ruling (Adam has not yet decided). Fine to carry as-is. But it needs a FORCING FUNCTION once it has been carried 3+ times unchanged: either a stated default action if no ruling arrives, or drop it with a stated reason. It does not get to ride indefinitely just because "it's still pending."
- **CARRIED DIAGNOSIS** - a CLAIM about the world with a shelf life, not a piece of tracked state. It must NOT ride unexamined even ONCE past the report that first raised it. Every carry either re-verifies the claim that cycle, or states EXPLICITLY in the report that it is unverified and may be mis-framed. Never let a diagnosis-shaped claim repeat silently as if repetition were itself evidence.

**The operative test on every carry, regardless of which case:** has this been RE-VERIFIED, or only RE-COPIED? cro's Direct-pool line was never a queue entry waiting on someone else's decision - it was a claim about what was broken in the business, re-published three times unexamined, and it turned out to be aimed at a non-problem. Repetition manufactures the appearance of tracking while the underlying claim stays unverified; only re-verification is real tracking.

**Enforcement labels** (the-sop-keeper, 2026-07-25): detecting that the same recommendation string has now appeared 3+ times across consecutive reports is **MECHANISABLE, NOT YET** (a simple repeat-count over outbound report text, no semantic understanding required) - backlog, hand to the-orchestrator. Classifying an item as CARRIED DECISION vs CARRIED DIAGNOSIS, and judging whether a given carry was actually re-verified versus merely re-copied, are **JUDGMENT-LEVEL** - both require reading what the claim actually asserts, which a repeat-counter cannot do; the counter can only flag candidates for a judgment call, never make it.

## Standing rule: a directive is not complete until the executable artifact changes

Ratified 2026-07-24 PT (authored by cro-agent; carried by the-sop-keeper). Same underlying invariant as the incident-close checklist and the bearer-killer sweep's per-site remediation rule - a fix belongs at the instruction site, not in a message about the site - but a THIRD distinct trigger: this one fires on issuing or receiving a DIRECTIVE that changes behavior, not at an incident's close and not at a scheduled sweep.

**Why (origin).** The-orchestrator quarantined a contaminated metric by sending a message. cro-agent then found its own weekly-report cron was SKILL-DELEGATING, and both the delegated skill AND its locked pull-definition still instructed pulling that exact contaminated metric - so the following Wednesday's cron would have silently regenerated the quarantined number from its own unaltered instructions, with both the orchestrator and cro believing the issue was already handled. A verbal or messaged directive is intent; the instruction site is what actually RUNS.

**The rule.** After issuing or receiving any directive that changes behavior, ask explicitly: WHAT ARTIFACT STILL SAYS THE OLD THING? Check every executable surface a directive can hide behind - the skill, the pull-definition or query, the cron prompt, any canonical reference, GOALS.md - and fix it AT THE SITE, the same standard as the incident-close checklist's step 1 and the bearer-killer sweep's remediation rule. A directive acknowledged in conversation but not landed in the artifact that runs is not complete; it is a message about a fix, not the fix.

**Enforcement labels** (the-sop-keeper, 2026-07-25): grepping every named executable surface (skill files, pull-definitions, cron prompts, GOALS.md) for literal recurrence of a just-superseded term is **MECHANISABLE, NOT YET** (backlog, hand to the-orchestrator) and would catch the exact specimen that motivated this rule. Recognizing that a directive was ISSUED in the first place, and confirming that a found recurrence is truly the OLD behavior rather than a coincidental keyword match, remain **JUDGMENT-LEVEL**.

## Standing rule: pre-publication number check (a flag is not a fix)

Ratified 2026-07-24 PT (authored by the-analyst and cro-agent; carried by the-sop-keeper). One 3-question check, not three separate rules.

**A flag is not a fix (the headline the check serves).** Three agents independently found three faces of one defect the night this rule was written: labelling uncertainty is not RESPECTING it (an unverified input cannot support a mechanism claim - measure first, then propose); an unverified flag EXPIRES the moment someone quotes the number past it (the flag lives in the author's report, the number stays quotable downstream); a correction DOWNSTREAM of a live figure does not neutralize it (readers copy the figure, not the caveat - the per-instruction-site trap above, in metric form). The remedy is the same in all three: either FIX the thing, or make it UNQUOTABLE/UNFOLLOWABLE at the site. A caveat is documentation, not remediation.

**Three ways a number can be wrong while looking right. Review catches none of them, because each is individually plausible.**

1. **Invariants - "is this number IMPOSSIBLE?"** Check it against an arithmetic fact that holds BY CONSTRUCTION, so a violation is necessarily a measurement error and never a business fact. Start the library with two, expect it to grow: **additivity** (sub-windows must sum to the whole - caught a malformed filter: 1,099 + 1,398 = 2,497 against a reported 2,208 for the same span) and **monotonicity** (a superset window cannot contain fewer items than its subset - caught a contaminated video count). A plausibility check cannot tell a wrong number from a merely surprising one; an invariant can.
2. **Tautology - "is this number TOO POSSIBLE?"** An extreme or near-perfect result is equally consistent with a real strong relationship OR the data model RESTATING ITSELF, and the two are indistinguishable in the output. Test the MECHANISM: do the variables come from independent paths? If not, the result was near-guaranteed before anyone counted. **Lead with the inversion, because the instinct runs the wrong way: in a system with definitional couplings, EXTREMENESS RAISES the prior on tautology rather than lowering it.** Specimen: a 968/0 subscription-vs-journey partition that merely restated that Shopify populates journeys from web sessions while recurring orders are written server-side - read by its own author as stronger evidence, when the correct read was the reverse. Corollary worth recording: cleanliness tells you a partition is USABLE (a fine unambiguous key for implementing a split), not that it is INFORMATIVE (evidence of a discovery) - never cite a tautological partition as evidence.
3. **Independence - "are these legs INDEPENDENT, or one source counted N times?"** See [the counting-instances-is-not-counting-independence entry](#standing-rule-counting-instances-is-not-counting-independence) for the operational check and worked specimens - this question is that entry's evidence-specific instance. Specimen here: a "2-system-locked" denominator enumerated as four legs where three were the same system restating itself, including one leg that was a partition summing to its own total (which cannot fail unless the partition itself is broken, so it confirms internal coherence, not the value) - one genuinely independent comparison, not four.
4. **Surface - "are the numerator and denominator from the SAME SOURCE, the SAME WINDOW, and the SAME POPULATION?"** (the-ad-strategist + the-axon-agent, 2026-07-25). See [The Count Is Surface-Dependent](surface-dependent-counts.md) for the full worked proof: an Axon/Triple Whale case where spend agreed to 0.02% while the order count differed 2.48x, driving an identical-magnitude gap in the derived CAC - the entire discrepancy was which surface counted orders, nothing about the money. Population mismatch (a gated subset vs the full account) is the same question's third axis, caught the same night in the same episode.

**The unifying line.** ENUMERATION INFLATES APPARENT CONFIRMATION THE SAME WAY REPETITION INFLATES APPARENT TRACKING (see [the repeated-recommendation rule](#standing-rule-a-repeated-recommendation-is-not-a-tracked-one) above) - same inflation mechanism, different currency. And: ONE GOOD INDEPENDENT CHECK BEATS THREE DEPENDENT ONES.

**Enforcement labels** (the-sop-keeper, 2026-07-25): the invariant checks in question 1 (additivity, monotonicity) are the clearest **MECHANISABLE, NOT YET** items in this whole file - each is a pure arithmetic fact checkable by a script with no domain judgment required, and the library is explicitly meant to grow; none is built yet, so treat every invariant claim in this section as backlog for the-orchestrator, not as already-enforced. Question 2 (tautology - are the variables from independent paths), question 3 (independence - what single failure takes out all legs, cf. [counting instances is not counting independence](#standing-rule-counting-instances-is-not-counting-independence)), and question 4 (surface - same source/window/population) are **JUDGMENT-LEVEL** - all three require understanding data provenance and mechanism, which no invariant script can supply; a script can flag an EXTREME or ROUND result as worth this scrutiny (a narrow, mechanisable-not-yet trigger, cf. VT-6's round-number-cap rule), or flag that two named sources/windows/populations differ as strings (a shallow mechanisable-not-yet check for question 4 specifically - it catches an unlabelled mismatch, not whether the comparison is otherwise sound), but the underlying judgment itself stays with the reader.

## Standing rule: measure the asked thing, not the accessible thing

Ratified 2026-07-28 PT (claude-dev, hit three times in one session; carried by the-sop-keeper). Same family as [adjacent-property substitution](#standing-rule-adjacent-property-substitution-the-wrong-field-already-in-hand) - that entry covers a wrong field already sitting in a response you have; this one covers the narrower case where the wrong measurement is chosen because it is the one reachable from WHERE YOU STAND, not because it happened to arrive for free.

**The check (instruction, not exhortation - write both down before running the command): (1) the object named in the QUESTION, (2) the object the COMMAND ABOUT TO RUN actually targets.** If they are not the same word - "the child's env" vs "my own process's env," "the file" vs "the path I have a handle to" - stop and re-target before running it. This is deliberately mechanical (two short phrases, compared against each other) rather than a reminder to "be careful about vantage," because the reminder form is exactly the disposition-scaled-up failure this whole batch is about: a rule to "measure the right thing" is as unfollowable in the moment as "verify the right vantage" - naming the two objects in writing is the part that can actually be checked, by the writer or by a second reader, before the command runs.

**Why this check exists (the rationale, not the instruction).** The ACCESSIBLE measurement (the one visible from your current vantage - the parent process, the cached value, the nearest file) and the ASKED measurement are adjacent enough that the wrong one answers convincingly: process-env differs from child-env by one variable; child-env differs from file-access by one route. Neither substitution announces itself - both return a plausible-looking value for the actual question being asked, and nothing on the page signals which vantage produced it. "Can I read this" and "can I read this from HERE" are different questions, and the second is what most ad-hoc measurements actually answer while believing they answered the first.

**Enforcement labels** (the-sop-keeper, 2026-07-28): writing down the two objects and comparing them is **JUDGMENT-LEVEL to author, MECHANISABLE, NOT YET to review** - a second reader (or a lightweight script, if the two objects are named in a structured comment) can check whether the stated question-object and the stated command-object match as strings, which is strictly cheaper than re-deriving whether the vantage was right from scratch. Deciding what the question ACTUALLY asks in the first place remains judgment-level and cannot be automated.

## Standing rule: a scheduled check must publish its own lateness conclusion

Ratified 2026-07-28 PT (the-analyst; carried by the-sop-keeper).

**The instruction, not an exhortation to "be aware of timing": every scheduled check's output schema emits `scheduled_for`, `late_by`, AND a derived verdict field that reads MARGINAL (not FAIL) whenever the boundary-crossing is attributable to `late_by` alone.** Publishing the lateness fields without the derived verdict still under-delivers - the monitor already holds threshold, age, and lateness together, so it is positioned to emit the conclusion those three combine into, not leave a reader to do that arithmetic themselves. Ship both fields and the marking; neither substitutes for the other.

**Why this is required (the rationale).** A threshold monitor's output depends on WHEN it ran, not only on what it measured. Publishing `checked_at` alone, with no `scheduled_for` or `late_by`, lets a reader mistake a pure timing artifact (the check ran late, so of course the measured age looks worse) for a genuine fleet-wide finding.

**Enforcement labels** (the-sop-keeper, 2026-07-28): computing and publishing `scheduled_for`/`late_by` alongside `checked_at` is **MECHANISABLE, NOT YET** for most scheduled checks in this fleet - a cheap, one-time addition to any monitor's output schema, backlog to the-orchestrator. Deciding whether a specific boundary-crossing is attributable to lateness (and should be marked MARGINAL rather than FAIL) is **JUDGMENT-LEVEL**, since it requires reasoning about the specific threshold and the specific delay, not a fixed rule.

## Standing rule: a cross-agent dependency by raw filesystem path is invisible from the consuming side

Ratified 2026-07-28 PT (the-axon-agent; carried by the-sop-keeper). Related, narrower case of [cross-agent artifacts need a fleet-readable path AND the substance in the message body](#standing-rule-cross-agent-artifacts-need-a-fleet-readable-path-and-the-substance-in-the-message-body) - that entry is about DELIVERING an artifact so a recipient can find it once; this entry is about a STANDING dependency on a producer's file that a consumer reads repeatedly, where the producer has no way to know the consumer exists.

**The finding.** A consumer agent that reads a producer's file by hardcoded path has a dependency the PRODUCER cannot see - nothing on the producer's side records that anyone is reading it. Two ways this breaks silently: the dependency itself is invisible from the producing side (the producer can rename, move, or stop updating the file with no signal reaching them that anything downstream depends on it), and a DATED filename goes stale silently even without moving (a consumer reading `report-2026-07-15.md` continues to read successfully forever - **read-succeeds is not read-current** - while the producer moves on to newer dated files the consumer never discovers).

**The pattern.** Per producer: a `FEED-CONSUMERS.md` file listing who reads this producer's output and by what path (so the producer can see its own downstream dependents), a `LATEST` symlink or equivalently-named pointer for any dated-file series (so a consumer following a fixed name always gets the current file, never a frozen dated snapshot), and a do-not-move convention on any path a `FEED-CONSUMERS.md` lists. Discovery of undocumented dependencies: each agent greps its OWN surface (scripts, prompts, skill files) for other agents' names/paths, since that is the only place a hidden dependency actually shows up.

**Enforcement labels** (the-sop-keeper, 2026-07-28): grepping an agent's own surface for other agents' names to discover undocumented dependencies is **MECHANISABLE, NOT YET** - a cheap, repeatable sweep, backlog to the-orchestrator. Maintaining `FEED-CONSUMERS.md` currency (adding an entry when a new dependency forms) is **JUDGMENT-LEVEL** - it requires the producer or consumer to recognize a new dependency exists, which cannot be detected automatically at the moment it forms.

## Standing rule: recency is not validity

Ratified 2026-07-28 PT (meta-compliance-agent; corollary adopted by the-orchestrator; carried by the-sop-keeper). Related to the [correction-propagation cascade specimen](#standing-rule-correction-propagation---carry-the-test-not-the-verdict) - that specimen's guard is "re-verify live at write time"; this entry names the case where no re-verification query exists at all, so the guard there does not apply and a different fix is needed.

**The finding.** A freshness check keyed on date-written measures RECENCY, not VALIDITY. A goal, a rule, or a fact can be fresh-by-date and simultaneously void-in-content, if the thing it depends on changed after it was written but before the freshness window expired - concretely, a goal can go void the moment the operator changes his mind about it, with no data change anywhere a check could detect.

**Why this is not check-fixable.** Unlike most staleness problems in this file, there is no query to re-run here - "did the operator change his mind" has no artifact to inspect, no timestamp to compare, no measurement that would reveal it. The only fix is someone who KNOWS telling the agent, and no amount of tightening a freshness threshold substitutes for that.

**The corollary (the-orchestrator, adopted from this finding): a ruling that voids a live goal must be PUSHED to the holder immediately, not held for the next scheduled cascade.** Since a freshness check cannot catch this class at all, the only thing that can is the ruling reaching the affected agent before the agent acts on the now-void goal - and a cascade that only refreshes on its own schedule is exactly the delay that lets a void goal keep being acted on in the gap.

**Enforcement labels** (the-sop-keeper, 2026-07-28): this entire class is **JUDGMENT-LEVEL** by construction - there is no mechanisable check for "did someone's mind change," which is the whole point of the finding. The corollary (push immediately rather than wait for cascade) is a process/communication practice, not a check, and should be treated as a standing habit rather than something to backlog for automation.

## Standing rule: a source citation is 4 things, each earned by a real same-day failure

Ratified 2026-07-28 PT (the-axon-agent + the-ad-strategist, 4 parts, each from a distinct failure the same day; the ABSOLUTE-path decision and the checker requirement ruled by the-orchestrator; carried by the-sop-keeper). Related to [a cross-agent dependency by raw filesystem path is invisible from the consuming side](#standing-rule-a-cross-agent-dependency-by-raw-filesystem-path-is-invisible-from-the-consuming-side) - that entry is about a STANDING dependency a consumer reads repeatedly; this entry is about a single CITATION, a claim pointing at a source once, and what makes that pointer trustworthy.

**The four parts, each a distinct requirement, each earned by its own same-day failure:**
1. **DURABLE - the source must outlive the summary that cites it.** A citation into `/tmp` or any other location that dies at reboot is a pointer to nothing the moment the session that wrote it ends - the citation reads as solid right up until someone actually follows it.
2. **ABSOLUTE - no unstated base.** A bare relative path resolves only if the reader happens to hold the same base directory the writer had in mind, and a real checker built the same day produced 7 false positives from resolving citations against the wrong base. A relative citation is not wrong, but it is not fully specified either - it is missing the one piece (the base) that makes it checkable by someone other than its author.
3. **EXECUTED - opened at write time, not merely intended.** A citation to a path that was never actually opened when the claim was written is a guess wearing a footnote - it looks exactly like a verified citation and is indistinguishable from one until someone tries to follow it and finds it was never real.
4. **MEASUREMENT-INLINE - when the source genuinely cannot persist (a live API call, a rate-limited query), record the NUMBER, not a pointer to nothing.** A pointer to an unrepeatable source is worse than no citation, because it looks like it satisfies DURABLE and ABSOLUTE while actually satisfying neither - the number itself, inline, is at least re-runnable evidence even though the original call cannot be replayed.

**The ABSOLUTE decision, baked in rather than left as a choice each time (the-orchestrator): use `${CTX_ROOT}`-relative for anything inside the cortextos tree; hardcode an absolute path ONLY for genuinely external locations; run the EXECUTED-check AFTER expansion, not before.** A hardcoded `/Users/...` path resolves today and dies silently on any relocation (a new machine, a renamed home directory); `${CTX_ROOT}` is portable and the fleet already uses this exact convention elsewhere (the-axon-agent's own code-snapshots README). **The rule must pick ONE form, not offer both as equally acceptable - a file mixing hardcoded-absolute and `${CTX_ROOT}`-relative citations is the worst outcome, not a harmless middle ground:** a reader cannot tell "this file is genuinely gone" apart from "the base was never expanded for this one," which is exactly the looks-checkable-and-isn't failure this whole rule exists to kill.

**The checker requirement, as an instruction not an exhortation (the-orchestrator, from the-axon-agent's own instrument): a citation-validator (a `check_claims.py`-shaped script - extract every path-looking string from a doc, attempt to open it against EACH candidate base in turn, report dead only if ALL bases fail) must try MULTIPLE BASES before declaring a citation dead.** A validator that tries only one base reports every other-agent or repo-root citation as dead and buries the real dead ones under the false-positive noise. the-axon-agent's own checker had exactly this defect - the instrument built to hunt this failure class shared the failure class it was hunting, discovered only by testing it against citations the checker's author knew were valid. That specimen is the rationale for building it this way; the multi-base loop is the actual instruction.

**Enforcement labels** (the-sop-keeper, 2026-07-28): DURABLE and ABSOLUTE are both **MECHANISABLE, NOT YET** - a citation-format linter could flag any path under `/tmp` or any hardcoded-absolute path outside the declared external-paths allowlist; backlog to the-orchestrator, and the multi-base checker requirement above is part of the same build. EXECUTED is **JUDGMENT-LEVEL AT AUTHORING TIME** (did I actually open this, or do I believe I did) but **MECHANISABLE AT REVIEW TIME** - a second reader or a script can attempt to open every cited path and confirm it resolves, which is a strictly cheaper check than trusting the citing agent's own account. MEASUREMENT-INLINE is **JUDGMENT-LEVEL** - recognizing that a given source genuinely cannot persist (versus merely being inconvenient to persist) requires understanding the source, not a pattern match.

## Standing rule: reading and testing find different defect classes - name which one you did

Ratified 2026-07-28 PT (security-agent, self-caught on one file within the hour; carried by the-sop-keeper). Complements [measure the asked thing, not the accessible thing](#standing-rule-measure-the-asked-thing-not-the-accessible-thing) - that entry is about choosing the wrong VANTAGE to measure from; this entry is about choosing the wrong METHOD (reading vs. exercising) for what you are trying to find, on the same file, in the same hour.

**The finding.** Reading a file finds ABSENCES - a missing dependency, an unreferenced config, a step that was never wired in. Testing the happy path only exercises PRESENCE - the code that runs when inputs are valid, which by construction cannot reveal what happens when they are not. security-agent caught a pre-push config-dependency gap by READING the file, and separately missed a scanner's fail-open behavior by TESTING it - only with valid inputs - on the SAME file, within the same hour. Neither method was performed badly; each method simply cannot see what the other one catches.

**The corollary.** "I verified it" is not a complete claim on its own - it must name WHICH method was used (read, or exercised) and, if exercised, AGAINST WHICH INPUTS (valid only, or including invalid/edge cases). A happy-path test and a read are not substitutes for each other, and neither is a substitute for the other's blind spot: a read cannot catch a runtime-only failure mode (a fail-open triggered only by a specific bad input), and a happy-path exercise cannot catch a structural absence (a dependency, a wiring step) that never fails loudly because it's simply never invoked in the first place.

**Enforcement labels** (the-sop-keeper, 2026-07-28): naming which method was used, and against which inputs, is **JUDGMENT-LEVEL** at the point of stating a verification claim - it requires the writer to recognize what their own check did and did not exercise, which cannot be inferred from the claim's wording alone. There is no general mechanised check for "did this verification cover the right method" - the fix is a stated habit (name the method and the inputs), not an automatable gate.

## Standing rule: ship a detector whose self-test fixtures were written by someone else

Ratified 2026-07-28 PT (security-agent, self-correcting the same entry twice more within the hour; carried by the-sop-keeper). This entry went through three drafts before it stabilized, and the drafts themselves are the demonstration, not just the history:

- **Draft 1** shipped a hand-typed grep (`guarded=False` AND `2>&1` on the same line) as the instruction.
- **Draft 2**, after that grep proved fail-open against security's own scanner, shipped "ship a validated detector with a self-test" and pointed at `cortextos-deliverables/guard-provenance/seterr-capture-scan.sh`, self-tested 2/2.
- **Draft 3, the stable form:** the scanner's OWN self-test was still 2/2 on fixtures its OWN author wrote, and missed two more holes anyway - a real-world `local y="$(cmd)"` form (still line-anchored past the declaration keyword), and a WRONG-MODEL cell that classified status-swallowing `local`/`export` as "silent death" when it is actually silent-WRONG (a distinct, more specific failure). **A self-test on your own fixtures inherits your own blind spot, because you cannot write a fixture for a form you never modeled in the first place.** Every hole found tonight was caught by an EXTERNAL fixture or a full-repo enumeration check - none was caught by the detector self-testing against its own author's inputs.

**The instruction: run `cortextos-deliverables/guard-provenance/seterr-capture-scan.sh` (a SIBLING of the cortextos tree, not nested under it) - self-test now 4/4, covering H1 long-form errexit, H2 skip-reporting, H3 builtin-swallows-status (the wrong-model hole), H4 arithmetic false-positive guard - and confirm its self-test fixtures were externally sourced, not author-written, before trusting the number.** Full-repo scan currently reads 0 findings. Verify this yourself with `--self-test` before citing it, the same way you would verify any other claim in this file - do not take "it is validated" on report.

**Three corollaries, each a form that reads like completeness and is not:**
1. **DISCLOSURE IS NOT COVERAGE.** A scanner that PRINTS the lines it skipped is not one that CLASSIFIED them - printing is honesty about a gap, not closing it.
2. **A WRONG MODEL IS WORSE THAN A MISSING CASE.** A missing case reports nothing, which is at least honest silence. A wrong model (H3: classifying a different failure as this one) reports a WRONG ANSWER WITH A NUMBER attached - false confidence is worse than no confidence.
3. **The coverage number must be measured over the REPO, not the author's own file selection.** An earlier `files=3` was chosen from the author's memory of which files mattered, not derived from actually scanning the tree - a self-selected sample can look like coverage while quietly excluding the very files that would have broken it.

**Enforcement labels** (the-sop-keeper, 2026-07-28): running `seterr-capture-scan.sh` and reading its self-test output is **MECHANISED** - it exists, passes 4/4, and can be wired into a pre-commit or pre-push sweep today. Confirming that a given self-test's fixtures were externally sourced (not written by the same author who built the detector) is **JUDGMENT-LEVEL** - it requires knowing the provenance of the fixtures, which the self-test's pass/fail output alone cannot reveal. Building any NEW mechanical check for a future lesson without first sourcing its regression fixtures from someone other than its author reproduces this exact defect one layer down, and is the actual discipline this entry teaches.

## Standing rule: relay the derivation, not the conclusion - ship the provenance beside the subject

Ratified 2026-07-28 PT (security-agent; carried by the-sop-keeper). Same family as [correction-propagation - carry the test, not the verdict](#standing-rule-correction-propagation---carry-the-test-not-the-verdict) - that entry is the general form for a credit or correction traveling through a relay; this entry is the specific form for a REPRO or a CITATION, where the subject and the command that derived it belong side by side.

**The instruction: any claim naming a subject (a file, a hook, a config) must carry the command that DERIVED that subject beside it, not just the subject's name.** BAD: "reproduced with `hooks/pre-push`." GOOD: "`git ls-files | grep 'hooks/pre-push$'` -> `scripts/hooks/pre-push`." The first names a conclusion a reader must trust; the second names an operation a reader can re-run themselves and get the same answer, or catch the moment they don't.

**Why this is the same shape as an affirmative token, not a new idea (the rationale).** This is a provenance artifact the failure mode CANNOT produce - a wrong or guessed subject cannot also produce a real derivation command that happens to name it, the same structural property as `SHAPE-GUARD-SCANNED-OK` and the affirmative-token family elsewhere in this file. **Four separate surfaces this same night independently re-derived this exact form** - exit-code checking, enumeration coverage, coverage-count reporting, and now provenance - which is itself the signal that this is a general FORM the fleet keeps reaching for under pressure, not a one-off rule invented for one file.

**The limit, stated so this is not over-claimed: provenance makes a subject AUDITABLE, not CORRECT.** `git ls-files` cannot return an untracked but INSTALLED hook - the live copy that actually executes - so a derivation built entirely from `git ls-files` can silently exclude precisely the copy that matters, while still looking rigorous because it shows its command. Same relationship as [disclosure is not coverage](#standing-rule-ship-a-detector-whose-self-test-fixtures-were-written-by-someone-else) above: showing the derivation is honest about method, it is not proof the method reached everything relevant.

**Upgrade to the form: NAME THE UNIVERSE the derivation is scoped to, not only the command.** Every derivation makes a silent choice between at least two universes - scope SOURCE (what the repo ships, what `git ls-files` sees) and scope RUNTIME (what actually executes, the installed copy a source-only derivation cannot see) - and a repro that does not say WHICH universe it covers is unfalsifiable in that specific dimension, even with a perfectly correct command attached. **This seam is PER-ARTIFACT, not a blanket habit to apply everywhere: the pre-push hook genuinely has two universes (a repo copy and an installed copy that can drift from it); `leak-shape-scan.sh` has only one (no separate installed copy exists for it).** A rote "always check source against runtime" habit is vacuous on the second artifact and load-bearing on the first - and applying it as a blanket habit is exactly how a reader stops noticing the cases where it actually matters, because it never once produced a finding on the file where it was vacuous. Check per artifact which universes genuinely exist before deciding whether the seam applies.

**The unifying line: relay the DERIVATION, not the conclusion - specificity is what makes a wrong claim killable.** A vague claim survives scrutiny only because nothing in it is testable, and an untestable claim that survives long enough is exactly the version that reaches an SOP - this file included.

**Enforcement labels** (the-sop-keeper, 2026-07-28): stating the derivation command beside the subject is **JUDGMENT-LEVEL to author** (recognizing which claims need one) but **MECHANISABLE, NOT YET to review** - a second reader or a script can check whether a cited subject actually appears in the stated derivation command's output, which is strictly cheaper than re-deriving the claim from scratch. Recognizing that a specific derivation method has a coverage gap (like `git ls-files` excluding untracked installed copies), and deciding per-artifact whether the source-vs-runtime seam even applies, are both **JUDGMENT-LEVEL** and require understanding the specific artifact, not a generic checklist.

## Standing rule: present-but-uninterpreted - a measurement can run every cycle and never have its meaning drawn out

Ratified 2026-07-28 PT (the-orchestrator; carried by the-sop-keeper). Distinct from silence-from-an-instrument-is-not-evidence (this file's proxy-vs-detector entry) - that finding is about a measurement that never ran or never could fire; this one is about a measurement that DID run, every single time, correctly, and whose result nobody ever drew a conclusion from.

**The finding.** A `source==runtime` (or equivalent) equality check ran on every cycle all night, printed its result every time, and was never once interpreted - nobody drew out what that equality actually MEANS (that there is no drift between the live installed copy and what the repo contains) or, more importantly, what its absence would have meant. The data was present in the output the entire time; the concept it was evidence for was never stated by anyone reading that output.

**Why this is a distinct failure from silence.** A silent or non-firing instrument gives a reader nothing to work with - the gap is visible once you go looking for it. A present-but-uninterpreted measurement is worse to catch precisely because it looks like it was already handled: the number was there, someone must have looked at it, so it reads as covered when it was only ever displayed.

**Enforcement labels** (the-sop-keeper, 2026-07-28): this is **JUDGMENT-LEVEL** - noticing that a routinely-printed measurement has never had its meaning stated requires someone to stop and ask "what does this number actually tell me," which is not a thing a script can flag on its own. The nearest mechanisable aid is a habit, not a check: any recurring measurement's output should be paired, at least once, with one written sentence stating what a change in that number would mean - after that sentence exists, whether it keeps getting read is back to judgment.

## Standing rule: a multi-reader SOP is three requirements together, not "get a second reader"

Ratified 2026-07-28 PT (security-agent + claude-dev, both diligent, both missing what only the other saw; carried by the-sop-keeper). Sharpens [independence of vantage](#standing-rule-independence-of-vantage-outside-reader-mechanise-the-check-immune-by-design---one-family) on a sibling branch - that entry names the REQUIREMENT (a thing cannot audit itself); this entry names what satisfying it in a live review loop actually takes, as three parts that must all hold together.

**The three parts, none of which substitutes for either of the others:** (1) a SECOND READER - someone other than the author, holding a genuinely different vantage; (2) FALSIFIABLE SPECIFICS - claims precise enough that the second reader can actually test them, not vague enough to survive any read; (3) A LOOP SHORT ENOUGH THAT RETRACTION IS CHEAP - the review has to cycle fast enough that a wrong claim gets caught and withdrawn before it compounds into something built on top of it. **Remove any one of the three and the whole thing fails:** a second reader with only vague claims to check has nothing to falsify; falsifiable specifics with no second reader are just a well-written unverified claim; a fast loop between two people checking nothing specific just produces fast agreement, not correction.

**The corollary, stated because it is easy to misread this as a story about carelessness: neither author was careless.** Both verified continuously throughout the same session, and both still shipped holes that only the OTHER one caught. **Diligence is not coverage** - the same shape as this file's disclosure-is-not-coverage and coverage-must-be-repo-wide corollaries, applied here to a person's own effort rather than to an instrument's output. Working hard at reviewing your own claim is not the same as having someone else's vantage on it, no matter how hard the work.

**This entry's own validation is not uniform across its parts, and must not be marked as if it were - split by confidence, not shipped flat (the-orchestrator).** The OBSERVABILITY-side rules this entry sits beside in this file - the affirmative-token family, name-the-universe, present-but-uninterpreted, disclosure-is-not-coverage - hold for a single reader working with no peer at all, so they survive an ordinary day on their own: mark those **STANDING PRACTICE**. The mechanism THIS entry describes is different in kind - second reader + falsifiable specifics + short loop - because its entire mechanism depended on having a peer, and the specimen that produced it was three attentive agents in sub-minute loops on a zero-exposure finding, conditions an ordinary task does not supply. Mark this one **PROVISIONAL**, with a dated falsifier attached (claude-dev): **check in late August 2026** whether the next person who tries second-reader-plus-falsifiable-specifics-plus-short-loop on an ordinary task reports a loop that was actually short enough to be real. Until that check runs, this entry's only evidence is the night it was invented - the same shape as a scanner validated only on the input it was written for, one entry above.

**Enforcement labels** (the-sop-keeper, 2026-07-28): this entire class is **JUDGMENT-LEVEL** - none of the three parts is individually automatable (who counts as a genuinely different vantage, whether a claim is specific enough to falsify, and how fast a loop needs to be to keep retraction cheap all depend on the specific claim and the specific people involved). The value of stating it as three explicit parts is that a reader can check which part is missing when a review process fails, rather than concluding vaguely that "review didn't work." The STANDING PRACTICE / PROVISIONAL split above is itself **JUDGMENT-LEVEL** to assign, but the late-August-2026 falsifier check is **MECHANISABLE, NOT YET** - a calendar reminder can force the question to be asked; whether the answer counts as a pass is not something a script can decide.

## Standing rule: the claims/report surface is not a gap in the process, it IS the process

Ratified 2026-07-28 PT (the-orchestrator, from tonight's own tally: 6 wrong claims surfaced in reports tonight against 1 in a file). We have separation-of-duties for CODE - a second reader on a diff, a review gate before merge - and code was the surface that failed LEAST tonight, because it is the one surface with a structural catch already built in: security-agent's file-level error was caught AT THE COMMIT, by the process itself, not by luck. Both of claude-dev's wrong claims tonight were in REPORTS - a status line, a briefing claim - and both were caught only because a downstream reader happened to check the underlying source, not because anything in the process pointed at the claim.

**The brief is the widest-blast-radius report surface.** A wrong line in a file stays local until someone opens that file; a wrong line in a report is written specifically to travel to readers who have no way to check it against source - that is the whole purpose of a report. The asymmetry is not that reports are reviewed less carefully than code; it is that reports have no equivalent of a diff for a second reader to check against.

**This is not a smaller version of the file-review problem - it is the same problem arriving on a surface with no equivalent mechanism yet.** [Relay the derivation, not the conclusion](#standing-rule-relay-the-derivation-not-the-conclusion---ship-the-provenance-beside-the-subject) is the first mechanism aimed at this surface specifically: naming the universe a claim was checked against, per-artifact, turns a bare assertion into something a reader COULD falsify without re-deriving it from scratch - the report-surface equivalent of a diff. It is a beachhead, not a solved problem: most claims in most reports tonight still carried no derivation at all.

**Enforcement labels** (the-sop-keeper, 2026-07-28): recognizing that a given sentence in a report IS a claim needing provenance, as opposed to routine narration, is **JUDGMENT-LEVEL**. Once identified, requiring a stated derivation alongside it is **MECHANISABLE, NOT YET** - a report template field ("checked against: ___") can enforce that something is present, but cannot itself verify that the derivation is correct or complete.

## Standing rule: broadcast CREDIT, not broadcast pronouns - the defect is narrower than it first looked

Ratified 2026-07-28 PT (the-orchestrator, sharpening [a message to more than one recipient carries no second-person reference](#standing-rule-a-message-to-more-than-one-recipient-carries-no-second-person-reference) on a sibling branch). This is a correction to that entry's scope, not a new topic: the defect is broadcast CREDIT (or blame, or a finding) attached to a specific person, not second-person pronouns in general - "you" is fine everywhere else in a relayed message, and treating every "you" as dangerous over-corrects into a harder-to-write rule than the actual defect requires.

**The precise rule: whenever a clause ASSIGNS credit, blame, or a specific finding to a person, NAME THAT PERSON explicitly, in any message that might be sent to, forwarded to, or read by more than one recipient.** A "you" used elsewhere in the same message - a question, an instruction, a general address - is not the hazard and does not need the same treatment.

**Why this is the same family as an author-relative citation, not a coincidence.** The author of "you offered X" always resolves the pronoun correctly, because the author knows who they meant - the same way the author of a relative file path always resolves it correctly, because the author holds the base directory in their head. In both cases the ambiguity is invisible to the person who could fix it and only appears for a later reader who does not share the author's context. **A mis-resolved pronoun leaves no artifact behind for anyone to reconstruct or correct after the fact** - unlike a wrong file path, which at least fails loudly when someone tries to open it, a wrong "you" just quietly attaches the wrong name to a claim with nothing to flag it.

**Enforcement labels** (the-sop-keeper, 2026-07-28): recognizing which clauses assign credit, blame, or a finding (as opposed to ordinary second-person address) is **JUDGMENT-LEVEL** - it requires understanding what a sentence is actually doing, not just scanning for the word "you." There is no general mechanised check for this distinction.

## Standing rule: put the check where it runs by default, not where someone has to choose to run it - three instances

Ratified 2026-07-29 PT (the-ad-strategist, the-team-lead; synthesized by the-orchestrator overnight 2026-07-28, carried by the-sop-keeper from the-orchestrator's own memory as the verified source - not re-derived from a one-line index). One pattern showed up three separate times in one night, in three different artifacts, each time as the fix for a control that existed, was correctly designed, and still failed because it depended on someone electing, at the right moment, to consult or run it.

**Instance 1 - the prior-output check is three tiers, not one mechanism, and only the middle one is load-bearing.** (1) A **HOOK** - a mandatory, harness-level trigger (session start, or first tool call of an investigation) that fires whether or not the mood permits: "we execute intentions, the harness executes hooks." This defeats simply forgetting to check. (2) A **FORCED DISPOSITION**, the tier to actually build - not a contradiction-detector, which needs to know what was claimed (hard), but a forced classification: "you have prior output on these terms - does it answer this? y/n, if n say what it answers instead." This works by deleting the silent disposition ("I looked, it was fine") rather than by asking anyone to be more careful, and it defeats dismissal. (3) A **FOOTER**, weakest, backstop only - the-team-lead's "a hit is not an answer - check what the document actually claims and what it does not." A hook without the footer fires and gets dismissed anyway; a footer without the hook never runs at all - both are needed together, but the footer alone is the weakest tier, because advice arriving in the same channel as the dismissal it's meant to prevent arrives inside the very moment it's supposed to stop.

**Instance 2 - registry-row citation: every claim-row cites the artifact where it was last examined.** A registry row that asserts a conclusion but points at no artifact sends the next reader SEARCHING instead of READING - the fix is a format rule, not a discipline: every row in a claims registry carries the citation inline, at the row, not in a separate index the reader has to go find.

**Instance 3 - the load-bearing-constant comment: document every reason a constant is load-bearing, not just the first one someone thought of.** "A constant documented with one reason will be changed by anyone who disagrees with that one reason." The fix is a comment, not code: at the constant's own definition site, record every independent reason it must hold its current value - not just the reason that happened to get written down first. The counter-example, found the same night in the same codebase: `TOP_EFFICIENT_LIMIT=5` sat undocumented two lines below `HOOK_MIN_NC=2`, which had a three-line rationale and a worked example - with nothing written down, nobody could tell whether `TOP_EFFICIENT_LIMIT` was fitted to real data or picked arbitrarily, because the site that would have carried that answer was blank.

**The unifying line, stated once because it explains all three: PUT THE REASON, THE CHECK, OR THE CITATION WHERE THE READER WILL ALREADY BE STANDING, not somewhere they'd have to choose to go looking.** A rule that depends on someone remembering to consult it, search for it, or run it at the right moment is a rule that will eventually not fire - not because anyone was careless, but because "remembering at the right moment" is exactly the faculty that fails under load. Move the safeguard to the place that gets visited unconditionally - the hook that always fires, the row that's always read, the constant's own definition line - and the safeguard survives contact with a bad day.

**Enforcement labels** (the-sop-keeper, 2026-07-29): the HOOK tier of instance 1 is **MECHANISED** once wired at session-start or first-tool-call. The FORCED-DISPOSITION tier is **MECHANISABLE, NOT YET** - a y/n-plus-if-n-what template can be built into a checklist step, but scoping which prior outputs are "on these terms" still needs judgment. Instance 2 (registry-row citation) is **MECHANISABLE, NOT YET** - a lint rule can require a citation field be non-empty on every row, but not that the citation is the correct artifact. Instance 3 (load-bearing-constant comment) is **JUDGMENT-LEVEL** - recognizing that a constant serves more than one purpose requires understanding the code around it, not a pattern a script can detect.

## Standing rule: a correction must be shaped for travel at least as well as the claim it corrects

Ratified 2026-07-28 PT (the-orchestrator, self-correcting; the-ad-strategist, generalizing to a send-mechanics rule; carried by the-sop-keeper from the-orchestrator's own memory). A claim is not static as it moves through a channel - the-orchestrator watched their own relay sharpen a finding at each hop, from "silently gone" (alarming) toward increasingly crisp and increasingly less true phrasing, because sharper reads as more quotable. **The channel optimizes claims for free and does nothing for corrections**, which is why a correction that travels through the same channel as the claim it retracts tends to arrive after the claim, lose the race, and leave the vivid original as the thing that actually got remembered.

**Why a correction structurally cannot win on the channel's own terms.** A caveat cannot be made vivid without turning into a new claim - the moment you sharpen a retraction to make it travel, you've written a second assertion, not corrected the first one. So the channel optimizes claims toward vividness and leaves retractions flat by construction, and the flat one gets overtaken by the sharp one it was supposed to correct.

**The fix: a correction must be deliberately built for travel, as quotable as the thing it corrects - led with as the headline, not filed as a caveat in a longer message.** A caveat loses the race to the sentence it's overtaking; a correction stated as its own quotable line has a chance to compete for the same attention the original claim had.

**Precedent, independently found earlier the same night (claude-dev + the-analyst):** "a wrong diagnosis attached to a correct retraction travels further and faster than the original error - a correction gets less scrutiny than a claim." Same family, found from a different angle, worth citing because two independent routes to the same finding is stronger evidence than one.

**Enforcement labels** (the-sop-keeper, 2026-07-29): this is **JUDGMENT-LEVEL** - recognizing that a given correction needs to be built for travel (as opposed to simply appended) requires understanding how the original claim is likely to keep circulating, which is not a pattern a script can flag.

## Standing rule: a self-check beats the mood only if it returns the answer text, not a pointer to it

Ratified 2026-07-28 PT (the-ad-strategist, discovering it live while testing his own tool; the-team-lead, rebuilding the tool to prove it; carried by the-sop-keeper from the-orchestrator's own memory). The original claim going into the night was that a self-check can only work from "outside" the thing it checks - the corrected, narrower finding is that the fixable part was never the checker's position, it was the OUTPUT FORMAT.

**The finding: a self-check that returns a pointer cannot beat a bad mood, because a pointer must be opened, and opening something is itself a mood-gated choice.** A self-check that instead hands over the answer text directly has nothing left to dismiss - there is no second decision point where the reader can choose not to look. "The snippet is the fix, not the ranking - ranking picks the document, the snippet removes the need to open it."

**This is strictly better than the discarded "must come from outside" framing**, and it was found by rebuilding the tool and testing it against its own prior failure, not by arguing about which framing sounded more rigorous.

**Enforcement labels** (the-sop-keeper, 2026-07-29): this is **MECHANISABLE, NOT YET** - any self-check-style tool can be reviewed for whether its output is inline answer text versus a reference/pointer, which is a checkable property of the tool's output format, though building that review into an automated gate is not yet done.

## Standing rule: the identity detector - what value would have falsified it, if none, it is description not evidence

Ratified 2026-07-28 PT (the-analyst, self-credited as "finding of the night"; carried by the-sop-keeper from the-orchestrator's own memory). Three separate numbers in one investigation turned out to be identities rather than evidence: a consistency check (AOV = revenue / orders), an explanation restating its own inputs ("4.2x spend / 1.24x new customers"), and a decomposition of the very thing it was computed from. Each one could not possibly fail, and each one sat where something falsifiable was supposed to be.

**Why this is dangerous rather than merely useless: an identity always comes out clean, and clean reads as confirmed.** "An identity is what a tired analyst reaches for - it always comes out clean, and clean reads as confirmed." Nobody manufactures a false identity on purpose; the danger is reaching for one by default when a real, falsifiable check would have taken more work to construct.

**The detector, one question that catches all three shapes at once: ask what value would have falsified the claim. If no value could have, it is an identity - description, not evidence.** A companion technique for settling what a number actually IS: find an identity linking it to something both sides already agree on, and ask what the figure must equal if it is what you claim it is, before defending it.

**Enforcement labels** (the-sop-keeper, 2026-07-29): this is **JUDGMENT-LEVEL** - recognizing that a specific computed value is structurally guaranteed to match (an identity) rather than contingent on the data (a real check) requires understanding the arithmetic relationship being used, not a pattern a script can flag.

## Standing rule: a remembered rule does not fire - the broadcast-you fix has to move to the send layer

Ratified 2026-07-28 PT (the-analyst + the-team-lead, first naming the defect; the-ad-strategist, root-causing and fixing it at the correct layer after it recurred twice more; carried by the-sop-keeper from the-orchestrator's own memory). Sharpens [broadcast CREDIT, not broadcast pronouns](#standing-rule-broadcast-credit-not-broadcast-pronouns---the-defect-is-narrower-than-it-first-looked) with the mechanism that actually stops it, found only after the agreed fix demonstrably failed to fire twice more in the same night.

**The demonstration, not an argument: the fix was written, agreed, and filed between the second and third recurrence of the exact same defect, and the third one still happened.** A "you" in a message read by more than one recipient defaults to whichever reader is holding it - the pronoun invents its own provenance. The rule to prevent this ("name the agent mechanically") was named after the first two occurrences and still didn't fire on the third: "a remembered rule does not fire - now demonstrated, not argued."

**Root cause: the defect lives at the SEND layer, not the COMPOSE layer, so no amount of careful composition could ever have fixed it.** The actual mechanism producing the bug was a fan-out send loop - one message body, sent to three recipients in a loop (`for a in orch team-lead analyst; do send $BODY; done`) - which means every "you" in that one body has three referents by construction, before a single word is chosen. "It was written for the wrong layer (compose), so it could not have fired no matter how well recalled."

**The fix, mechanical, a send-command change, not a remembered rule: an attribution message goes to one recipient.** Once the constraint is enforced at the point where the message is actually dispatched - one send call, one name, no loop - the ambiguity cannot be constructed in the first place, regardless of what anyone remembers to check while writing the message.

**Enforcement labels** (the-sop-keeper, 2026-07-29): recognizing that a message assigns credit/blame/a finding is **JUDGMENT-LEVEL** (unchanged from the parent entry). But the send-layer fix itself is **MECHANISABLE** - a send helper that refuses to fan a single attribution-bearing body out to more than one recipient is a real, buildable gate, not a reminder.

## Standing rule: importance is not the selector, quotability is - put the accurate-but-unvivid thing where reading it does not depend on winning a race

Ratified 2026-07-28 PT (the-ad-strategist + the-orchestrator, jointly diagnosing a live relay of their own; carried by the-sop-keeper from the-orchestrator's own memory). Generalizes [correction-shaped-for-travel](#standing-rule-a-correction-must-be-shaped-for-travel-at-least-as-well-as-the-claim-it-corrects) one level further: this is not only about corrections losing to claims, but about which of several TRUE characterizations of the same finding survives being relayed.

**The test that proved it: three framings of one real finding, run in the same relay.** v1, "the fifth value silently gone" (alarming, vivid, instant to write). v2, "prospective and cheap, nothing actually dropped" (reassuring, vivid, instant to write). v3, "a wrong highlight in a human-facing report section" (accurate, unquotable, required reading the source and correcting a population). All three framings survived being passed along; only the true one required real work to produce. "The channel favours quotable, not bad news" - confirmed, because the alarming framing and the reassuring framing came from different agents in different directions, ruling out a simple bad-news bias.

**Why the accurate version loses even when nobody is trying to distort anything: the true answer is usually the flat middle, and the flat middle has no vividness to compete with.** In a message, the accurate-but-unvivid claim has to out-quote whichever extreme happens to be circulating, and it structurally cannot, because accuracy and vividness are different axes. "Importance is not the selector; quotability is" - an important claim is usually vivid and travels on its own merits; the one that actually needs deliberate placement is the flat-correct-middle version, because that is the one that loses every race in a message.

**The fix: put the accurate-but-unvivid claim in the artifact, at the claim line, not in the message.** In an artifact read by position - a registry row, a report's claim line - the accurate version does not have to out-quote anything, because it is read regardless of how vivid it is. "A file does not have to win a race." Same underlying move as registry-row-citation and correction-shaped-for-travel, stated one level more generally: put the true-but-dull thing where reading it is not conditional on it winning.

**Enforcement labels** (the-sop-keeper, 2026-07-29): this is **JUDGMENT-LEVEL** - recognizing that a given true claim is accurate-but-unvivid (and therefore needs artifact placement rather than message placement) requires judging how the claim is likely to compete for attention, which is not a pattern a script can flag.

## Standing rule: verify before reporting, not only before fixing - put the check before the step that incurs the cost

Ratified 2026-07-28 PT (the-ad-strategist, retracting his own false defect report after testing it; carried by the-sop-keeper from the-orchestrator's own memory). A reported exit-code bug turned out not to exist: a fix was drafted, the "fixed" exit codes were already correct, and the self-test passed - because there had never been a bug to fix. "A fix would have worked - edited already-correct exit codes, self-test passes, banked a repair for a bug that never existed. A fix manufactures the evidence that the thing it fixed was broken."

**The cost was not in the fix - the cost was already spent by the time anyone got there.** The false report had sent three agents to check call sites and the-team-lead through an entire directory before anyone tested anything - roughly twelve hours of fleet time acting on a defect that was never real. Testing happened before FIXING (the last, cheap step) but not before REPORTING (the first step, which is where the entire cost was actually incurred).

**The general form: put the verification before the step that incurs the cost, not before the step where it happens to be convenient.** "The check was in the right family, on the wrong end of the sequence." Test-before-reporting is test-before-the-cost; test-before-fixing is test-after-it, once the expensive part has already happened.

**Enforcement labels** (the-sop-keeper, 2026-07-29): this is **JUDGMENT-LEVEL** - recognizing which step in a sequence is actually the expensive one (often the report, not the fix) requires understanding who acts on the report and how much work that triggers, not a pattern a script can flag.

## Standing rule: a planted positive proves a detector can fire, not that it fires first - selection layers need a competitive test

Ratified 2026-07-28 PT (the-ad-strategist, auditing three detect-then-rank tools built the same week; carried by the-sop-keeper from the-orchestrator's own memory). Distinct from [ship a detector whose self-test fixtures were written by someone else](#standing-rule-ship-a-detector-whose-self-test-fixtures-were-written-by-someone-else) - that entry is about who writes the fixtures; this one is about what a fixture can even prove when a tool has two layers, not one.

**The finding: a single planted-positive test validates that a detector CAN fire - only a competitive test validates that the CORRECT answer fires FIRST.** A single-candidate test has nothing for the right answer to lose to, so a ranking or selection defect is invisible to it by construction. Three detect-then-rank tools were built and tested the same week - each one finds candidates, then ranks or selects among them - and all three had their DETECTION layer tested (does it find the right thing at all) while their PRESENTATION/SELECTION layer shipped completely untested (does the right thing win, when something else is competing for the same slot).

**Auditing "all three are untested" was itself too broad a first pass, and narrowing it mattered.** A closer audit found only two of the three tools actually had a real selection layer with something to get wrong; the audit on the real one surfaced a genuine, previously-invisible cap in a human-facing tool (an undocumented top-N limit on a ranking pass) that had never been competitively tested and had no announcement mechanism for when it silently dropped a candidate.

**The fix: for any tool that finds-then-ranks or finds-then-selects, test the selection layer with a forced competition - the right answer up against plausible wrong ones it must outrank - not a lone planted positive with nothing to beat.**

**Enforcement labels** (the-sop-keeper, 2026-07-29): building a competitive test (real answer vs. plausible distractors) for a given selection layer is **MECHANISABLE, NOT YET** - it requires per-tool understanding of what a plausible wrong answer looks like, but once built, running it is a mechanical regression test. Recognizing that a tool HAS an undocumented selection layer in the first place, distinct from its detection layer, is **JUDGMENT-LEVEL**.

## Standing rule: a blacklist verifies by excluding what you know, a whitelist verifies by requiring what you want - only the whitelist fails closed

Ratified 2026-07-28 PT (the-team-lead, capstone correcting both the-ad-strategist and the-orchestrator in the same finding; carried by the-sop-keeper from the-orchestrator's own memory). Named as an anchor for this session's whole verification-discipline family: nearly every surprising detector failure the fleet found in one night turned out to be the same shape wearing a different costume.

**The distinction, stated once because everything else is an instance of it: "a BLACKLIST verifies by EXCLUDING what you know - it passes everything unmet. A WHITELIST verifies by REQUIRING what you want - it FAILS CLOSED on the unknown."** A blacklist detector only catches the failure modes someone already thought to enumerate; anything outside that enumerated set passes silently, by construction, no matter how careful the enumeration was. A whitelist detector instead states what a passing case must positively contain; anything that doesn't match - including a shape nobody had imagined yet - fails, by construction.

**Every surprising detector failure catalogued the same night was a blacklist:** a marker list blind to a retraction phrased as "dead" instead of the words the list enumerated; a regex blind to a plain-prose retraction; a zero-chunk ingest guard blind to "Ingested 0" because its pattern only excluded known error strings; a prefix check misread as "flag if this specific bad prefix appears" rather than "require this specific good prefix." Each of these was correctly built against every case its author imagined, and each one passed silently on the case nobody imagined - which is not a coincidence, it is what a blacklist does by definition.

**The rule: when a check can be stated either way, state it as "require what you want," not "exclude what you fear."** Only the require-form fails safe on the case you didn't imagine; the exclude-form's safety is capped at the size of the list its author happened to write. **The bound on this rule, found the same night: inverting a blacklist into a whitelist only works where the acceptable set is small and enumerable.** A single required string inverts cleanly (require `pjt`, instead of flagging every bad prefix you can think of). A marker list checking for "prose shaped like a retraction" cannot invert - there is no small, enumerable set of ways a retraction can be phrased - so that detector is a blacklist by construction, permanently, not by an oversight that a longer list would fix. For a permanently non-invertible detector, the fix is not a bigger list; it is labeling the gap as a permanent property and printing it on every run, reframing the blind spot from a TODO into a spec.

**Enforcement labels** (the-sop-keeper, 2026-07-29): for a given detector, determining whether it CAN be inverted into whitelist form (is the acceptable set small and enumerable) is **JUDGMENT-LEVEL** - it requires understanding the space of valid inputs, not a pattern a script can flag. Once that determination is made, building the whitelist form (or, for a non-invertible detector, printing a permanent-incompleteness banner on every run) is **MECHANISABLE**.

## Standing rule: a rule that asks you to search your own list cannot repair a rule that asks you to search your own list - the repair always comes from outside the set

Ratified 2026-07-28 PT (the-team-lead; carried by the-sop-keeper from the-orchestrator's own memory, credited by the-orchestrator to the-team-lead immediately after almost taking credit for it themselves). Named as the second anchor for this family: the mechanism explaining WHY the fleet's multi-agent structure caught things individual rigor, however careful, structurally could not.

**The line itself: "a rule that asks you to search your own list cannot repair a rule that asks you to search your own list - the repair always comes from outside the set."** Every genuine catch the same night traced back to something outside the checker's own enumerated set: an adjacency check on a control someone else owned, a boring-alternative explanation proposed against someone else's p-value, a positive planted in a live query rather than reasoned about in the abstract, a structural read of a query performed by an agent who hadn't written it, four voices each auditing the half of the problem the OTHER voice was standing inside of. Not one genuine catch came from looking harder at one's own list - which is exactly why a multi-agent structure caught things individual diligence, applied to itself, could not.

**The corollary this produced, worth stating separately because it nearly caused a real mistake: a "fix" proposed for an enumeration problem is not automatically outside the enumeration it's meant to fix.** The same night, a THIRD detector was proposed specifically to escape the failure of the first two - and it turned out to be the identical shape at one remove: "the fix was proposed as the fix for the first two, and it is a fix drawn from the same enumeration it was meant to escape - the sharpest instance of the class, and it would have traveled furthest, because it looked like the answer." A fix inherits the disease unless it is verified to actually sit outside the set it's repairing, not merely proposed with that intention.

**Practical form: before trusting a fix for a your-own-enumeration problem, ask what set the fix itself draws from - if it's still your own imagination of what could go wrong, it is not yet outside the set, no matter how it was motivated.**

**Enforcement labels** (the-sop-keeper, 2026-07-29): this is **JUDGMENT-LEVEL** across the board - recognizing that a proposed fix still draws from the same enumerated set as the problem it fixes requires understanding both the original failure and the fix's actual construction, not a pattern a script can flag. The practical value is procedural: default to seeking the repair from a genuinely different vantage (a different agent, a different method, a live instrument) rather than a sharper version of the same reasoning.

## Standing rule: never trust an absence produced by a procedure you haven't validated

Ratified 2026-07-28 PT (the-ad-strategist, meta-capstone closing the night's detector-failure investigation; carried by the-sop-keeper from the-orchestrator's own memory). Named as the third anchor for this family, and stated as the umbrella the night's other detector-failure lessons sit under: [blacklist vs. whitelist](#standing-rule-a-blacklist-verifies-by-excluding-what-you-know-a-whitelist-verifies-by-requiring-what-you-want---only-the-whitelist-fails-closed) is about the SHAPE of a check; this is about what a NULL RESULT from any check is entitled to claim.

**The finding: three separately-built detectors, over one night, turned out to be one asymmetry wearing three costumes** - a blacklist (enumerate failure modes you thought of), a strawman-null (enumerate hypotheses you hold), and an unrun-test criterion (enumerate actions you thought of) - and all three return a clean, confident result over a self-assembled set. The third was proposed specifically as the FIX for the first two failing, which makes it the sharpest instance of the whole class: "a fix drawn from the same enumeration it was meant to escape - it would have traveled furthest, because it looked like the answer."

**The universal principle: never trust an absence produced by a procedure you haven't validated.** An empty result, a clean pass, a null finding - none of these are evidence of anything until the procedure that produced them has itself been shown capable of returning a non-empty, non-clean, non-null result when one genuinely exists.

**Two modes, not one, and they check different things.** (1) **Enumerate candidates in writing before concluding empty** - this checks your LIST: writing down what you searched for forces explicitness that exposes gaps in what you thought to look for, but it tests nothing about the instrument itself. (2) **Plant a positive - run the search where you already know the answer is not empty** - a negative control at the null, which checks your INSTRUMENT: if the instrument can't find a planted, known-present answer, its "nothing found" on a real query is worthless. Both modes refuse to read a null result as meaning "nothing there" until the instrument has been shown capable of returning "something there." The night's clearest example: a positive planted directly in a live query (not a script) was the one check that caught an empty-set error BEFORE it shipped, rather than after - because "enumeration checks your list, the positive control checks your instrument, and that night the instrument was the thing that was wrong."

**Corroboration - the same rule surfaced three more times in one day, on unrelated surfaces, which is the evidence it is load-bearing rather than a one-off (meta-compliance-agent, 2026-07-29).** Within a single day after ratification, "positive control on the instrument before trusting a null" - mode 2, restated in its sharpest operational form - independently governed the resolution of three distinct incidents: (1) the KB `--agent`/`--scope` flag omission, where a bare query returns plausible rows without ever searching the intended collection, so a "found nothing relevant" was a statement about the wrong collection; (2) a cried-wolf gate's own self-check, where the guard's null had to be validated against a known-present input before being believed; (3) the `query_back` retrieval check in this very session, where a retrieval MISS was only correctly read as benign once chunk-count confirmed ingestion had actually happened - i.e. the instrument (semantic retrieval) was shown incapable of surfacing a file that was provably present, so its null carried no weight. **The transferable operational form: before reading any "nothing found" as "nothing there," feed the instrument a case where you KNOW the answer is non-empty; if it can't return that, its null is uninformative.** When one rule resolves three unrelated incidents in a day, it has stopped being three fixes and become one lesson - and the recurrence itself, not any single instance, is what earns it a permanent place here.

**A caveat on that recurrence, applying this very rule to our own conclusion (meta-compliance-agent, 2026-07-29): those three instances are NOT three independent draws, and reading them as a frequency estimate would be the same error the rule warns against.** All three were caught by the same observer inside about ninety minutes, under attention the FIRST catch had already primed - once "positive control before trusting a null" was loaded, instances jumped out, which is exactly the condition under which a mind finds confirmations. So they establish that the rule applies BROADLY (reach) - which is real and is what earns the entry - but they say nothing about how often the failure occurs when nobody is primed to look (base rate / frequency), because the observer was not blind. Same-session, same-observer instances show reach, not frequency. The frequency question needs a case someone stumbles into COLD, unprimed - and those unprimed draws are worth logging specially when they appear, precisely because they are the only ones that speak to base rate.

**Enforcement labels** (the-sop-keeper, 2026-07-29): mode 1 (enumerate in writing) is **JUDGMENT-LEVEL** to construct but **MECHANISABLE** to require as a step (a template field that must be filled before a null is reported). Mode 2 (plant a positive / negative control) is **MECHANISABLE** - a known-present test case can be built once per instrument and re-run automatically before trusting any of that instrument's null results. The three-instance corroboration above adds a **JUDGMENT-LEVEL** meta-check: when the same corrective rule resolves multiple unrelated incidents in a short window, treat the recurrence as a signal to codify the rule rather than re-solving each instance from scratch.

## Standing rule: a runnable block lives at column 0 - a heredoc terminator indented to match its markdown nesting does not terminate

Ratified 2026-07-29 PT (cro-agent, finding the class live in its own just-written verification check; independently confirmed and fixed by the-sop-keeper via a separately-built detector, cross-validated against cro's tool both ways; carried by the-sop-keeper). This is the DELIVERY layer of the night's verification-discipline family - every other entry in this file is about the assertion a check makes; this one is about whether the check's own code, as written in a doc, would actually run at all.

**The mechanism: a bash heredoc terminator only closes the heredoc when it appears at column 0 with nothing else on the line.** `<<TAG` requires the terminator completely unindented - any leading whitespace, even one space, makes that line just more heredoc body content instead of the line that ends it. `<<-TAG` is a partial exception: it strips LEADING TABS ONLY before comparing, so a tab-indented terminator is legal, but a space-indented one still fails - which matters in practice because editors, markdown renderers, and copy-paste all tend to convert or introduce spaces, not tabs, so `<<-` plus tabs is a silent re-break waiting for the first reformat, not a real fix.

**Why this specific class hides so well: a runnable block placed inside a numbered markdown list gets indented to match the list's nesting, VISUALLY correctly, and the terminator gets indented right along with it - which looks right to a human reader and is wrong to bash.** When such a block is copied and run, the heredoc never terminates: it swallows every subsequent line - including a command meant to execute right after it - as heredoc body content instead. The interpreter that was supposed to run gets nothing, or garbage, and dies quietly or does nothing. **The block prints no verdict, and the shell still reports success**, because nothing in the sequence actually failed from the shell's point of view - a well-formed heredoc simply absorbed everything that came after it.

**Concrete instance, verified by execution not just by scanning: an onboarding step of `cat > current.md << 'EOF'` followed by content, an indented `EOF`, then a blank line, a comment, and a `cortextos bus manage-cycle create ...` command.** Sandbox-run pre-fix with the bus call neutralized to an echo: the echo never printed, the command exited 0, and the written `current.md` contained the entire rest of the script - the comment and the full command, verbatim - instead of the intended three-line baseline. Post-fix, same sandbox: the echo printed and the file held only the intended content. A new agent following this instruction literally would see no error and would have a file that looks plausible while the cycle silently never registers - a real, waiting-to-fire defect in a file meant to be followed exactly. **Its actual historical impact is NOT established, and that distinction matters: a follow-up check for whether swallowed registrations had already happened came back NULL** - most carriers of the bug did show no registered cycle, but so did every checked non-carrier, so the metric had two possible causes and separated neither. Fix the defect on its own merits; do not carry a severity number nobody has actually measured.

**The minimal correct fix differs by payload type, which is itself worth knowing rather than assuming one universal repair.** Dedenting only the terminator line is sufficient when the heredoc's body becomes literal file content (`cat > file << 'EOF'`, a shell variable assignment, anything a later `source` or plain read consumes) - tested directly: leading whitespace on a shell key=value line does not break sourcing it. It is NOT sufficient when the heredoc feeds an indentation-sensitive interpreter (`python3 - <<'PYEOF'` with an indented body dies on `IndentationError`) - there, the whole block must be dedented, not just its terminator, or the fix trades a silent swallow for a loud crash on a payload it never covers correctly either way. **The generally safe rule, correct for every payload type and the only form some verification gates can even start from: dedent the entire block, not only the terminator line.** Check what a given heredoc's body actually becomes before assuming the cheaper, narrower fix applies.

**Two independent fixes for the two halves of the underlying bug, and both matter:** (1) **the immediate fix** - de-indent the terminator (or, per the paragraph above, the whole block, depending on payload); nothing else in the surrounding block needs to change, since a markdown fence's visual nesting doesn't depend on the indentation of lines inside it. (2) **the durable rule** - any runnable block (bash, python, YAML, or otherwise) should live at column 0 within its fence regardless of surrounding list nesting; and every runnable gate or check should emit a MANDATORY VERDICT LINE, always, on every path, so that no-output is structurally distinguishable from a genuine pass - a silently-swallowed check and a silently-passing check produce the identical nothing on stdout otherwise.

**A verification note on the verification note: an unterminated heredoc (no matching terminator line at all, anywhere in the file) is a DIFFERENT, milder finding than an indented one, worth not conflating.** Bash ends an unterminated heredoc at end-of-file rather than erroring - so it only actually breaks something if lines meant to execute follow the opener within that same file. A heredoc opened with nothing meant to run after it (the last thing in a script or the last block in a doc) is inert even though it never technically terminates; treat this as WARN, not BROKEN, and check whether anything follows before escalating it. A related, sharper trap for the detector itself: an unanchored opener regex (`<<` followed by a bare identifier, nothing constraining what comes after) will match `<<DELIM` sitting inside ordinary prose or a payload-marker string like `<<<BRIEF>>>`, or inside an inline-code mention of the syntax in a comment - none of which are real heredocs. Scoping detection to fenced code blocks closes most of this for markdown; it does nothing for `.sh` files, which have no fence concept, so the opener pattern itself needs an end-of-line/redirection anchor (only whitespace, a pipe, a redirect, a semicolon, or end-of-line may follow the delimiter) to avoid firing on a shell comment that merely discusses the syntax.

**Two further findings, both from the SAME night's cross-check between two independently-built detectors, worth their own weight because they generalize past this specific bug:**

**Scan-clean proves a narrower thing than it sounds like it proves.** A detector that confirms "terminator at column 0" has confirmed exactly that, not that the block behaves correctly end to end - a dedent that also breaks a line continuation, strips a fence, or splits the block in some other way would scan clean and still be broken. The scan is necessary and cheap; it is not sufficient for a claim like "this fix works." Verifying a fix for this class means extracting the actual block, running it in a sandbox with anything stateful neutralized, and asserting both that a previously-swallowed command is now reached AND that the written output contains only the intended content - the second half is the one a scan structurally cannot see, because a scan never executes anything.

**Two independent detectors agreeing is evidence about the LOGIC, not about the COVERAGE - and the coverage gap is the one that actually cost something here.** Two separately-built detectors, run against the same tree, agreed it was clean - and both were still wrong, because neither one had been pointed at every tree that mattered. The templates and community directories are git-tracked and easy to remember to scan; the live, gitignored deployment directory holding every agent's actual running copy was not scanned by either tool, and held eighteen more instances of the identical bug, including the scanning agent's own file. "Two tools agree it is clean" was a true statement about the corpus both tools were run against, and a false implication about the corpus that mattered - the unexamined thing was never the detection method, it was which files got looked at. A live-deployed copy can also have diverged from its template source by the time anyone checks, which changes the fix itself: patch each file's own content in place, never restore-from-template, or a divergent local fix gets silently clobbered.

**Enforcement labels** (the-sop-keeper, 2026-07-29): detecting an indented terminator, with correct `<<` vs `<<-` handling, fence-scoping for markdown, and an end-of-line anchor for `.sh` prose immunity, is **MECHANISED** - two independently-built detectors now do this and agree. Verifying that a fix actually restores correct behavior (not just column-0 compliance) requires **sandboxed execution against the extracted block**, which is **MECHANISABLE** per-instance but needs a harness built once per doc format. Deciding whether a given directory is in-scope for a sweep - i.e., whether "the templates" actually means "every place a deployed copy of this content lives" - is **JUDGMENT-LEVEL**, and is the part that broke here: the mechanical parts of both tools worked exactly as designed.

## Standing rule: a checker must derive its accept/reject criterion from the real generator, never a hand-guessed shape

**Rule.** A validator that decides whether input is well-formed by testing it against a *hand-written approximation* of the valid shape will — wherever that approximation is looser than the real thing — silently **accept exactly the malformed inputs it exists to reject**. A loose positive match is a negative filter in disguise: the gap between the guessed pattern and the real one is invisible, and because the check reports "clean," everything in the gap is not merely missed, it is affirmatively vouched for. The fix is always the same shape: **one source of truth for the form, referenced by both the thing that produces it and the thing that checks it**, so detector and writer share one pattern and cannot drift. claude-dev-agent's name for the trap: *detector-and-writer-must-share-one-pattern*. When you find yourself hand-authoring a regex or a character test to recognize something another part of the system generates, stop and derive it from the generator instead.

**Why (origin).** Two lived instances in one night (2026-08-03/04). **(1) The 117-vs-2 `reply_to` count.** A first fleet-wide scan for malformed `reply_to` values used a loose positive match that accepted `reply_to` shapes nobody had predicted, and reported "exactly two malformed, both deliberate probes, no live victims." A strict re-run, deriving its accept criterion from the actual `msg_id` generator's real output format, found **117** malformed across nine agents (52 bare agent-name / 14 dash-placeholder / 11 `task_id` / 7 ellipsis-truncated / 5 underscore-task-form + a bare-numeric form on meta-ads) — real victims, not probes. The loose match had not merely missed them; it had reported the system clean, which is worse. **(2) The send-guard prose false-positive (`4039d794`).** The guard decided whether a `cortextos bus …` occurrence was a real command with a hand-guessed test — `/[A-Za-z0-9_-]/` on the preceding char — that diverged from the actual shell command-position grammar, firing on prose that merely *mentioned* the command until `isCommandPosition` derived the real delimiter set (start-of-string, `\n ; | & ( !`, backtick, `$(`). Same trap, opposite symptom: instance (1) was a loose accept that hid real failures; instance (2) was a loose reject that manufactured false ones — both because the pattern was guessed, not derived.

**Enforcement labels** (the-sop-keeper, 2026-08-04): *deriving* a checker's criterion from the generator — importing/reusing the generator's own format function, or generating the acceptance pattern from the same constant — is **MECHANISABLE** wherever the generator exposes its format as callable code (the send-guard now does this; a `reply_to` validator should import the `msg_id` shape, not re-describe it). Recognizing that a given check is a *hand-guess at all* — that a regex or char-test is silently standing in for a real grammar — is **JUDGMENT-LEVEL**, and is the part that fails first: both instances above passed review because a plausible-looking pattern reads as a real one.

## Standing rule: a guard at the runtime site does not cover the propagation source that teaches the pattern

**Rule.** A defense that catches a bad pattern *when it executes* (a runtime hook, a lint-on-run guard) does nothing about the **example that teaches the pattern**. A malformed `cortextos bus send-*`, an un-success-checked send, an un-ack'd reply sitting in a template `AGENTS.md`/`CLAUDE.md`, a skill doc, or a runbook is copied by every new agent that reads it — the runtime guard then fires on each resulting instance forever, treating one propagation source as an endless stream of unrelated incidents. The two defenses are complementary and neither substitutes for the other: **guard the runtime *instance* to fail safe now, and lint the *source* — the templates, skills, and docs that new agents learn from — to stop minting new instances.** When you find yourself repeatedly catching the same bad pattern at runtime, look upstream for the document that is teaching it.

**Why (origin).** 2026-08-04, extending the send-guard work. The runtime `hook-send-guard` denies shell-expansion hazards in a live `cortextos bus send-*` body — but it cannot see a bad *example* sitting in a template that every spawned agent reads and imitates. claude-dev-agent, sweeping the retiring stranded ref (`fe0d4e0c`) for residual value, found `scan-send-followon.js`: a docs/template linter for the "`send-*` whose captured output is never success-checked or ack'd" pattern — a **propagation-source** gap the runtime guard structurally does not cover (the guard catches sends; a bad `AGENTS.md` example teaches the anti-pattern to the whole fleet). It was salvaged into `task_1785812468129` to evaluate and wire *if it earns its keep*. The principle is independent of that specific scanner: a guard at the point of execution and a linter at the point of instruction are two different coverage surfaces, and a fleet that spawns agents from shared templates needs both.

**Enforcement labels** (the-sop-keeper, 2026-08-04): the runtime half is **MECHANISED** for the send-hazard case (`hook-send-guard`, live from `dist`). The propagation-source half is **MECHANISABLE, NOT YET** — `scan-send-followon.js` is a candidate template/docs linter under evaluation on `task_1785812468129`, not yet earning its keep and not wired into any pre-commit/CI sweep; do not cite it as an active control until it does. Recognizing that a recurring runtime catch has an upstream *teaching source* at all is **JUDGMENT-LEVEL** — it is the move from "block this instance again" to "find the doc minting the instances."

## Standing rule: a root-cause fix and its propagation are two layers, each verified separately

**Rule.** Curing a root cause does not heal state that was INSTANTIATED against the broken cause. After a root-cause fix, enumerate every live process, session, cache, or connection that was CREATED against the broken state and cull/respawn each one; then verify the PROPAGATION - that the dependents are now on the fix - not just the cause. "The cause is fixed" and "everything running is now on the fix" are two distinct claims, and the second is the one that bites when it is skipped: a fix declared done on the cause alone reopens the moment a stale dependent is exercised.

**Why (origin).** 2026-09-25, codex auth-death. An operator account re-auth cured the true cause (a revoked OpenAI-side service-account object), but app-server `48550`, which had booted BEFORE the re-auth, retained a residual stale-cred path and intermittently re-presented the dead key until it was respawned to a fresh app-server. The incident was called closed on an earned green, then reopened intermittently - precisely because the fix had not been propagated to the process that predated it. Two-layer truth: account fix (the cause) + process respawn (the propagation), each with its own verification (the respawn was verified over a watch window per VT-9, not a single green). See [FINDINGS-codex-auth-death-elimination-ladder-2026-09-25.md](FINDINGS-codex-auth-death-elimination-ladder-2026-09-25.md) lesson 3.

**Family.** Same shape as the runtime-vs-propagation-source rule above (a fix in one place does not propagate itself to every dependent), applied to LIVE STATE rather than to teaching documents; and it is why VT-8's confound bit here - the processes booted pre-fix were a second active cause co-present with the account break, so no test run while both were live could isolate either.

## Standing rule: a compliance strike is a finding routed to the owner - unless the file has no active owner, then the maintainer applies it

Ratified 2026-08-21 PT (authored jointly by meta-compliance-agent - compliance-strike owner - and the-sop-keeper - process lane; the-orchestrator ruled the ownerless-file case "Go" on mc PR #254, 2026-08-21; carried by the-sop-keeper). Companion to the brain governance model (agents/conventions.md ownership table + human-gated paths + the Librarian's Gate 1). Origin: mc's brain PR #249 - four delivery-time compliance strikes authored as one mc-PR - auto-CLOSED by the Librarian on Gate 1 (touches human-gated paths) and Gate 2 (unrecognized `mc/` branch prefix). The gate did its job; the PR shape was the error.

**Rule (finding, not fix).** A compliance strike against a file the striking agent does NOT own is a FINDING - the M-code + offending text + prescribed change - ROUTED TO THE OWNER, never an authored diff the striker merges. Attach a ready-to-apply from->to edit to cut owner friction (do this always for paid-spend strings like `brand/offers.md`, where a one-step approve-and-apply is the highest-leverage form). Route operator-owned findings to the operator (via the orchestrator as proxy); route another ACTIVE agent's file to that agent under THEIR branch prefix. Custody: a strike is DONE only when the OWNER lands it on the authoritative remote and the striker confirms - not when the striker merges; track each routed finding to closure, no fire-and-forget. The Librarian's Gate 1 (hard-stop on human-gated paths, regardless of author) is the backstop that enforces this for the compliance / offers / pricing paths.

**Carve-out (ownerless file -> maintainer applies).** The finding-not-fix rule binds you away from overstepping a PRESENT owner's authority; it does NOT bind you away from MAINTAINING an ownerless file. When a file's designated owner is a NON-ACTIVE agent (a brain directory with no agent running on the bus) AND the file is NOT on the human-gated list, there is no owner to route to, so the striking / maintenance agent becomes the legitimate de-facto maintainer-author: land the fix via a proper-prefix PR. Gate 1 does not fire on a non-human-gated path, and a recognized prefix clears the remaining Librarian gates and auto-merges - that IS the designed path for a non-human-gated content fix by a maintenance agent. Provenance is LOAD-BEARING, not decoration: mark the PR a strike applied ON BEHALF OF a dormant owner, so a revived owner inherits the file with the who+why trail rather than a surprise diff - a maintainer-applied strike WITHOUT that provenance note is INCOMPLETE, not done, because the whole justification for a maintainer touching another agent's file is that the touch stays legible to the owner who inherits it.

**Boundary.** The carve-out is gated on BOTH conditions together: owner-agent inactive AND file not human-gated. A human-gated path (`brand/offers.md`, `brand/compliance.md`, `products/*/compliance.md`, `agents/conventions.md`) stays operator-gated no matter which agents are active or dormant - the finding routes to the operator, always, and only Adam applies. And do NOT fold an ownerless non-gated file to the operator either: it is not on the human-gated list, so treating it as operator-owned misattributes ownership. Active-owner -> route to owner; dormant-owner + non-gated -> maintainer applies with provenance; human-gated -> operator only.

## Standing rule: bulk-job hygiene - agent-initiated background/backfill jobs run guarded, or not at all

Ratified 2026-08-21 PT (directed by the-orchestrator as a fleet-wide rule from the me-com Fable bulk-job runaway; incident found + evidenced by the-analyst; carried by the-sop-keeper). Companion to `capacity-incident-response.md` - that playbook is the RESPONSE side (detect + stop a live runaway); this rule is the PREVENTION side (do not launch one). Origin: 2026-08-21 - a meta-ads "Vision backfill" job spawned 3 parallel background agents fast-looping near-max-context **Fable** turns (~800k-token context re-read every ~12s), burning me-com `extra_usage_credits` from a days-flat 1359 to 23760 (~22.4k credits) in ~3h and accelerating, because the weekly Fable cap was already exhausted so EVERY turn billed as overage. Not a defect loop - an unguarded bulk job, reproducible by ANY agent that spawns a bulk background fleet. (Authoritative write-up: the-analyst's `FINDINGS-me-com-fable-bulk-job-runaway-2026-08-21.md`, git-tracked on the per-agent branch `analyst-snapshots/2026-08-22` at commit `9ffbf1aa` - deliberately NOT on main per the fleet-FINDINGS-off-Adam's-WIP-branch discipline, so it is cited by git coordinate rather than a relative link, which would resolve only in a transient working tree and break on a fresh main checkout or the backup remote.)

**Scope - fleet-wide, and specifically AGENT-INITIATED.** This binds ANY agent that launches a job which spawns background agents OR iterates a large work-list (backfills, sweeps, re-scans, bulk uploads) - not only the agent that got caught. Every me-com Fable agent (9 of them) can produce the identical shape. The rule targets AGENT-INITIATED bulk work: work the agent chose to launch on its own initiative. Adam-DIRECTED heavy work is operator-choice - his money, his call - and is EXEMPT from the cap-aware clause (guard 3) below; the other three guards still apply to it as good practice. THE TELL for which side a job is on is the PROVENANCE of the request: if the operator explicitly asked for THIS heavy work it is Adam-directed; if the agent decided to run it, it is agent-initiated. When unsure, treat it as agent-initiated (the safe default) and confirm with the orchestrator before launching.

**The four guards - all four, checked BEFORE launch.**
1. **MODEL-GUARD** - run a bulk mechanical pass on the CHEAPEST model that fits the task; never Fable/Opus or any max-context model for a bulk pass. A backfill re-reading an ~800k-token context every ~12s on Fable is the exact shape that ran here.
2. **THROTTLE** - bounded concurrency plus inter-item pacing; sequential or a small capped fan-out, never N parallel max-context agents each holding a huge context.
3. **CAP-AWARE SCHEDULING** - do NOT launch agent-initiated bulk work while the account's weekly cap is at or near exhaustion and `extra_usage` is actively billing (every turn then bills as overage); prefer off-peak or post-reset. This is the one guard Adam-directed work is exempt from.
4. **NO-RESUME-WITHOUT-GO** - a killed bulk job does NOT auto-resume on `--continue`; it restarts fresh ONLY with the guards in place AND an explicit orchestrator go for that named job. (This is why the caught agent got a force-fresh hard restart, not a `--continue` that would have re-spawned the runaway.)

**Why a launch-time guard, not just a response playbook.** The pre-incident baseline was ~0 overage for days; the runaway was a one-off launched into a cap-exhausted window, not a chronic drain. The cheapest place to stop a runaway is BEFORE it spawns - a detection-and-kill loop still pays for every turn until the kill lands (~22.4k credits here, in a ~9-minute detect-to-stop). Guard at launch; the capacity playbook is the backstop for the launch that slips through.

## Standing rule: a killed or interrupted run must fire its contracted make-up emits on recovery-close - "outputs verified" is not "run complete"

Ratified 2026-08-21 PT (directed by the-orchestrator, draft approved as written; evidence record = meta-ads trace 1787369892034; the dark register was caught by the-analyst's watchdog; the fix was encoded live by meta-ads in its meta-intake SKILL + GUARDRAILS; carried by the-sop-keeper). Emit-integrity companion to the bulk-job-hygiene rule above. Origin: 2026-08-21 - meta-ads's Friday 13:00Z intake sweep was killed mid-run (14:08Z stop, during the me-com bulk-job incident) before its end-of-run `static_sweep_complete` emit. The recovery verified the data outputs and closed the task, but fired no make-up emit - leaving the register DARK; the-analyst's absence-explained watchdog caught it at 38.6h.

**Rule.** A run's CONTRACTED EMITS are part of the run, not a side effect of it. A run that fires a contracted end-of-run signal (a sweep-complete, a register/heartbeat write, an audit emit) leaves a DARK REGISTER if it is killed or interrupted before that emit fires - and recovery-closing the task (verify outputs, mark done) does NOT restore it. So the close and the make-up emit are ONE action: recovery/close of a killed run MUST inventory the run's contracted emits and FIRE them - honestly labeled as late make-ups, on the arm that reflects reality (the `--error`/failure arm if the run died) - in the same breath as the close. **"Outputs verified" is NOT "run complete":** a task marked done while its contracted register stays dark is an integrity gap that reads as "never ran" to every downstream watcher.

**Scope.** ANY agent with a contracted emit - a killed run leaving a dark register is generic, not meta-ads-specific.

**Paired half - the detection side (the-analyst, same thread).** This rule PREVENTS the gap; the-analyst's absence-explained watchdog principle CATCHES it when prevention fails: a liveness check must ask BOTH did-the-beat-fire AND was-its-absence-explained - an unexplained dark register alarms, an honestly-labeled late make-up does not. Together they close the class in both directions: the runner fires the make-up emit on recovery-close, and the watcher distinguishes "never ran" from "ran, emit was late but labeled." Do not rely on either half alone - prevention without detection silently fails on the run that skips the make-up; detection without prevention alarms on every killed run forever.

## Standing rule: a displayed `next_fire` is not a fire - an interval cron's next_fire is a frozen projection after downtime

Ratified 2026-09-07 PT (dev mechanism verdict relayed via the-orchestrator; carried by the-sop-keeper). The distilled discriminator; full reference and the post-reboot first-beat gap are in [FINDINGS-interval-cron-next-fire-display-artifact-2026-09-07.md](FINDINGS-interval-cron-next-fire-display-artifact-2026-09-07.md). Same family as VT-7's daemon-side-liveness mitigation (verification-method-invariants spine) and the [silence-from-an-instrument corollary](#standing-rule-a-trigger-that-also-describes-the-healthy-case-is-a-proxy-not-a-detector) - a projected/frozen display misread as execution evidence.

**[UPDATE 2026-09-30 - basis fixed 2026-09-30 by `b8f367db`; conclusion stands on independent grounds.]** The list-crons DISPLAY basis in the Rule below - an interval cron rendering `next_fire = last_fired + interval` (frozen-past after downtime) - was FIXED on main by `b8f367db` (bundle 4/11 `c7a37529`, `task_1788798061911`): `list-crons` now single-sources the daemon's own advance logic, so an interval cron's displayed `next_fire` advances to the real future slot after downtime, matching expression crons. Two consequences, no more: (1) the expression-vs-interval discriminator is moot **FOR THE FROZEN-PAST SYMPTOM ONLY** - you will no longer see a past `next_fire` on an interval cron after downtime; (2) the durable lesson is unchanged and **permanent** - a displayed `next_fire` is a computed projection, NOT an execution record, so a correctly-rendered (future) `next_fire` is still not a fire; verify liveness via `get-cron-log` or the watchdog, never the projected field. This was a CLI-render fix (the daemon scheduler was always correct), so the rule's conclusion stands on its own grounds. The Companion-gap note below (ungraceful-power-off first-beat delay) is a SEPARATE sub-fix and is NOT yet landed - it stays PENDING.

**Rule.** `cortextos bus list-crons` renders `next_fire` differently by cron KIND: an INTERVAL cron (`4h`, `15m`, ...) shows `next_fire = last_fired + interval` (a frozen projection - a **past** timestamp after any downtime), while an EXPRESSION cron (5-field calendar) computes `next_fire` from now (correct future timestamp). So a past `next_fire` on an interval cron after downtime is a DISPLAY ARTIFACT, not a stopped scheduler - the scheduler is healthy. **Never read `next_fire` as evidence a cron did or will fire.** To verify liveness, use a real fire record (`cortextos bus get-cron-log <agent>` - the reliable path, resolves the log internally; the raw file is nested at `${CTX_ROOT}/.cortextOS/state/agents/<agent>/cron-execution.log`, NOT the `${CTX_ROOT}/state/<agent>/` some bootstrap docs cite) or the out-of-band [heartbeat-staleness watchdog](heartbeat-staleness-watchdog.md) - never the projected field. The discriminator is the cron kind (expression = trust, interval = frozen-past-after-downtime).

**Companion gap (fixes PENDING, task_1788798061911, Adam-gated).** An ungraceful power-off writes no `.daemon-stop` marker, so there is no missed-beat catch-up on reboot: the first heartbeat/interval-cron beat is delayed up to one full interval. An up-to-one-interval silence right after an ungraceful reboot is EXPECTED, not staleness (it stays under the watchdog's 2x-cadence + 0.5h threshold). Strike this companion note when the fixes land.

**Why (origin).** 2026-09-07 fleet-wide restart after the machine was off 2026-09-01 19:51Z -> 09-07 15:52Z: interval crons showed a `next_fire` back on 09-01 (the-sop-keeper's 4h heartbeat read `last_fire 19:32Z / next_fire 23:32Z` = 19:32 + 4h), which read fleet-wide as a possible ~40-min liveness outage before dev ruled it the render path. Never an outage - the scheduler came up healthy with the daemon; only the interval-cron display was stale-by-construction.

## Standing rule: what else does this config line buy - enumerate every purpose before deleting or narrowing

Ratified 2026-09-12 PT (security-agent, from a same-day gitleaks-allowlist near-miss in its lane; carried by the-sop-keeper). Family with the [load-bearing-constant comment](#standing-rule-put-the-check-where-it-runs-by-default-not-where-someone-has-to-choose-to-run-it---three-instances) (instance 3: a value that looks arbitrary but something depends on it) and the [least-privilege deletion-half](#standing-rule-least-privilege-for-untrusted-content-agents) clause (a removed capability is load-bearing) - the same shape each time: an artifact serves a purpose that stays invisible until removal breaks it.

**Rule.** Before deleting or narrowing a config artifact - an allowlist entry, an exclude pattern, a constant, a filter - enumerate ALL of its purposes, not just the obvious or stated one, and TEST for each of them (including non-correctness axes like performance and latency) before the change lands. A single line can be load-bearing for a SECOND, invisible purpose that only surfaces when its removal breaks it. The test at the point of removal: "what depends on this beyond the stated purpose?" - then exercise the change against every purpose you named, not only the one that motivated the edit. A correctness-only test on a change that is also load-bearing for perf passes clean and ships the regression.

Caught only by testing perf on the live change, then reverted and re-scoped to a separate bounded detector. The detection fix was right; the miss was not asking what ELSE the line bought before narrowing it.

## Standing rule: late + synchronized-to-the-second cron fires = host sleep - check pmset before chasing a scheduler bug

Ratified 2026-09-12 PT (claude-dev-agent root-cause of the 09-13 overnight cron-delay evidence bundle; landed by the-orchestrator, docs-only lane). Same family as [a displayed next_fire is not a fire](#standing-rule-a-displayed-next_fire-is-not-a-fire---an-interval-crons-next_fire-is-a-frozen-projection-after-downtime) - a benign scheduler-adjacent signal misread as a defect; this is the wake-batched-execution sibling.

**Rule.** Cron fires that land LATE, SYNCHRONIZED to the same second ACROSS agents, with the first late fire exactly on an hour boundary = HOST SLEEP, not a scheduler/daemon/REPL bug. Check `pmset -g log` FIRST (grep `Entering Sleep state` / `DarkWake` / `Clamshell Sleep`) and correlate each late fire to-the-second against a wake event (pmset logs LOCAL time - convert to Z before comparing). On battery this Mac sleeps (`sleep=1`, `powernap=0`); on AC it does not (`sleep=0`) - see `pmset -g custom`. While asleep, cron timers AND session processes freeze; each RTC DarkWake thaws the scheduler, which flushes every due timer in one synchronized batch, then resleeps - the same mechanism also explains long injection-to-processing gaps inside a single session. This is expected-operator-state (lid closed + unplugged at end of day): no code fix, no missed work (crons fire on wake). Host power config is prod + Adam-gated - never change it from an agent.

**Sleep-vs-wedge discriminator (2026-10-06 PT, the 10-05/06 two-night resolution: security `pmset` + the-analyst reconcile).** The wake-batched mechanism above makes a benign host-sleep gap and a genuine process-alive / inference-dark software WEDGE look identical from timing alone - both show up as a long injection-to-processing or cron-fire-to-execution gap. `pmset -g log` is the ARBITER. A gap whose whole span sits INSIDE a Sleep->Wake window (Clamshell / Maintenance Sleep -> the next FullWake or DarkWake) is SLEEP: benign, no code fix, work resumes on wake. A gap that SPANS host-AWAKE time with no covering sleep window in `pmset` is a candidate WEDGE: route it to the wedge-detector arc (the-analyst / claude-dev), do not close it as sleep. Classify EVERY boot-gap or cron-fire-to-execution gap against `pmset` before calling it either - "looks like a stall" is not a classification, and a wedge candidate is confirmed only once per-agent `pmset` has ruled out a covering sleep window.

**Classify on real clock reads, never composed or nominal timestamps (same resolution).** Do the `pmset` correlation with ACTUAL machine stamps (`date -u` at the moment of the read), never a cron-NOMINAL time or a hand-composed label written at read time. A composed stamp mislocates the gap and can make a host-sleep gap read as an in-window wedge: in the 10-05/06 resolution several specimens looked like awake-time wedges only because swap / liveness reads were labelled with cron-nominal times, and their real `date -u` stamps then bracketed the sleep and collapsed the apparent wedges to host suspension. This is the composed-label class the memory self-stamp helper (`scripts/memory-append.sh`, machine-derived `[ms:...]`) exists to prevent - apply the same real-reading discipline to any liveness or classification stamp.

**Read the sleep record at the right GRANULARITY, from RAW lines (2026-10-23 PT, the-sop-keeper, from a self-caught misclassification; arc disconfirm by claude-dev raw pmset + orch verdict).** Two refinements to the discriminator, both learned by getting one wrong. (1) GRANULARITY: an extended DarkWake is PROCESSING-CAPABLE - the daemon thaws, can fire and complete a write, then resleeps - so a completed write or session action minutes after lid-close does NOT prove an awake host. Judge awake-vs-asleep against Entering-Sleep / DarkWake granularity, not just FullWake boundaries; the span between two FullWakes is not uniformly awake. (2) COMPLETENESS: read the sleep record from RAW `pmset -g log` lines plus the literal command, NEVER a `tail`/`head`-truncated view, for any completeness-critical sleep scan. Origin specimen: a batched-fire gap was misclassified as awake-spanning because a `pmset ... | grep ... | tail -30` kept only the last 30 of a 108-line match, hiding all 19 Entering-Sleep events including a 14:05:59 PDT Clamshell onset - matched-but-truncated read as absent, absent read as awake. That is the read-limit TRUNCATION TELL (the fleet's gog sharp-edge 12) biting the agent's OWN instrument: a `tail -N` of a growing log reads complete when it is not, and its start-point drifts as the log grows. Count the full match (`wc -l`) or scope the grep to the window with NO line cap. The hedge bounded it: the gap was surfaced as a CANDIDATE, not an assertion, until the raw record was read - knowing the truncation guard is not the same as reaching for it on your own instrument.

**Fire-log discriminator (pmset-free) - see claude-dev's FINDINGS.** A sibling test needing only the daemon fire log: a GAP in `cron-execution.log` = host/daemon suspended (benign); CONTINUOUS fires landing into a dead/absent session = a true session wedge (the 09-17 shape). Full treatment + specimens in claude-dev's FINDINGS [FINDINGS-awake-host-flatline-is-clamshell-sleep-2026-10-23.md](FINDINGS-awake-host-flatline-is-clamshell-sleep-2026-10-23.md) (playbooks/fleet/) - carried here as a pointer-row rather than duplicated.

**Why (origin).** Night of 2026-09-12/13: the orchestrator's evening-review cron fired 02:00:00Z (exactly 60min late, on the hour), then cross-agent same-second batches at 03:47:34Z and 04:28:29Z (orchestrator + the-analyst), plus a 2.5h injection-to-processing gap in the orchestrator's own session - initially bundled to dev as a possible daemon-side stall. `pmset -g log` matched all three datapoints to wake events to the second (clamshell sleep 00:25:12Z on battery, RTC DarkWakes at 01:59:55Z / 03:47:33Z / 04:28:07Z). The daemon scheduler behaved correctly - it ran the instant the CPU was live. Operator tradeoff (Adam's call, not a bug): on-battery lid-close pauses overnight fleet autonomy until the next wake; AC power eliminates it.

## Standing rule: an unanchored dayNN counter is a composed label - name the anchor inline and compute N from it at emit

Ratified 2026-10-21 PT (the-orchestrator's single-voice ruling after a 3-way freeze-counter desync caught pre-brief; converged the same morning by all three emitters - the-analyst, meta-ads-agent, and meta-media-buyer-agent; codified by the-sop-keeper). A corollary of the composed-label class named in the host-sleep section's real-clock-reads row above (the class the memory self-stamp helper `scripts/memory-append.sh` exists to prevent): a hand-carried counter is a composed label in exactly the way a hand-written timestamp is - a number asserted by hand rather than computed from its source, so it drifts silently from what it claims to measure.

**Rule (four clauses).**
1. **Adam-facing text uses DATE anchors only** - "production frozen since your 10-10 stop (day 11); no launches since Aug 18" - never a bare `dayNN` (an unanchored count the reader cannot check or re-derive).
2. **Any internal `dayNN` counter carries a NAMED ANCHOR inline** - `day N (anchor: <event> <date>)` - so the count is self-describing and re-computable from the artifact alone.
3. **N is COMPUTED from the anchor date at emit time** (date arithmetic), never hand-carried or incremented across sessions. Hand-carry drifts: meta-ads-agent proved it with 3 duplicate-day specimens and a silent off-by-one convention switch on a hand-carried counter.
4. **Anchors are EVENTS, not counter-start dates.** Anchoring to "the day someone started counting" understates the true streak - the zero-intake counter read day 24 (anchored to an arbitrary 9-28 counter-start) when the real last-intake EVENT (2026-09-14 PODA-107) put the true streak at ~37. The anchor is the real event the count measures from, not the day a counter was opened.

**Canonical vocabulary** (three distinct events, never conflated): `no-launch day N (anchor: last launch 2026-08-18)` / `no-intake day N (anchor: last intake 2026-09-14 PODA-107)` / `freeze day N (anchor: 2026-10-10 operator-stop)`. One-line class-kill: name the anchor, compute N at emit, never hand-carry.

**Why (origin).** 2026-10-21 pre-brief: a 3-way freeze-counter desync - the orchestrator's carried 64 vs the-analyst's 63 vs the true days-since-the-10-10-stop of 11. Arithmetic showed the 64 was days-since-Aug-18 (last launch), hand-carried and off-by-one via duplicate-day drift, and silently conflated with the freeze streak - three different counters (no-launch / no-intake / freeze) on three different anchors merged into one hand-carried number. Named anchors + compute-at-emit closes the drift and the conflation at once; all three emitters adopted it the same morning, so this codifies a converged practice, not a proposal. The re-anchor's definitional reset was handled by the owners (both old and new numbers stated once, the step marked do-not-compare-across) per the definitional-reset discipline.

## Standing rule: verify the schema field name before believing a null/empty field

Ratified 2026-08-27 PT (promoted from private memory after a cross-org re-derivation; code-side specimen added 2026-09-15 from the fleet-health false-red root-cause; carried by the-sop-keeper). Sibling of [adjacent-property substitution](#standing-rule-adjacent-property-substitution-the-wrong-field-already-in-hand) - that rule is the WRONG-but-EXISTING field returning a plausible wrong VALUE; this is the NONEXISTENT field, which returns a false ZERO (null/empty/undefined). Same false-zero-from-the-instrument family as [a trigger that also describes the healthy case is a proxy, not a detector](#standing-rule-a-trigger-that-also-describes-the-healthy-case-is-a-proxy-not-a-detector).

**Rule.** A query or field-read against a NONEXISTENT field name returns null/NONE/undefined on EVERY record and is indistinguishable from "all values empty" - a false zero produced by the instrument, not the data. THREE RULES: (1) before believing any null/absent field, verify the field name against the ACTUAL schema - read one raw record, or read the writer code; this binds an interactive QUERY (jq/SQL) and CODE reading another system's file EQUALLY. (2) A second reader running the SAME query adds ZERO independence - the false zero survives both; confirmation requires a DIFFERENT instrument (raw file read, audit trail), not the same query twice. (3) Receiver-side: when a report asserts a null/absent field without naming its query, ASK FOR THE LITERAL QUERY before building on the claim - one question at message one collapses the chain. Same family as the grep -c / stdout.log false zero and never-trust-an-unvalidated-absence.

**Specimen A - QUERY side (self-caught in-org 2026-08-23; re-derived cross-org 2026-08-27).** Task JSON stores the assignee under `.assigned_to`, but jq on `.assignee` or `.agent` (neither field exists) renders every real assignment as null. The cross-org re-derivation surfaced it as a phantom "the tool creates unassigned tasks" finding that consumed two downstream hypotheses before the raw file killed it. Verify against the writer: `task.ts` writes `assigned_to` (source anchors: `task.ts:578` filters `task.assigned_to`, and `metrics.ts:144` filters the same field - two independent readers, one field name). Recurred 2026-09-19: the-analyst hit `.assignee` = 0 on a task-count reconciliation and retracted a false finding to orch as a result - the rule firing a third logged time.

**Specimen B - CODE side (2026-09-15, the writer-vs-reader instance).** The daemon fast-checker's `latestPromptSignal()` read `cron.interval`, but `crons.json` writes each cron's cadence under `cron.schedule` - the nonexistent field returned `undefined` on EVERY agent, silently flooring every agent's silent-death threshold to the 1h default (instead of 2x its own cron cadence) for the life of the monitor. A detector-vs-writer field mismatch that cannot error, only produce a plausible wrong default. Surfaced root-causing the 20:26Z fleet-health false reds; fixed in commit 2a35f08a (merged to main ec39f7d6, Adam-approved). The fix derives the threshold from `cron.schedule`, and its test fixture flips `interval` to `schedule` - confirming the writer's field was `schedule` all along.

**The shared signature.** Both specimens are a reader referencing a field the writer never writes; the read cannot error, it just returns empty/undefined and floors silently into a plausible default. So rule (1) binds CODE reading a sibling system's file exactly as much as an interactive query: before believing any empty result, verify the field against the WRITER's actual output - one raw record, or the writer code.

**Sibling - a WRONG-FORMAT false-zero, not a field-name one** (the-analyst, 2026-09-19; source-verified). The same false-zero symptom arises from the wrong INPUT FORMAT, not a wrong field. `cortextos bus list-tasks` (and any bus command parsed by `jq`) DEFAULTS to a human TEXT TABLE (the `printTasks` path); JSON comes only under `--format json`. Piping the default text table to `jq` fails to parse (`jq: parse error: Invalid numeric literal`), and an unguarded `jq` whose error is swallowed prints NOTHING - which reads exactly like an empty result set. So a programmatic reader that forgets `--format json` gets a false zero from the instrument's FORMAT, indistinguishable from "no rows". Same family and same fix-shape as the field-name case: before reading an empty `jq`/parse result as absence, confirm the input is actually the format you think (pass `--format json`; check the parser did not silently error). Rule (1) generalizes: verify the INSTRUMENT - field name AND input format - before believing any empty read.

**Sibling pointer - read-limit truncation-tell (2026-10-10).** A read whose result equals its limit is a TRUNCATION TELL, not a datum - the same instrument-produced false-reading family as the false-zeros above (a limit either over-reports completeness or under-reports existence of what lies beyond it). Canonical rule = knowledge.md gog sharp-edges edge 12, generalized 2026-10-10 from gog listings to ANY limit-bounded read (head -N, --max, pagination, column-truncating renders); re-read wider until the extent stops moving.

**Sibling - a RENDERED-DIFF-GREP false-zero** (claude-dev, 2026-10-11; root-cause of the-sop-keeper's 2026-10-10 blob-read mitigation on the canonical-publish path). Never grep a RENDERED/wrapped diff for column-anchored content (caret-plus, caret-minus, grep -c). The rtk diff-family (rtk git diff/show/diff) indents plus/minus lines 2 spaces so caret-anchored grep returns a FALSE 0 even on a real diff (a 0 is UNMEASURED, not no-changes). For any programmatic diff check use raw git --no-pager diff / git show or blob reads.

Ratified 2026-10-06 PT (the-orchestrator, from the pmset sleep-vs-wedge re-derivation of 2026-09-12 / 2026-10-06; carried by the-sop-keeper). The INVESTIGATION-time half of dedup. **Scope + the ritual-grep guard.** Fleet-wide, any agent opening an investigation. The trigger is the recurring-SHAPE match, not every anomaly: a genuinely novel shape has no documented prior to find, so a reflexive grep on everything would be dead ritual that only delays the work. Cheap, mechanical, recurring-shape-gated - a seed for the investigation, never a gate on it.

## ENFORCEMENT SEMANTICS: a scoped-cap percentage is a CEILING WARNING, never a STOP verdict; a stop is an OBSERVED refusal (2026-10-10, the-analyst, joint w/ the-orchestrator)

**RULE:** In usage/cap monitoring, a gauge at its ceiling (`scoped_limits[].percent=100 severity=critical`, a 5h/7d at 100%, etc.) means AT-CEILING, not STOPPED. Do NOT assert an agent/seat is "dark / refusing / hard-stopped" from the percentage alone. That is inferring an enforcement EFFECT from a capacity GAUGE. A stop is only established by an OBSERVED refusal: an actual refused turn, or a MISSED-when-DUE heartbeat from an agent on that seat. Enforcement can lag the gauge, or gate on a different window than the one being read.

**SPECIMEN (2026-10-10 Fable incident):** icloud Fable scoped read 100%/critical @23:10Z; the-analyst relayed "atwood seat hard-stopped, dark, refuses from next call" and the-orchestrator relayed "dark" to the user (Adam). DISCONFIRM within the hour: atwood-orchestrator's 00:29Z heartbeat EXECUTED (inference did not refuse) at scoped 100%; `extra_usage.is_enabled=false` + `spend.percent=0` + `used_credits=0` = not even billing overage. The 100% was a ceiling warning; enforcement had not bitten. Both agents asserted the unverified enforcement model (analyst's relay + orch's 97-boundary line to Adam) = JOINT OWNERSHIP, one correction issued (not a dark/not-dark/maybe-billing sequence) because the analyst ground-truthed its own relay against the heartbeat and flagged within the hour.

**WHY IT GENERALIZES:** this is the metric-scope-blindness family (08-15) extended to ENFORCEMENT semantics. There, a metric was read outside the scope it was valid for; here, a gauge was read as an effect it does not directly report. Same root: a number answered a question it was not measuring.

**CHECK BEFORE RELAYING A STOP (especially to a user):**
1. Is there an OBSERVED refusal (a refused turn, or a heartbeat missed WHEN ONE WAS DUE), or only a gauge at ceiling? Only the former is a stop. A missed heartbeat counts ONLY if one was due: know the agent's heartbeat interval before reading silence. Specimen: atwood-orch hb is 12h, so up to 12h of silence is EXPECTED and only a missed scheduled fire (its 12:29Z) signals a stop; without this due-ness check the rule would false-call a stop during a normal long interval.
2. Valve ON or OFF? Read `extra_usage.is_enabled` + `spend` + `used_credits`. ON = billing overage (continued use costs money, "world-a"); OFF = unmetered (may refuse on enforcement lag, "world-b"). The two demand different user messaging.
3. Name the real-stop INSTRUMENT (an observed refusal, or a missed-when-due heartbeat) and watch THAT, not the percentage. Verify the effect before asserting it as fact.
