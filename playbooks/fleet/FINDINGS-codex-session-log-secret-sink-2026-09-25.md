## Durable lessons (fold into leak-class practice)
- **AI-CLI session/log stores are a recurring secret sink** (codex `~/.codex/sessions/*.jsonl` + `logs_2.sqlite`; claude transcripts). They log verbatim: relayed inter-agent messages, tool output, and provider error bodies.
- **Classify full-vs-masked and real-vs-echo BEFORE rating.** Provider APIs mask keys in their own error bodies (`sk-svcac****`); our own incident messaging emits truncated refs (`sk-...last4`); codex echoes our security-tooling content (gitleaks configs, synthetic test fixtures) verbatim. All three inflate a naive scanner count and can masquerade as a cleartext leak. Verify the actual bytes (and query a SQLite surface with sqlite3, not a text grep) before calling it cleartext.
- **A dead/superseded token is not a current-live one:** cross-ref codex-log token fingerprints against current live `.env`/`accounts.json` before assigning severity.
- **Propagation observation (validates the fingerprint-only discipline):** the 12 truncated refs on disk were deposited by OUR OWN inter-agent incident messaging (the auth-recovery relay) landing verbatim in the codex session log / logs_2.sqlite. They are leak-safe BY DESIGN (prefix + last 4 only) - which is precisely why the fingerprint/prefix-only convention for credential references in bus messages matters: message content demonstrably persists to these logs, so a full-token reference in a message WOULD have landed in cleartext. Keep credential references in messages to fingerprint/prefix+last4 form.
- **Scanner-parity gap repeats across credential families** (sk-ant-oat01 2026-06-18; sk-svcacct/sk-proj now): a new provider token format silently evades both gitleaks-default and our custom rules until explicitly added. Detect-at-rest AND redact-in-flight must both carry the format.
- **`grep -l` is a locator, not evidence:** a case-insensitive `grep -l` with a SHORT (<=4 char) or base64-common alternation generates file-level false positives (here "fvMA" FP'd on base64 substrings in cacert.pem / pnpm.mjs and produced a phantom "3 files affected" claim). Never rate a leak from a `grep -l` file list - inspect the matched VALUE (masked? truncated? full?) before assigning "cleartext." This was the exact root of the false alarm here.
